STEP 01

先看 API 接线为什么失控

A concrete integration problem

问题不是「没有 API」，恰恰是 API 已经很好用了，却仍要为每个 AI 产品重做一遍接入。

假设团队已经有一个成熟的 NoteBox API：GET /notes/:id 读笔记， POST /notes 新建笔记，OAuth 控制权限，OpenAPI 文档也齐全。现在三个团队同时来接： 聊天桌面端想让模型整理笔记，IDE 想引用项目笔记，客服 Agent 只想读取客户授权的那几篇。

普通程序员看见的是「三次 HTTP 接入」。AI Host 真正需要补的却更多：把接口翻译成模型能选的工具 schema、 告诉模型何时可读何时可写、展示调用前确认、把错误变成模型能继续处理的结果、控制哪些工具进入上下文。 下一个日历 API、工单 API 加进来时，这套翻译还要再做三遍。

MCP 的出发点不是发明另一种业务 API，而是把这层重复胶水变成共同协议：数据源一侧实现 MCP Server， Host 一侧实现 MCP Client。它把最坏情况下的每对定制，改成每一边各实现一次公共边界。

第一条心智模型 MCP 是 AI 集成协议，不是 API 的竞争对手。 一个 MCP Server 最常见的实现，就是在里面继续调用你已有的 REST、GraphQL、数据库或本地文件接口。
起点来源：Anthropic 2024 原始发布说明 · 当前官方架构
STEP 02

把 API、RPC、JSON-RPC、MCP 放回各自层

Four layers, four different questions

它们不是四个互斥选项，而是从「能做什么」到「线上怎样表达」的一组嵌套答案。

同一个「读取笔记」需求，用 REST 常写成资源地址与 HTTP 动词：

# REST：HTTP 方法和 URL 共同表达操作
GET /notes/n-42 HTTP/1.1
Authorization: Bearer …

RPC 则更像在远处调用函数；JSON-RPC 2.0 给这个调用套上标准信封：

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "notes/read",
  "params": { "id": "n-42" }
}

JSON-RPC 只知道 method、params、id 和结果/错误；它不知道「工具是什么」、 什么时候应让用户确认，也不知道怎样列出服务器能力。MCP 在这个信封之上规定方法名、对象 schema、 discovery、能力、transport 和安全边界。

MCP 2.0 又给成功结果加了一条不能漏的规则：正常完成时，JSON-RPC 的 result 必须包含 resultType: "complete"。下面是一条完整的工具成功响应： 

{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "complete",
    "content": [
      { "type": "text", "text": "n-42: 项目上线清单" }
    ],
    "isError": false
  }
}
Complete 不是可选装饰 server/discover、list 方法和 tools/call 的正常成功响应都要带 resultType: "complete"。只有走 JSON-RPC error 时，才没有这个成功结果字段。
常见误读 远程 MCP 即使使用 HTTP，也通常是在一个 endpoint 上 POST JSON-RPC； 「用了 HTTP」不等于「它是 REST」。
规范依据：JSON-RPC 2.0 Specification · MCP Base Protocol
STEP 03

模型工具调用不等于 MCP

Decision format vs integration protocol

Tool calling 解决「模型怎样表达我要调用」，MCP 解决「Host 怎样找到并执行那个能力」。

模型供应商的 tool/function calling 通常做两件事：Host 把工具 schema 放进模型请求；模型不执行代码， 只返回一个结构化选择，例如「调用 read_note，参数是 n-42」。 真正执行工具的一直是 Host 及其外部系统。

因此，模型通常不直接“说 MCP”。模型看到的是 Host 挑选后放进上下文的工具描述， 返回的也是供应商定义的 tool call。MCP Client 在 Host 里面负责协议通信；没有模型参与时， 测试程序也完全可以直接发送 tools/list 和 tools/call。

为什么这个区别重要 模型选错工具，要改描述、选择策略或允许列表；MCP 连不上 Server，要查 transport、版本和认证。 把两层混成一层，会让排障永远打错靶。

工具也不是越多越好。每个 schema 都消耗上下文，名字相近会增加误选；生产 Host 通常需要 allowlist、 缓存或按需加载，而不是把 Server 的所有工具一次性塞给模型。

真实 Host 示例：OpenAI Remote MCP / Connectors 官方指南
STEP 04

分清 Host、Client、Server

Roles are trust boundaries, not machines

“Client/Server”描述协议角色；“本地/远程”描述部署位置。两组概念不要绑死。

  • Host：最终产品。它掌握用户、模型、UI、全局上下文和安全策略。
  • MCP Client：Host 内的协议适配器，通常与一个 Server 建立一对一协议关系。
  • MCP Server：暴露能力的一方。它可以是本地子进程，也可以是互联网服务。

Server 暴露的三个经典 primitive

不要被单词骗了 “Server”可以只是你电脑里被启动的一个命令；“Client”也不是用户看到的 App。 如果把 Server 默认理解成云机器，就会误判 stdio 的安全和生命周期。
架构依据：MCP 2026-07-28 Architecture
STEP 05

还原 MCP 1.0 的完整一天

Why the stateful design once made sense

本文后面统一这样称呼：MCP 1.0 = 官方 Legacy era，以 2025-11-25 为代表； MCP 2.0 = 官方 Modern era，指 2026-07-28 及以后版本。 这是学习用的分代名；代码里的 protocolVersion 仍必须填写官方日期版本。

MCP 1.0 Client 连接 Server 后，第一件事不是列工具，而是发 initialize：双方选择协议版本、交换身份和能力。 Server 返回结果后，Client 发 initialized 通知，进入 operation 阶段。之后 list、call、通知和 Server 主动请求 都发生在这次已协商好的会话里。

同一协议可以走两类 transport

反方向：Server 也可以调用 Client

上面全是 Client 发、Server 回。MCP 1.0 还有一条反方向的通道：Server 处理请求处理到一半， 可以主动向 Client 发一条独立的 JSON-RPC request。它服务于三个 Client feature—— 看懂这三个场景，才看得懂 STEP 08 的 MRTR 究竟替换掉了什么。

Elicitation要用户补字段或确认动作。模型要求删掉整个项目，Server 不直接执行，先反向让 Client 弹确认表单，用户同意后才落地。
Sampling借用 Client 的模型。Server 是本地检索工具，命中 50 个文件，自己没有模型也没有 API key，于是请 Client 把它们压成一段摘要。
Roots问清工作区边界。IDE 里 Server 想读文件，先问 Client「用户现在打开了哪些项目根目录」，据此限定搜索范围。

最容易卡住的是 sampling：Client 都已经生成摘要了，为什么还要还给 Server，再由 Server 返回给 Client？ 两个原因。其一，这次调用的业务逻辑属于 Server——摘要往往只是中间产物，Server 还要拿它去匹配 Git 记录、 组装最终报告；Client 半路截胡，Server 剩下的逻辑就断了。其二，外层那个 tools/call 全程都在挂起等待， 只有 Server 发出最终响应，这次调用才算闭环。

三条别记反 prompt 是 Server 写的——messages 与 systemPrompt 由 Server 构造， Client 只是握着 key 和模型选择权。 sampling 不是用户看不见的后台调用——规范要求 SHOULD 始终有 human in the loop， 应用 SHOULD 让用户在发送前查看并编辑 prompt、在交回 Server 前审阅生成结果，用户随时可拒绝。 要不要把上下文带进去由 Client 说了算——那是 includeContext 参数 （none／thisServer／allServers，默认 none，后两个已弃用）， 而 Client MAY 修改或忽略它且不必告知 Server。
读这段的前提 Sampling 特性自 2026-07-28 起已 deprecated：新实现 SHOULD NOT 采用， 现有实现 SHOULD 改为直接对接模型供应商 API。这里讲它是为了理解 MCP 1.0 为什么需要反向通道， 不是建议你在新 Server 里用。它也没有被移除——兼容实现仍可把 sampling/createMessage 放进 MRTR 的 inputRequests。 被移除的是「Server 主动发起独立 request」这个机制，不是这三个 feature 本身。

为什么当年这样设计很合理

  • 本地 stdio 里，一个 Client 对一个子进程；把能力和状态绑在连接上最直接。
  • 能力协商一次，后续报文短；Server 还能主动请求模型采样、用户输入或 roots 信息。
  • 远程 SSE 能持续推送，session 与 resumability 看起来能延续这套双向体验。
评价设计要看约束 MCP 1.0 不是“错协议”。它优化的是有连接、有会话、双向交互的世界； 真正的转折发生在远程 MCP 要穿过负载均衡器、代理和多副本平台之后。

STEP 06

负载均衡死亡现场

The remote scaling pressure

只要第二个请求可能落到另一个副本，“连接里记得什么”就从方便变成部署约束。

先看清被藏起来的是什么 initialize 一共只交换三样东西：protocolVersion、clientInfo、 capabilities，序列化后通常不到 1 KB。所以问题从来不是「这些数据太大、每个请求带不动」， 而是 MCP 1.0 允许后续请求把它们全部省掉，于是每条 tools/call 都成了一句只有听过开头才听得懂的话。丢的不是数据量，是自描述能力。 记住方向和直觉相反：MCP 2.0 不是让报文更省，而是让每个请求多带几百字节， 换回「任意副本都能独立读懂」。下面的扩容问题不要误读成「无状态是为了性能」。

NoteBox MCP Server 上云后跑三个副本。第一次 initialize 落到 A，A 为会话 S-42 记住版本、能力和进行中的状态。下一次 tools/call 被负载均衡器送到 B；B 收到了 session id， 却没有 A 的内存。协议本身没坏，部署路径已经断了。

MCP 1.0 不是不能扩，只是每条路都要付复杂度

粘性路由同一 session 永远送回 A；A 重启、扩缩容、热点倾斜仍要解决。
共享 session store所有副本读写集中状态；一致性、过期、清理和网络延迟进入关键路径。
连接代理保持长 SSE/双向通道；断线恢复、背压、取消和重放都要跨层协调。

网关还有一个更朴素的问题：要按「哪个方法、哪个工具」做路由、限流、计费或可观测性， MCP 1.0 代理通常必须解析 JSON body。能力又只在握手里出现一次，后续请求本身并不能完整说明自己是谁、能做什么。

别过度归因 这不等于“session 永远不好”，也不等于新协议自动无限扩展。 数据库、限流、幂等和长任务仍然需要应用设计；MCP 2.0 只是不再让协议正确性依赖连接记忆。
变化依据：2026-07-28 Release · 官方 Changelog
STEP 07

Stateless、sessionless 与显式 handle

Move hidden protocol state into the request

MCP 2.0 不是把状态消灭，而是要求：影响请求解释的协议信息随请求来，跨请求业务状态用显式名字指向。

2026-07-28 删除了 initialize / initialized 和 Mcp-Session-Id。 Client 的协议版本、身份与能力放进每次请求的 _meta。MCP 2.0 Server 必须实现 server/discover，Client 可以选择先调用它查看 Server 身份和能力； discovery 不会创造一个后续必须依赖的协议 session。 

// 简化示意：每个 MCP 2.0 request 自带协议解释所需 metadata
{
  "jsonrpc": "2.0",
  "id": 21,
  "method": "tools/call",
  "params": {
    "name": "commit_note_import",
    "arguments": { "workflowHandle": "wf_9K2" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "notes-host", "version": "1.4" },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

版本不匹配：读支持列表，协商共同 revision

如果 Client 填入 Server 不支持的日期版本，Server 返回 JSON-RPC 错误码 -32022， 在 data.requested 回显被拒绝的版本，并用 data.supported 列出自己支持的 revision。 Client 应该（SHOULD）与自己的支持列表求交集，并选择共同 revision 重试原方法。若决定重试， 本教程建议分配新的 JSON-RPC id，让两次请求的追踪和关联保持清楚；这是重试实现建议， 不是 versioning 规范额外规定的 MUST。没有共同版本时应向用户报告不兼容错误；既然已经识别出 MCP 2.0 的 -32022，就不能静默 fallback 到 MCP 1.0。 

// 原请求 id=30 的版本不被支持
{
  "jsonrpc": "2.0",
  "id": 30,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": {
      "requested": "2026-08-01",
      "supported": ["2026-07-28"]
    }
  }
}

// 选择共同版本后，用新 id=31 重试原工具与参数
{
  "jsonrpc": "2.0",
  "id": 31,
  "method": "tools/call",
  "params": {
    "name": "commit_note_import",
    "arguments": { "workflowHandle": "wf_9K2" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

显式 handle 怎样承载真正的跨请求状态

导入一万条笔记显然不可能每次从零开始。第一次请求可以创建业务工作流并返回 wf_9K2；后续请求把 handle 明写在参数里，任意副本用它查询共享数据库。 Server 重启并不会使协议语义失效，业务状态的所有权、过期和权限也有了明确落点。

Handle 不是认证 知道 wf_9K2 不应等于拥有它。Handle 应高熵、过期，并在服务端绑定已验证的用户与权限； 每次使用都重新授权，不能把“难猜”当访问控制。
规范依据：Base Protocol · Statelessness · Security Best Practices · State Handles
STEP 08

MCP 2.0 不只是“删 session”

MRTR, routing, cache, extensions, tasks, auth

它把原来的双向会话改造成可重试的请求循环，同时让代理、缓存和扩展有明确接口。

MRTR：Server 不再突然反向调用 Client

MCP 1.0 Server 可以主动发 elicitation 或 sampling 请求。MCP 2.0 移除独立的 Server→Client JSON-RPC request， 改用 Multi Round-Trip Requests（MRTR）：Server 正常返回 resultType: "input_required"， Host 按 inputRequests 取得用户/模型输入，再由 Client 用新的 JSON-RPC id 与同 key 的 inputResponses 重试原方法。只有 Server 返回了 requestState 时，Client 才 MUST 原样回传；若 Server 没有返回，Client MUST NOT 自行添加。 

// id=21 的结果：inputRequests 是 key → ElicitRequest map
{
  "jsonrpc": "2.0", "id": 21,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "confirm_commit": {
        "method": "elicitation/create",
        "params": {
          "mode": "form", "message": "确认提交 wf_9K2 的笔记导入？",
          "requestedSchema": {
            "type": "object",
            "properties": { "approved": { "type": "boolean" } },
            "required": ["approved"]
          }
        }
      }
    },
    "requestState": "opaque-state-from-server"
  }
}

// 新 id=22；同 key → ElicitResult map；本例 Server 返回了 requestState，所以必须原样带回
{
  "jsonrpc": "2.0", "id": 22,
  "method": "tools/call",
  "params": {
    "name": "commit_note_import",
    "arguments": { "workflowHandle": "wf_9K2" },
    "inputResponses": {
      "confirm_commit": {
        "action": "accept",
        "content": { "approved": true }
      }
    },
    "requestState": "opaque-state-from-server",
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

Headers：让网关不用先拆 JSON

同一次修订里的其他变化

Deprecated 与 Removed 不能混写 logging 这个功能处于弃用期，不代表 MCP 2.0 仍定义 logging/setLevel； roots 功能同理，notifications/roots/list_changed 已从新 RPC 面移除。 迁移时既要决定功能替代方案，也要删除不能再发送的旧方法与 elicitationId 字段。 旧 Tasks 也不能原样搬运：用 tasks/get + tasks/update 轮询替代 tasks/result，删除 tasks/list，并且只在双方协商 opt-in Tasks extension 后启用。
SSE 没有完全消失 MCP 2.0 Streamable HTTP 仍允许一个 POST 请求以该请求范围内的 SSE流式返回。 被移除/弃用的是旧的独立 GET stream、协议 session 与 SSE resumability；所以“MCP 2.0 删除 SSE”是错误总结。

Auth 也要分层看：MCP Server 在 HTTP OAuth 中是 resource server，Client 是 OAuth client，授权服务器可以独立部署。 Token 必须绑定正确 issuer 和 audience/resource，逐请求发送，禁止 token passthrough；stdio 不套这条 HTTP OAuth 流程， 本地凭据通常由进程环境或 Host 注入。

STEP 09

迁移不是“改一个版本号”

Choose compatibility, then redraw trust boundaries

先盘点你依赖了哪些 MCP 1.0 语义，再决定仅支持 MCP 2.0、双版本兼容还是暂时不动。

  1. 冻结基线：记录现有 Client/Server 支持的协议日期、SDK 主版本与 transport。
  2. 找隐含状态：搜索 initialize、initialized、Mcp-Session-Id、GET/SSE resume、Server→Client requests。
  3. 改请求模型：每次带完整 _meta；跨请求工作流改用显式 handle。
  4. 改交互：把 elicitation/sampling 路径重画成 input_required → retry。
  5. 双向互测：MCP 2.0 Client→Server、MCP 1.0 Client→兼容 Server、断线重试、多副本轮询都要测。
  6. 最后去 MCP 1.0：先观察真实调用方，再在弃用窗口内移除旧 transport 和 lifecycle。

迁移时顺手重画安全边界

  • 描述也不可信：工具名和 description 会进入模型上下文，恶意 Server 可把指令藏进去。
  • 确认要看完整参数：不能只问“允许调用 delete 吗”，要展示对象、范围与不可逆后果。
  • Token 不转发：Server 只接受为自己签发、issuer/audience 正确的 token。
  • Handle 每次授权：随机且过期，服务端绑定用户；错误用户即使拿到 handle 也应失败。
  • 本地 Server 是代码执行：Host 启动的命令拥有本地进程权限；展示完整命令、优先 stdio、尽量沙箱。
  • HTTP 查 Origin：本地 HTTP 默认只绑定 localhost；远程 endpoint 配合认证与最小 scopes。
  • 写操作要幂等：MCP 2.0 请求断线后没有 SSE resume；重试不可逆工具时使用业务幂等键。
两类“安全”不要混 JSON Schema 能拒绝缺字段或类型错误，却不能判断调用者是否拥有 n-42； OAuth 能认证调用者，却不能判断工具返回的一段文字是不是 prompt injection。

STEP 10

从手写报文走到真实 MRTR

Five labs and a self-check

不要一上来就让模型参与。先证明协议，再证明 Server，再证明 transport，最后才证明模型集成。

Lab 1 · 手写一个 calculator stdio Server

不用 SDK，只读 stdin 的逐行 JSON，按 id 返回 JSON-RPC。至少实现 server/discover、tools/list 和 tools/call；工具只有 add(a, b)。日志只写 stderr。用一个小 Client 连续发三条请求并断言结果。 三个方法的正常响应都必须在 result 中带 resultType: "complete"； 不能只给 tools/call 加，遗漏 discover 或 list。由于 discover 与 list 的结果适用缓存规则， id 1 的 server/discover 和 id 2 的 tools/list 还必须同时返回 ttlMs >= 0 与 cacheScope。 

// MCP 2.0 raw request：三条都必须携自描述 _meta
{"jsonrpc":"2.0","id":1,"method":"server/discover",
 "params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
 "io.modelcontextprotocol/clientCapabilities":{},
 "io.modelcontextprotocol/clientInfo":{"name":"raw-lab","version":"0.1"}}}}

{"jsonrpc":"2.0","id":2,"method":"tools/list",
 "params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
 "io.modelcontextprotocol/clientCapabilities":{},
 "io.modelcontextprotocol/clientInfo":{"name":"raw-lab","version":"0.1"}}}}

{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"add","arguments":{"a":2,"b":3},
 "_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
 "io.modelcontextprotocol/clientCapabilities":{},
 "io.modelcontextprotocol/clientInfo":{"name":"raw-lab","version":"0.1"}}}}

第三条请求对应的完整成功响应应当是：

{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "content": [
      { "type": "text", "text": "5" }
    ],
    "isError": false
  }
}
Lab 1 断言 对 id 1、2、3 分别断言 response.result.resultType === "complete"， 对 id 1、2 额外断言 result.ttlMs >= 0 且 cacheScope 字段存在， 再断言 id 3 的文本内容为 5。缺少这些必需字段时，即使 payload 看起来正确也不算 MCP 2.0 合格成功响应。

Lab 2 · 用 Inspector 找协议错误

运行 npx @modelcontextprotocol/inspector 连接本地命令，检查工具清单、输入表单和结果。 故意发送缺少 b、字符串类型的 a、不存在的工具名，并观察错误落在哪一层： JSON-RPC envelope 或 CallToolRequest 这一层的 schema 畸形，以及未知工具名，属于 JSON-RPC protocol error；已经通过合法 CallToolRequest，但对具体工具的 inputSchema 校验发现 缺少 b、a 类型错误或数值越界，则仍返回成功 envelope，其结果是 resultType: "complete" 与 isError: true。边界取决于失败发生在哪个 schema 层。 Inspector proxy 能启动本地进程，不要暴露到公网。

Lab 3 · 用官方 SDK 重写，但保留协议测试

选择支持 2026-07-28 的官方 Python 或 TypeScript SDK。实现同一个 add，再加一个只读 resource 和一个 prompt； 用 SDK 的内存 Client 测 list → call，不要让测试依赖模型 API key。锁定依赖版本， 并显式确认 Client 使用 MCP 2.0 或 auto negotiation，而不是从“SDK v2”推断 wire mode。

进入 HTTP 前，再沿用 NoteBox 故事做一个故意带隐式状态的两步 workflow： start_note_import(noteIds) 校验笔记并把导入计划存进当前 Server 进程的 currentImport；commit_note_import() 从同一内存变量取计划并提交。 单进程测试会通过，这正是 Lab 4 要打破的假安全感。两个工具正常成功时同样返回 resultType: "complete"。 

# Python 官方文档当前的起步方式；具体 API 以锁定版本为准
uv add "mcp[cli]"
uv run mcp dev server.py

Lab 4 · 切到 Streamable HTTP

先保持隐式状态实现不变，只替换 transport 并启动 A/B 两个 Server 副本。每一个 JSON-RPC POST 都必须发送 Accept: application/json, text/event-stream，同时携协议 metadata；抓包观察 MCP-Protocol-Version、Mcp-Method、Mcp-Name，并确认没有 Mcp-Session-Id。

让负载均衡器把 start_note_import 发到 A，再把 commit_note_import() 发到 B。 B 没有 A 的 currentImport，应稳定复现 “no active import”——这是本实验必须先看到的红灯， 不是靠 sticky routing 藏起来的偶发错误。

然后迁移：start_note_import 把计划写入共享应用存储，并在完整成功结果中返回 workflowHandle=wf_9K2；commit_note_import(workflowHandle) 显式接收 handle， B 用它读取同一计划。重跑 A→B 路径应变绿。最后让一个响应使用请求范围内的 SSE，断开后用新 request id 与业务幂等键重试，证明 SSE 仍可用、但旧流不会恢复。

Lab 5 · 给同一个 commit_note_import 加 MRTR

不换工具、不换故事：第一次调用 commit_note_import(wf_9K2) 不产生副作用， 而是返回 input_required，让 Host 展示导入条数、目标 notebook 与影响；批准后用新 id、 同 key inputResponses 重试。若结果带 requestState 就 MUST 原样回传；若未带则 MUST NOT 添加。重试成功后才真正提交。

测试接受、拒绝、超时、重复重试与跨用户 handle 五条路径。用户 B 拿用户 A 的 wf_9K2 必须在产生 elicitation 之前就被拒绝，避免泄露计划内容；相同幂等键的重复批准只能提交一次。 最后才可选接入真实模型 Host，并保留 mutation 每次审批与 allowed tools。

完成标准 不是“Chat UI 里成功了一次”，而是：raw 报文能解释、Inspector 能复现、SDK 测试无模型依赖、 A→B 隐式状态测试先红后因 handle 变绿、MRTR 的拒绝/授权/幂等重试路径有自动化测试。

十问自测

1. NoteBox REST API 已经稳定，三个 AI Host 都要接入。第一步应选哪种架构？

保留现有 REST API，在它前面实现一个 MCP Server；各 Host 复用 MCP Client。业务 API 继续做事实来源，MCP 统一 AI 接入边界。

2. id=3 返回了正确的数字 5，但 result 里没有 resultType。能判成功吗？

不能。MCP 2.0 的正常成功结果必须包含 resultType: "complete"；先检查它，再检查具体 payload。

3. 模型返回了 read_note(n-42)。下一步谁负责发送 tools/call？

Host 把模型的选择交给对应 MCP Client，由 Client 向 Server 发送 tools/call；模型通常不直接说 MCP。

4. 一个只访问本地仓库的开发工具，应优先选 stdio 还是公网 HTTP？

优先 stdio：Host 启动本地子进程，协议走 stdin/stdout，日志走 stderr。只有出现跨机器访问等需求时再引入 HTTP 与认证边界。

5. start_note_import 落到 A，commit 落到 B 后找不到状态。正确修复顺序是什么？

先保留这个失败作为回归测试，再让 start 返回显式 handle、把计划写入共享应用存储，最后让 commit 携 handle 读取；不要只用 sticky routing 隐藏问题。

6. Server 返回 -32022、data.requested 与 data.supported。Client 应怎样继续？

把 data.supported 与自己的版本列表求交集：有共同 revision 时 SHOULD 选择它并重试；没有时向用户报告不兼容。重试使用新 id 是本教程的关联与追踪建议，不是 versioning 的额外 MUST。不能把已识别的 MCP 2.0 错误静默 fallback 成 MCP 1.0。

7. 一个规范标记为适用的结果只带 ttlMs、没带 cacheScope，可以把后者当可选优化吗？

不可以。适用结果上的 ttlMs 与 cacheScope 都是 MUST 字段，不是可省略的 hints。

8. 发送 Streamable HTTP JSON-RPC POST 时，Accept 应填什么？还能用 SSE 吗？

每次发送 Accept: application/json, text/event-stream。响应仍可在本次请求范围内使用 SSE，但旧 GET stream、session 与 resume 不再属于 MCP 2.0 core。

9. 用户 B 拿用户 A 的 workflowHandle 调 commit。先发确认表单还是先拒绝？

先鉴权并拒绝。Handle 不是认证；若先返回 input_required，确认内容本身就可能泄露 A 的导入计划。

10. “logging deprecated”与“logging/setLevel removed”是否矛盾？

不矛盾。前者描述功能的迁移生命周期；后者说明该 RPC 已不在 MCP 2.0 wire。ping、roots list-changed、resource subscribe/unsubscribe 和旧 elicitation completion 也要按 removed RPC 清理。
