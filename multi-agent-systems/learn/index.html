STEP 01

先看一次「全能单 Agent」的死亡现场

任务最擅长在第 8 轮从内部瓦解

在讨论如何设计多 Agent 之前，先看清一个被寄予厚望的单 Agent 是如何走向自我窒息的。

假设你构建了一个“全能客服与研发诊断助手”。用户给它下达了一个任务： “查找用户 9812 昨天支付失败的日志，排查原因，修复底层 SQL 字段类型，并给用户发封邮件告知处理完毕。”

单体 Agent 启动了经典的 ReAct 循环。它被赋予了 25 个工具：SQL 查询、日志检索、Git、代码编辑、测试运行、邮件通知……

STEP 02

单 Agent 的三道物理硬墙

为什么窗口标称 1M/2M 也救不了单 Agent

上下文窗口不是无底洞；装得下，绝不等于用得好。

硬墙 1 · 上下文污染
每一步工具调用的返回，都会成为后续每轮推理的永久注意力负担。历史堆栈越厚，指令遵循率越呈指数级衰减。
硬墙 2 · 工具认知过载
塞入超过 20 个跨域工具时，函数 Schema 互相重叠。模型在进行 Tool Choice 决策时频繁出现意图混淆与参数幻觉。
硬墙 3 · 角色人格撕裂
单 Prompt 无法兼顾对抗性需求：要求同一个模型既要最大胆地探索重构，又要最吹毛求疵地严控合规，结果必然是平庸与妥协。
// 为什么不能盲目上 Multi-Agent？因为代价极其高昂： Token_Cost(MAS) = 3 ~ 10 × Token_Cost(Single_Agent) End_to_End_Latency(MAS) = ∑ Latency(Agent_i) + Coordination_Overhead // 结论：只有当业务明确撞上上述三道硬墙时，才被允许引入 Multi-Agent！
Anthropic 经验法则 先压榨单 Agent 的极限。 在考虑多 Agent 之前，先尝试引入 Tool Search Tool（动态检索并按需加载工具 Schema）， 或通过更严格的 Prompt 约束收窄上下文。只有当单 Agent 确实因上下文污染无法完成闭环时，再启动多 Agent 架构。
STEP 03

第一性原理：按「上下文边界」拆分

绝不按「问题类型」拆分 · 破除传话筒陷阱

绝大多数工程师在设计多 Agent 时踩的第一个大坑：把敏捷开发的角色生搬硬套给 LLM。

最常见的直觉做法是：设一个“架构师 Agent”、一个“程序员 Agent”、一个“测试员 Agent”。 Anthropic 在官方指南中明确指出：这是教科书级别的反模式（Anti-Pattern）！

❌ 反模式 · 按问题类型拆分 (Decomposing by Problem Type)
架构师 -> 程序员 -> 测试员
典型的“传话筒效应（Telephone Game）”：程序员丢掉了架构师推演时的隐式边界； 测试员拿到代码时，根本不知道实现时的假设，只能写出浮于表面的弱测试用例。交接成本巨大，上下文彻底断裂。
✅ 推荐范式 · 按上下文边界拆分 (Context Boundaries)
Auth 模块 Worker (设计+编码+自测)
赋予负责特定垂直领域的 Worker 完整的闭环能力。负责 Auth 模块的 Agent 自己写代码并自己写单测，因为它拥有该领域最完备的上下文。
“Decomposition follows context, not problem type. Keep work grouped by the context it requires.” Anthropic · Building Multi-Agent Systems (2025/2026)
STEP 04

五大基础协作拓扑与树状编排

从 Prompt Chaining 到 Google ADK 的 Single Parent Rule

建立系统架构的心智地图：确定性流水线 vs 动态自主集群。

拓扑模式 机制特征 控制流 典型适用场景
1. Prompt Chaining 静态串行链路，节点 $A ightarrow B ightarrow C$ 纯代码顺序调用 文本逐步清洗、固定格式转换
2. Routing 意图分类器将输入派发至专有 Agent 条件分支 (Switch) 客服工单智能分流、领域专有工具隔离
3. Parallelization Sectioning (并发分块) / Voting (多路投票) Fork-Join 并发 超长研报分段起草、多模型投票压制幻觉
4. Orchestrator-Workers 中央主管动态拆解任务并分派给专业 Worker 动态运行时编排 复杂全栈代码重构、全网多源深度调研
5. Evaluator-Optimizer 生成者 (Generator) 与评估者 (Critic) 双节点打回闭环 迭代反馈循环 高难度算法编写、专业法律合规文书拟定
Google ADK 的单一父节点原则 (Single Parent Rule) 在 Google Agent Development Kit (ADK) 体系中，智能体被严谨划分为 LLMAgent（大脑）、WorkflowAgent（流程管理器，如 Sequential/Parallel/Loop）与 CustomAgent。 ADK 强制规定：每个子 Agent 在组织结构中必须且只能有一个确定的父级节点，杜绝网状混乱引发的状态死锁与多头指挥。
STEP 05

规划引擎的进化跃迁

从盲目 ReAct 到 ReWOO 与 LLMCompiler 的 DAG 并行

如何在长程复杂任务中既保持全局视野，又消除 80% 的模型推理延迟？

代际 1 · Naive ReAct（单步贪心）

Thought -> Action -> Observation 循环。每执行一步都要拉起一次大模型全量上下文推理。 缺乏全局蓝图，一旦遇到意外报错极易陷入原地打转。

代际 2 · Plan-and-Execute（两阶段规划）

Planner 先生成完整执行计划，由 Executor 串行推进。克服了短视问题，但在中间执行阶段仍需要频繁唤起大模型。

代际 3 · ReWOO（变量占位解耦）

Planner 输出包含变量占位符的计划（如 #E1 = Search[Paris Weather], #E2 = Convert[#E1]）。 Worker 执行期完全由纯代码运行，零大模型调用！节省 80% Token，延迟降至 API 物理极限。

代际 4 · LLMCompiler（DAG 依赖流式调度）

Planner 流式输出有向无环图（DAG），Task Fetching Unit 在依赖满足的瞬间并行发射独立任务， 端到端速度提升高达 3.6 倍。
ReWOO 的核心精髓 将“规划时的逻辑依赖”与“执行时的 API 调用”彻底剥离。Planner 只负责构思蓝图并绑定占位符， 执行引擎拿到蓝图后如同运行一段解析脚本，直到最后需要汇总时才由 Solver 做单次提炼。
STEP 06

状态治理：工件指针模式（Artifact URI）

杜绝跨节点数据倾倒的工程黄金法则

当 Agent A 处理了 50MB 的销售数据，它该如何交给 Agent B 进行分析？

01 / 全局黑板 (Blackboard)
Shared State
所有 Agent 围绕同一个会话字典读写。优点：全局可见；危险：并发写入时极易产生状态污染与竞态。
02 / 消息传递 (Actor Model)
Message Passing
如 AutoGen v0.4 Core。Agent 内部状态完全隔离，仅收发强类型消息。优点：天然支持跨机分布式与高并发。
03 / 工件指针 (Artifact URI)
Pointer Passing
生产级首选。数据沉淀至外部存储，Agent 间仅传递 80 Token 的 URI 句柄（如 art://sales.parquet）。
// ❌ 灾难：直接在消息中倾倒 10,000 行 CSV (烧掉 40,000 Tokens)
{"role": "assistant", "content": "这是提取的数据：id,name,amount\n1,Alice,100\n2,Bob,200..."}

// ✅ 正解：工件引用指针模式 (仅需 60 Tokens)

  "artifact_id": "art_20260823_parquet",
  "uri": "s3://company-analytics/q3_sales.parquet",
  "schema": ["user_id: int", "region: string", "gmv: float"],

沙箱隔离与精简汇报 给每个 Subagent 分配独立的上下文沙箱。当 Subagent 经过 15 轮内部搜索探索后，向 Supervisor 汇报时只提交一份 100 Token 的结构化 JSON 结论，其内部的中间失败与无用 Trace 全部留在沙箱内销毁，保护主管 Context 始终保持纯净。
STEP 07

危险的数学：级联失效率与 LLM Saga

乘法法则下的残酷现实 · 不可逆副作用回滚

分布式系统的残酷铁律：每增加一个节点，系统的不可靠性呈指数级飙升。

// 在 n 步串行多 Agent 链路中，系统整体成功率为单步概率的连乘积： P_system = ∏(i=1..n) p_i // 假设单步可靠性高达 95% (p = 0.95)： 5 步链路成功率 = 0.95⁵ ≈ 77.38% 10 步链路成功率 = 0.95¹⁰ ≈ 59.87% // 超过 40% 的任务直接失败！ 20 步链路成功率 = 0.95²⁰ ≈ 35.85%
不可逆操作的灾难 当 Agent 拥有写数据库、发邮件、扣费等真实副作用时，简单的失败重试会导致极其严重的脏数据灾难。

解法 1 · 局部幂等重试提升单步可靠性

给每个关键步骤配置 Pydantic 校验与最多 $k$ 次重试，使单步等效可靠性提升为 $p_{\text{effective}} = 1 - (1 - p)^k$。 在 $p=0.90, k=3$ 时，等效可靠性跃升至 99.9%。

解法 2 · LLM Saga 逆向补偿事务

每一个具有副作用的 Agent 工具必须成对注册正向操作与补偿操作（如 lock_stock 对应 unlock_stock）。 一旦第 4 步发生未捕获异常，编排引擎按逆序自动调用补偿链，将系统安全回滚至干净状态。
STEP 08

假共识与马屁精陷阱 (Sycophancy)

打破模型与生俱来的顺从偏好 · 盲审裁判机制

多智能体辩论不会自动产生真理，除非你打破它们的顺从偏好。

学术界提出了 Multi-Agent Debate（多 Agent 辩论）来抑制幻觉。但在工程实操中， LLM 普遍经过 RLHF 对齐，表现出极强的顺从妥协倾向（Sycophancy）。 次级 Agent 在第二轮就会无原则附和主要 Agent 的错误观点：“您说得太有道理了，我收回我的意见……”

防线 1 · 强制对立角色
显式将 Agent 设定为控方与辩方，并在 Prompt 中加入对抗性惩罚项，严禁在前两轮达成共识。
防线 2 · 异构模型部署
混合调用 Claude、Gemini 与 GPT，彻底打破同源预训练数据带来的共性认知盲区。
防线 3 · 盲审裁判 (Judge)
裁判 Agent 只能审查匿名论点与真实的 Tool 执行返回值。不带外部可验证证据的论点一律判无效。
警惕早期误判 (Early Victory) 在验证 Agent（Verifier）中，最常见的问题是跑通了一个最基础的 Happy Path 就草草宣布胜利。 必须在 Verifier 的 System Prompt 中强制注入反向测试与全量回归用例要求。

生产落地的代码模式与框架选型矩阵

面对繁杂的框架生态，如何在生产环境中写出不失控的代码？

框架 核心哲学 状态模型 最佳适用场景
LangGraph 状态图 (Pregel) 驱动 集中 TypedDict + Reducers 复杂、需要断点续跑 (HITL) 与时间旅行的企业级系统

# Anthropic 生产级推荐：应用层硬编码熔断循环
def run_production_orchestrator(goal: str, max_attempts: int = 3):
    orchestrator = LeadOrchestrator()
    verifier = IndependentVerifier()
    
    for attempt in range(1, max_attempts + 1):
        plan = orchestrator.plan(goal)
        results = [Worker(t.domain).run_isolated(t) for t in plan.tasks]
        draft = orchestrator.synthesize(results)
        
        # 独立验证闸门 (强制负向测试)
        audit = verifier.verify(goal, draft)
        if audit.passed:
            return {"status": "SUCCESS", "data": draft}
            
        goal = f"{goal}\n[Attempt {attempt} Failed]: {audit.reasons}"
        
    raise RuntimeError(f"MAS 未能在 {max_attempts} 轮内收敛，触发熔断并通知人工！")
STEP 10

监控、评估与「第一处偏离」归因

从「感觉集群坏了」到精准锁定元凶

如何从由 15 次跨 Agent 调用构成的 Trace 树中，用算法找出真正的第一个错误节点？

1. OpenTelemetry GenAI 语义追踪

统一使用 gen_ai.conversation.id 串联整个集群调用链，记录每个节点的 agent.name、tool.call、Prompt 与 Completion Token 消耗。

2. 第一处偏离检测（Earliest Divergence Detection）

沿着拓扑执行树做断言检查。系统级错误的根因几乎永远是最早发生偏差的那个 Step，下游 Agent 的所有异常只是被污染 Context 的受害者。

3. 反事实消融归因（Counterfactual Step Ablation）

将怀疑出错的 Agent 输出替换为人工作出的标准答案（Gold Output）。若下游全流程立即恢复成功，则该 Agent 承担全额失效归因责任。
