从一个 Agent
到一支可控团队

Multi-agent 不是 single-agent 的升级按钮。它用更多独立上下文换取上下文保护、并行探索与专业化， 同时引入交接、合并、错误级联与更高成本。十步走完后，你应该能证明一个任务究竟值不值得拆。

STEP 01

先建立最强的单 Agent 基线

The baseline is part of the architecture

不知道一个 agent 能做到什么，就不知道多个 agent 究竟解决了什么。

假设值班工程师收到一条支付失败告警。先把相关日志、runbook 和代码交给一个 agent，让它给出故障假设、对应证据、修复建议和用户说明。工程师复核时不只看答案，还要看它读过哪些材料、在哪一步走偏、有没有漏掉约束。这条完整 trace 就是 baseline。

如果同类任务里，单 agent 反复被长日志挤掉关键上下文，或者总在几个相似工具之间选错，拆分才有明确目标。反过来，如果它已经稳定完成任务，再加 planner 和 reviewer 主要会增加交接，未必带来可测收益。先把简单方案做到可复现，后面与 multi-agent 的对照才有意义。

【来源事实】Anthropic Anthropic 建议先从最简单可行方案开始；其测试中，等价任务的 multi-agent 实现通常消耗 single-agent 的 3 到 10 倍 token。这是厂商经验，不是跨任务定律。
为什么“第 8 轮一定崩”不是一个好判断？
轮数本身不是因果变量。真正要测的是：上下文里有多少无关材料、工具是否混淆、关键约束是否丢失、任务是否能局部隔离。某些长任务一个 agent 仍能稳定完成，某些短任务则可能因为权限或路由设计立即失败。
STEP 02

只为三类真实收益拆分

Context · Parallelism · Specialization

多一个 agent 必须对应一个可测瓶颈，而不是多一个角色名称。

上下文保护
子任务读取大量材料，但主任务只需要短结论。worker 在自己的 context 中过滤，只回传证据与摘要。
并行探索
多个研究路径彼此独立，可同时运行。主要收益通常是覆盖面；墙钟时间可能下降，总计算量往往不会随之下降。
专业化
工具、权限或领域上下文明显不同。先试工具发现与更好提示；路由边界清晰时再拆 specialist。

拆之前，先说清瓶颈落在哪张卡上。主 agent 被长材料淹没，才需要上下文保护；几条检索路线互不等待，并行才可能缩短墙钟时间；权限或工具集合确实不同，专业化才有稳定边界。一个任务可能同时命中两项，但最好先写下主要假设，后面的实验才能解释收益来自哪里。

  • 瓶颈可以在同一任务集上复现，而不是一次主观感受。
  • 更好的 prompt、检索、压缩或工具发现仍解决不了。
  • 拆分后的质量收益有机会覆盖成本、延迟和维护风险。
不要拆简单任务、强耦合任务、不可隔离的写操作，以及没有 trace、预算、超时和验收条件的系统。
STEP 03

按上下文边界拆，不按工种拆

Decomposition follows context

如果 worker 必须不断追问“你刚才为什么这么做”，边界通常拆错了。

坏边界 · 传话筒
规划 → 编码 → 测试 → 评审
同一功能的实现动机和失败历史被反复压缩、转述，协调成本可能高于工作本身。
好边界 · 可隔离
认证模块 / 支付模块
每个 worker 在清晰接口内完成设计、实现与自测；独立 verifier 做黑盒验收。

两张卡的差别在交接物。按工种拆时，下一位往往要补齐上一位的动机和试错过程，结果是 agent 在传话。按模块拆也不是自动正确：认证和支付之间仍要有清楚的接口，worker 的输出还得能单独测试。下面三个问题就是在检查这件事，而不是替角色表找更多名字。

三个边界测试

  • worker 能否在少量初始输入后独立工作？
  • 结果能否用 schema、artifact 和证据短交接？
  • 并行任务是否同时满足“无数据依赖”和“无副作用冲突”？
STEP 04

分清拓扑、控制流与通信

Google ADK as one concrete vocabulary

“谁管理谁”“谁先运行”“数据怎么传”是三个不同问题。

维度回答什么常见选择风险
拓扑谁能调用或管理谁orchestrator–workers、router–specialists、peer路由错误、中心瓶颈、责任不清
控制流谁先运行、谁可并行sequential、parallel、loop、DAG错误级联、race、不收敛
通信输入输出怎样传递message、shared state、artifact reference污染、陈旧值、权限扩散
【来源事实】Google ADK 博客 ADK 用 parent/sub-agent hierarchy 组织 agent，并介绍 SequentialAgent、ParallelAgent、LoopAgent，以及 shared state、LLM-driven delegation 和显式 AgentTool 调用。
版本边界 · 截至 2026-08-23 这些名称是 ADK 的具体表达，不是通用 MAS 标准。当前 ADK 2.0 还提供 graph、dynamic、collaborative workflows；实现前应重新查官方 API 与支持矩阵。

把这三层画清后，才轮到 planning。Multi-agent 轴问的是执行责任和上下文是否拆给多个自治运行单元；planning 轴问的是系统是否显式生成任务、顺序与依赖。一个决定“谁来做”，一个决定“工作怎样安排”，所以同一套拓扑可以有或没有 planner，同一份 plan 也可以交给一个或多个执行者。

下一步的四象限不是成熟度阶梯。默认从左上角的 single-agent 逐步行动开始：只需要全局依赖时向右，保留一个 agent 但显式规划；只需要隔离上下文或 specialist 时向下，用 router 协作而不先生成全局计划；只有任务形状也要动态发现、执行又确实需要独立 worker 时，才走到右下角的 planner → workers → joiner。

STEP 05

Planning 与 multi-agent 是正交维度

How work is planned ≠ who executes it

Planner、executor、joiner 可以是不同 agent，也可以只是同一应用里的普通节点。

无显式 planning
有显式 planning
Single-agent
逐步行动一个 agent 观察后决定下一步
先计划再执行一个 agent 生成 step list 或 DAG
Multi-agent
Router → specialist没有全局 planner 也能协作
Planner → workers → joiner计划与执行单元均被拆开
常见误区有四个节点不代表有四个 agent；先生成 DAG 也不自动让系统成为 multi-agent。判断标准是运行单元是否拥有可区分的上下文、职责、工具或控制权。
STEP 06

用同一个任务看三种决策方式

ReAct · ReWOO · LLMCompiler

差别不在名字，而在何时决定下一步、怎样传值，以及 ready 分支能不能同时运行。

统一任务：查出本届 Super Bowl 的两支参赛队伍，找出各自 quarterback，再按相同的常规赛字段比较两人。下面只用 Team A、QB-A 这类占位符，不提供时效体育答案。

轨迹 A · ReAct
  1. Round 1：模型调用 Search(参赛队伍)，收到 Observation: Team A, Team B。
  2. Round 2：模型调用 Search(Team A quarterback)，收到 Observation: QB-A。
  3. Round 3：模型查询 QB-A 的统计，observation 却是季后赛口径。
  4. Round 4：模型根据上一轮结果改查 regular season，收到 Stats-A。
  5. Round 5：模型调用 Search(Team B quarterback)，收到 QB-B。
  6. Round 6：模型查询 QB-B 的 regular season 统计，收到 Stats-B。
  7. Round 7：模型调用 Compare(Stats-A, Stats-B)，收到比较结果这一条 observation。
  8. Round 8：模型读完 Round 7 的 observation，才输出 Finish(answer)。
这是一条单轨串行链：下一轮必须等上一轮 observation，Team A 与 Team B 两条分支不会自动并发。历史也会不断变长。假设 10 轮请求的输入依次是 1k, 2k, …, 10k tokens，每轮都重传完整历史，没有缓存或压缩，而且只计算输入 tokens，那么累计输入是 55k。这只是说明重复读取历史的假设例子，不是 ReAct benchmark。
轨迹 B · ReWOO
  1. Planner 先写完整蓝图：#E1 = Search[参赛队伍]；#E2 用 #E1 中的 Team A 名称查询 Search[Team A quarterback]；#E3 对 Team B 做同类查询；#E4/#E5 再分别查询两名 QB 的 regular season 统计。
  2. 原版 Worker 不做 readiness 调度，而是按 #E1 → #E2 → #E3 → #E4 → #E5 顺序填空。后一个查询需要变量时，先把已经得到的 evidence 替换进去。
  3. Solver 最后读取全部 Plan/Evidence 作答，Work 阶段没有原生 replan。这个共享示例的 Worker 全是 Search 工具，所以模型调用只有 Planner 1 次加 Solver 1 次，共 2 次。
#E 让值流向可见，也减少每步重送完整历史。它不是经过拓扑校验的 DAG，作者原版 Worker 也不并行。一般情况下，如果计划里出现 LLM[...] Worker，每执行一个就会额外调用一次模型；因此“Planner + Solver = 2 次”只适用于上面这个全 Search 示例。
轨迹 C · LLMCompiler
  1. Planner 流式产出任务及依赖：任务 1 是 search_teams()；任务 2、3 是 search_qb("first team in $1") 与 search_qb("second team in $1")；任务 4、5 分别用 $2、$3 查询 regular season 统计；任务 6 等待 $4 和 $5 后比较。
  2. 普通调度组件检查哪些依赖已经满足，再把 ready tasks 交给异步 Executor。任务 1 完成后，两个 search-backed QB 查询可以一起运行；任一 QB 返回后，对应统计查询就能启动。
  3. 比较任务等待两边统计。Joiner 读取完整结果后选择 Finish 或 Replan；Replan 会开启下一轮规划，但改动范围取决于新计划，不能保证只局部修补。
Planner 负责生成任务和依赖，调度与执行不要求固定使用某一种线程池。并发优势来自关键路径：流程按 1 → (2 ∥ 3) → (4 ∥ 5) → 6 推进，而不是把所有节点一次性发出。漏边会让任务过早执行，多余的边会损失并发；共享写冲突、限流和补偿仍要由应用处理。

Plan-and-Execute 位于 ReAct 与后两者之间：它先列 step list，再由 executor 逐项执行并让 planner 判断结束或重规划，但没有 ReWOO 的显式 evidence slots，也没有 LLMCompiler 的 readiness scheduler。

任务信号优先考虑需要接受的代价
新 observation 经常改变下一步ReAct串行关键路径、重复模型决策、增长中的历史
路径可预见，主要想减少重复 promptReWOO原版顺序 Worker，执行期不改计划
多个慢工具有清晰的部分依赖LLMCompilerPlanner 必须画对边，还要治理并发与副作用
步骤固定，模型无需决定路由普通 workflow灵活性较少，但更容易测试和恢复
来源边界LangChain 提供 Plan-and-Execute、ReWOO、LLMCompiler 的比较入口；ReAct、ReWOO 和 LLMCompiler 的执行细节与实验数字应回到各自论文和作者代码。完整逐轮轨迹、调用形状与准确 benchmark 口径见研究笔记 §4 和 §7.4。
共同边界三者都不天然是 multi-agent。一个模型、一段调度代码和普通工具就能实现这些流程；只有节点真正启动拥有独立上下文和控制权的 agent runtime 时，具体部署才是 multi-agent。
STEP 07

用合同交任务，不用一段含糊 prompt

Task contract before delegation

可靠 handoff 至少要说清目标、边界、依赖、权限、预算、证据和失败语义。

# 教学性通用模型，不是任何厂商协议
task:
  id: research-adk-001
  objective: 提取 ADK 协作模式及版本边界
  include: [hierarchy, workflow, communication]
  exclude: [写最终跨来源结论, 修改仓库]
  dependencies: []
  permissions:
    tools: [web_read]
    write_scope: []
  budgets:
    max_model_calls: 6
    deadline_seconds: 180
  output:
    required: [claim, source_url, evidence_type, uncertainty]
  errors: [blocked, retryable_error, partial, success]
TaskEnvelope
描述“为什么派、允许看什么、允许做什么、怎样算完成”。
AgentResult
返回状态、摘要、证据、artifact、未决问题和可否重试；不倾倒整段 scratchpad。

TaskEnvelope 解决执行前的不确定性，AgentResult 让协调者在执行后能验收、续跑或止损。可以做一个朴素检查：worker 此刻退出，另一个 worker 能否只凭任务合同和已保存的 artifact 接手？如果还得翻整段对话猜目标，handoff 仍然没有设计好。

STEP 08

失败时局部恢复，不要整队重跑

Classify · Preserve · Repair · Stop

失败恢复的核心不是“多试几次”，而是保留已验证成果，只修明确缺口。

分类失败
timeout / 缺证据 / 冲突
→
冻结成功结果
checkpoint / artifact
→
有界修复
局部 retry / replan

先看失败有没有污染共享状态或产生外部写入。只读查询超时而原计划仍成立时，可以重试这个节点；新证据推翻了下游依赖时，应重规划受影响的分支；已经发出的邮件或数据库写入，则要先确认幂等、审批和补偿范围。分类决定哪些结果可以冻结，也决定修复要停在节点、分支还是人工处理。

场景 A：一个 research worker 超时
保留其他 worker 已验证的结果；缩小超时节点范围并复用已抓取 artifact；最多进行约定次数的重试。再次失败则返回 partial 和缺口，不把全队重新运行。
场景 B：两个 worker 给出冲突结论
先比较来源时间、版本、定义和证据，不用多数投票抹平分歧。必要时新增一个只核对冲突点的验证任务，并在最终结果中保留仍未解决的不确定性。
场景 C：任务包含发邮件或写数据库
无数据依赖不代表可以安全并行。先标注 read/write set、幂等性、审批与可补偿范围。补偿动作不能保证恢复到“从未发生”，不可逆副作用应尽量置于最终审批之后。
STEP 09

从 single-agent baseline 评测净收益

Outcome · Trajectory · Cost · Reliability

多 agent “能完成”不够；它必须稳定优于最强的简单方案。

实验要先从失败预算反推，而不是让更复杂的系统靠无限重试换成功：固定每个版本可用的 model/tool calls、tokens、wall time、重试和 replan 次数，再在同一任务集、模型与工具下比较。这样测到的才是架构收益，而不是额外计算量。

版本系统它回答的问题
S0single agent＋相同工具最简单系统能做到什么？
S1single agent＋压缩/工具发现更简单的优化能否解除瓶颈？
W1固定 sequence/parallel workflow收益是否只来自确定性控制流？
M1动态 orchestrator＋workers动态分解和独立上下文是否还有净增益？

这四个版本是一组因果消融：S1 判断收益是否来自单 agent 优化，W1 隔离确定性编排的贡献，M1 最后才检验动态分解和独立上下文。随后给每个版本注入相同的 timeout、缺证据或冲突结果，沿 trace 找到第一处偏离：如果原计划仍成立，只重试失败节点；如果新证据改变了下游依赖，只重规划受影响的局部子图；预算耗尽就返回 partial 或停止。

因此实验还要记录“保留了多少已验证工作”和“恢复后是否重新通过验收”。只比较最终成功率，会把整队重跑与局部恢复混为一谈，也看不出多 agent 的额外故障面究竟有没有被控制住。

  • 结果：正确性、完整性、约束满足、引用有效。
  • 轨迹：分解覆盖、路由、工具参数、越权、第一处偏离。
  • 效率：tokens、成本、model/tool calls、p50/p95、关键路径。
  • 可靠性：多次运行通过率、恢复成功率、失败类型分布。
【实践建议】保留门槛只有当 M1 相对 S0/S1/W1 的质量或覆盖提升稳定大于额外成本、延迟、故障率与维护负担时，才保留动态 multi-agent。
STEP 10

做一个会失败的最小 Lab

Build evidence, not a demo

真正的练习不是“多开三个 agent”，而是证明边界、恢复和评测都成立。

任务
选择一个需要阅读 9–12 份一手资料的技术问题，最多 3 个只读 research workers、最多 1 次 replan。
四个版本
依次实现 S0、固定并行 W1、动态 M1、M1＋人为 timeout/缺证据。
记录
质量、来源覆盖、引用错误、tokens、model calls、wall time 与恢复结果。
毕业标准
能说清收益来自隔离、并行、专业化，还是其实只来自更好的 workflow。

毕业自测

1. Planner 生成 DAG，普通函数执行节点。这一定是 multi-agent 吗？
不一定。Planning 描述分解、依赖和调度；如果只有一个 agent，其余节点都是确定性函数或工具，它仍可以是 single-agent workflow。
2. 两个任务没有数据依赖，就一定能并行吗？
不一定。还要检查共享资源、写集合、rate limit、锁、幂等、审批与权限。数据独立只是并行安全的一部分。
3. M1 质量高 2%，成本高 6×，应该上线吗？
信息不足。还要看统计不确定性、任务价值、安全硬门、关键切片、故障/恢复率、p95 延迟预算，以及 W1/S1 是否已经得到相同收益。
如果十步只记一条先有 baseline，再谈团队；按 context boundary 拆；用同题评估证明净收益。
