把上下文压小
而不压坏

如果把大模型比作破案侦探，上下文窗口就是它的办公桌。任何一个能连续办案几个小时的 AI Agent，背后都必然有一套极为讲究的“桌面收纳法”。 桌上如果堆满了几百页的旧案卷和冗长日志，它不是把桌子压塌报错，就是抓起新线索转头就忘。 上下文压缩绝不是锦上添花的算力省流技巧，而是让 Agent 能够持续存活并把复杂长程任务做完的前提。 本文摒弃空洞的口号与公式，用最贴近日常的生活类比和步步递进的思维链，带你轻松搞懂：怎么把越来越厚的历史记录压得足够小，却丝毫不伤及核心推理线索。

STEP 01

最真实的“翻车现场”：Agent 是怎么被撑爆的？

直击长程任务的瓶颈根源

在琢磨怎么收纳之前，我们得先看一眼没做收拾的案发现场到底有多惨烈。

想象一下，你招了一位极其聪明的新助理帮你修一个复杂的登录 Bug。你对它下达了第一道任务指令：

# 第 1 轮
User: 修复登录 bug                                    ~20 token
Agent: 我先看看项目结构                                ~30 token
Tool: ls -R                     → 返回 800 个文件路径   ~9,000 token

# 第 2 轮
Agent: 读取认证模块核心代码
Tool: read auth/session.ts      → 返回整个文件完整内容 ~14,000 token

# 第 3 轮
Agent: 全局搜索相关的调用
Tool: grep -rn "validateSession" → 返回 60 处匹配代码   ~7,000 token

# 第 4 轮 …… 第 12 轮（不知不觉累加）
                                                     累计 ~180,000 token
# 第 13 轮
Provider: 400 Bad Request — context_length_exceeded

仅仅跑了 13 个回合，Bug 还没查清楚，模型就直接弹出了 400 报错，当场暴毙。 停下来仔细看一眼这几个数字的巨大反差： 你对它说的那句话只有短短 20 个 Token，而它随手读一个文件就吃掉了 14,000 个 Token —— 两者整整差了 700 倍！

直觉反转：第一条关键思维 很多人第一反应以为：“对话说得太多，所以把窗口聊爆了”。
但真实的 Agent 世界恰恰相反：撑爆上下文窗口的从来不是聊天，而是工具吐出来的一长串文件内容与终端日志！
这就好比你让助理查账，你只问了一句“上个月花了多少”，他却把厚厚三整箱银行流水账单直接一股脑全砸在了你的办公桌上。每一次工具调用，都像在小桌子上倒下一卡车的沙子。

如果你是负责设计的工程师，你的第一直觉是不是：“那咱们等大模型窗口再做大一点不就行了？从 8K 涨到 200K，甚至 1M、2M，总装得下了吧？”
这里藏着软件工程里一条百试不爽的铁律：办公桌换得再大，你堆杂物的胆子也会跟着等比例放大。
在 8K 时代，你只敢小心翼翼让 Agent 读函数片段；到了 1M 时代，你就敢让它跑全库索引、读几十兆的日志、同时拉起五个子任务。只要没有主动收纳机制，多大的窗口都会在几分钟内被迅速填满。

STEP 02

上下文窗口这堵墙，到底有什么怪脾气？

三个违背直觉的底层特性

要想设计出一套聪明的收纳法则，首先得摸清大模型上下文的三大“怪脾气”。它们个个反直觉，却决定了一切工程选择。

脾气一：历史不是追加日记，而是每次重念一遍的“前情提要”

大模型是没有状态记忆的（Stateless）。到了第 13 轮，它并不是“接着第 12 轮的想法继续往下琢磨”， 而是你必须把前 12 轮发生的所有对话、工具调用和报错日志，一字不差地从头到尾重新给它念一遍，然后在末尾加上新的一句话。

这就像一位记忆只有几分钟的金鱼侦探，每次翻开新的一页，都要把前面的整本案件卷宗从头读到尾。这个特性带来了三个连锁后果：

  • 每一轮都必须能装得下：不是最后收尾能装下就行，而是办案的每一步，桌子都绝对不能塌。
  • 只要前情提要一字不差，云厂商会给你打巨额折扣：各大厂商普遍支持 Prompt Cache（提示词缓存）。只要你念的前半部分与刚才完全一致，模型不用重复计算，缓存命中部分直接按约 0.1 倍（一折）计费！所以“背着旧账本”本身的推理开销其实很低。
  • 但只要你动了开头一个字，整个打折全部作废：前缀缓存就像整齐排列的多米诺骨牌，开头一旦被改写，后面的缓存立刻全部失效。
两难困境：压缩与缓存的天然博弈 只要你想压缩，就必须对早期的历史动手术（比如做个总结）。但那一块恰恰是缓存的最前端！
你刚把旧记录压成一段摘要，原有的 Prompt Cache 瞬间全部报废。下一次请求发出去，系统就得按全价甚至 1.25 到 2 倍的溢价重新往缓存里写入：

换句话说：你省下的本来是只花一折的廉价旧 Token，却反手付了一笔全额的缓存重建违约金！
所以记住推导出的第一条原则：千万别把“为了省钱省 Token”当成做压缩的理由，这笔账往往根本算不过来。我们做压缩，纯粹是为了保命 —— 保证 Agent 不被活活卡死！

脾气二：桌上堆得下，不代表脑子看得清（迷失在中间）

很多初学者会想：“既然窗口有 200K，那只要还没到 190K，我就完全不管它，等快撑爆了再压缩呗？”

这就好比复习考试：你一口气看了厚厚几百页的书，你能记住的往往只有第一章的导论和最后一章的总结，夹在正中间那大几百页，脑子里全是一片糨糊。大模型也是一模一样的！学界著名的发现 Lost in the Middle（迷失在中间）证明： 大模型对上下文开头和末尾的注意力极高，而对中段内容的检索准确率会大幅下挫，呈现出一条深陷下去的 U 形曲线。

一段塞到 90% 的超长上下文，中间那 100K 就算没有报错，模型也大概率正在“神游”，关键线索摆在它眼前它也会漏看。 因此，压缩不仅是为了防止报错撞墙，更是为了主动给桌面清灰，把有用的线索擦亮。

脾气三：供应商标的容量，可能只是个“参考值”

文档上白纸黑字写着“支持 128K 窗口”，你在实际写代码时就真敢用到 128K 吗？往往不敢。因为服务商往往还要给模型的输出预留空间，或者服务端内部还有隐藏的 Guardrail 校验，甚至不同分词器的计算方式有细微出入。

在调研的 11 个开源平台里，kimi-code 的思路极其朴素而管用：它根本不去盲信文档上的宣称值。只要在实际运行中遇到一次溢出报错，它就立刻把本次请求大小的 85% 默默记下来，当成这台模型的真实物理红线，并在后续执行中永远留出足够的安全余量。 既然测不准墙在哪，就撞一次记住它，以后绕着走。

STEP 03

不压会怎么死，乱压又会怎么伤？

看清天平两端的真实代价

别一拍脑袋就去调个小模型写摘要。工程的本质，永远是在不同的代价之间做权衡。

如果不做压缩，Agent 会以哪三种姿势倒下？

姿势一：当场暴毙（硬失败）
API 抛出 400 Context Exceeded。整个会话直接死锁中断，前面干到一半的代码和推理全部报废，刚才花掉的几十轮推理费也全部打了水漂。
姿势二：钱包大出血（软失败）
缓存悄无声息过期。供应商的缓存通常只有 5 分钟寿命。Agent 在跑长测试、做复杂推理时稍稍耽搁一下，超时后再发请求，几十万 Token 的历史就得全额全价重新计费。
姿势三：悄悄变傻（静默失败）
开始胡说八道、逻辑倒退。接口完全没报错，但模型开始遗忘你一开始立下的规矩，或者把刚才已经验证行不通的蠢办法又重复试一遍。这是最危险的死法。

那随便找个小模型总结一下不就得了？看三个触目惊心的实证数字

很多人以为“做压缩嘛，随便抓个便宜小模型把前文归纳一下不就完了”。近期的多项权威评测用真实数据给这种轻率泼了一盆冷水：

避坑提醒一：别把写摘要当成廉价的“外包杂活” 上面的 6.5 分血泪教训告诉我们：做摘要的模型选谁，对最终任务成败的影响跟主模型几乎平起平坐！
这就像一位极聪明的老板，如果配了一个抓不住重点、每天写错交接备忘录的糊涂实习生，老板的决策也会跟着被带偏。在写摘要上省下几厘钱，可能换来主模型几百次调用全打水漂。
避坑提醒二：压缩就像“传话游戏”，会悄悄吃掉你的规则 第二、第三个数字揭示了同一个残酷的现实：在把长篇大论压缩变薄的过程中，特定规则是最容易被优先漏掉的。
像“不能删库”、“不要输出敏感信息”这类全网通识，基座大模型自己在预训练时背过千百遍，还不容易忘；但你们团队独创的软约定（比如“修改任何接口必须走 v2 路由”），摘要模型一看觉得是细枝末节，三两句省略掉，下一轮 Agent 立刻把这规矩抛到了九霄云外。
STEP 04

建立思维坐标系：收纳整理的六个动作层

给混乱的专有名词理清脉络

各大开源框架起的名字五花八门 —— Compaction、Compression、Condensation、Pruning、Eviction…… 别被这些花哨的名词绕晕了。就像收拾一间杂乱的房间一样，世界上任何一套上下文治理机制，本质上都在做这六件事：

L1Measurement 计量先拿尺子量一量，桌面到底堆了多少？看云厂商返回的 Usage，还是在本地粗算字符
L2Trigger 触发 ⭐什么时候该动手收拾了？占满 80%？还是剩余空间告急？还是固定每 5 步整理一次？
L3Selection 选点哪些东西必须留在桌上，哪些可以打包收走？切口划在哪里才不会把对话切碎？
L4Reduction 削减 ⭐收走的东西怎么变薄？呼叫模型写摘要、直接拿大剪刀截断、去重，还是直接丢掉？
L5Reassembly 重组整理好之后怎么摆回桌上？保证角色一问一答格式合法、工具调用的请求和回包别脱节
L6Persistence 持久化 ⭐扔掉的旧草稿去哪了？直接扔碎纸机彻底不要了，还是归档到地下室以后还能搜回来？
研读 11 家源码后的干货结论 对比各家顶级开源项目的代码会发现：大家在 L1（怎么量）、L3（选点切口）、L5（怎么拼回去） 上的做法高度收敛，几乎都用同一套标准的工程解法，我们直接复用业界成熟方案即可。
而真正决定一个 Agent 是“玩具”还是“工业级系统”的分水岭，全在标了 ⭐ 的这三层：什么时候该动手（L2）、用什么手段削减（L4）、丢掉的内容还要不要找回（L6）。你自己写代码时，应把八成精力放在这三项设计上。
STEP 05

亲自动手：六步搭一个好用又抗造的最小压缩器

步步推导，每一步都给你开箱即用的黄金默认值

不要一上来就搞极其庞杂的微服务。跟着这六步推导，你就能亲手写出一个稳健可靠的生产级压缩组件。

第一步 · 计量：优先看官方账单，没有就用字符粗估

模型调用结束后，接口返回的 usage 字段是最权威的数据源。如果是在发送请求前需要本地预估，最实用省事的经验法则是：英文字符与代码数 / 4（中文大约按 字符数 / 1.5 估算）。一开始千千万万别在本地挂一个重量级的 Tokenizer 分词包！分词不仅耗费 CPU，而且判断“桌子是不是快满了”根本不需要精确到个位数。

但这里有个九成新手都会踩中的隐形巨坑：量桌子时，别只去数聊天记录！
很多代码只去统计 User 和 Assistant 说了多少句话，却忘了桌面上还摆着一个巨大的显示器 —— System Prompt 和几十个工具的 JSON Schema 定义！ 一个稍微复杂点的 Agent，光是把所有工具的入参和说明列出来，就能吃掉 15,000 Token。如果你没把这部分算在总预算里，实际早爆仓了，你的代码还以为桌上很空呢。

第二步 · 触发：看“还剩多少空地”，别看“用了百分之几”

先看一个经典的直觉陷阱：很多人写代码习惯写 if (used > 0.8 * window)（用了超过 80% 就触发）。
停下来用思维链推导一下：
如果窗口是 200K，剩下 20% 是 40K 空闲；
但如果窗口是 1M，剩下 20% 是足足 200K 空间！—— 你放着相当于一个标准大模型的 200K 宽敞空地不用，急吼吼地去触发压缩？

更合理的衡量口径是看绝对安全余量（Absolute Headroom）：if (window - used < 20000)。
我们核心关心的不是占了百分之几，而是：“剩下的空地，还够不够模型再尽情吐一次长回答和长代码？”

20,000 这个数字有充分的行业实证：OpenClaw（TypeScript）和 opencode（Python）是两个不同团队在不同时间用不同语言写的项目，最后竟然不约而同把安全余量都定在了 20,000 Token！

但别生搬硬套常数！必须配一个小模型保护兜底： 
reserve = min(20000, window * 0.15)   // 遇到小窗口模型时，按比例退让
if (window - used < reserve) compact()
想一想为什么？如果你把程序跑在一个只有 16K 窗口的本地小模型上，20,000 的余量要求直接超过了它的整个脑袋！结果即便是一句空对话，系统也判定为“空间不足”，每轮交互都疯狂触发压缩，压完还是不足，最终引发无限压缩的死循环。开源项目 OpenClaw 的源码里，就为此特意写了一长串防护与注释。

第三步 · 先做一招“免费”的物理瘦身，然后重新量一次！

一旦余量报警，很多人第一反应是赶紧呼叫大模型写摘要。
慢着！先别急着花钱调模型。
回想 Step 01：最占地方的是什么？是终端吐出来的几千行测试报错或文件搜索结果！
你想想平时看一份几十页的崩溃日志，是不是只看开头是哪一行挂了，以及最后几行报错堆栈，中间成千上万行千篇一律的业务加载流水你根本连看都不看？

直接用代码做一步确定性的“掐头去尾”粗剪（不要钱、零延迟、确定性极强）：
直接复用业界成熟的默认规则：单次工具输出如果超过 8192 字符 → 只保留头部 4096 字符 + 尾部 1024 字符，中间直接插入一行显眼的提示：[... 中间冗余日志已自动省略 ...]。

最精妙的一步在于“重新量一次”：粗剪完毕后，拿尺子再量一遍当前体积。如果水位已经乖乖回落到了安全红线以下，恭喜你，昂贵的大模型摘要直接跳过不做了！
你不仅省下了一次 API 费用，保住了宝贵的 Prompt Cache，还免除了一次信息被总结篡改的风险！很多只是偶尔读了个大文件的轮次，单靠这一招就能直接满血自愈。

细节防坑：字符串截取请务必按 Unicode 码点（Code Point）进行切分，切忌按 UTF-16 的裸字节去切！否则遇到 Emoji 表情或者生僻字，恰好砍在代理对中间，就会劈出半个不可解析的乱码。

第四步 · 选点：把两头当成宝贝护住，专挑中间打发走

必须呼叫模型做摘要时，挑选哪一段呢？策略极为简单坚决：
顶部的 System Prompt 钉死不许动，底部最新的几轮原话和工具结果当成宝贝牢牢保留，唯独把夹在中间的那一大段历史抽出来拿去总结。

这完美顺应了 Step 02 讲的 U 形注意力规律：既然模型天生对头尾最敏感、对中段最迟钝，那我们就顺水推舟，把中段原本就看不清的杂草修剪成干练的精华！

注意：保护尾部时，一定要按 Token 预算保护（例如保留最近 8,000–20,000 Token），绝不要图省事写成“保留最近 10 条消息”！因为有的消息只有三个字，有的消息带着一整个文件，按条数保护极容易发生体积暴雷。

第五步 · 削减：给摘要模型一张“固定表格”，绝不让它写自由作文

千万不要写“请总结上述对话”这种毫无约束的 Prompt！这就像你让助理“写个工作总结”，他大概率会给你写一篇散文。
你要做的是递给它一张格式严谨的表单，逼它按项填空：

## 核心目标 — 用户最初到底要什么，验收标准是什么？
## 当前进度 — 严格分成 [已搞定] / [进行中] / [受阻卡壳] 三大栏！
## 关键技术决策 — 敲定了什么方案，以及为什么这么决定？
## 下一步明确动作 — 具体要敲什么命令、改什么代码，不要写抽象方向
## 关键文件清单 — 触碰了哪些关键路径，为什么它重要？

这是各大平台打磨出来的最小完备集。尤其是“进度分三栏”这一条格外值钱 —— 它能彻底治好模型的盲目乐观，逼它把“事情已经做完”和“自己以为做完但还没验证”严格区分开。

第六步 · 重组：摘要贴回去，顺带附上一句“接头暗号”

把新鲜生成的结构化摘要包装成一条消息放在历史开头，后面无缝接上保留的最新对话尾部。
在最后务必追加一句明确的续接指令：
“请注意：上述早期历史已经完成结构化归档。请直接沿着既定目标推进下一步任务，绝不要在回复中啰嗦重复或讨论‘上文已经被压缩’这件事！”

这句叮嘱绝不是客套话。如果少了它，很多模型开口第一句就是：“好的，根据您提供的历史摘要，我看到我们之前完成了……接下来我将……”—— 它会傻乎乎地把用于系统治理的内部记忆当成了用户的闲聊输入。
现在就可以动手跑跑看 把上面这六步连起来，你的代码量并不大，但已经构建出了一套具备极强抗造能力的最小压缩管线。在早期切忌画蛇添足加复杂的奇技淫巧 —— 拿一段真实的长程会话喂进去，看 Agent 压缩前后能不能丝滑顺畅地接着干活。能，你的工程基线就彻底稳了！
STEP 06

踩过这五个工程暗坑，你才算真正入行

基线跑通之后，这些棘手问题会排着队找上门
暗坑 1 · 工具调用被拦腰切断（有借无还） 如果你挑选的切点恰好落在了“模型发出工具调用指令（tool_calls）”和“工具返回执行结果（tool_result）”的正中间，发给 API 的消息列表就会出现有借条却没有对账单的悬空调用。
主流模型厂商的网关会当场翻脸，直接抛出 400 校验异常拒绝服务！

避坑解法：切分之前必须往前“回溯”，确保切点一定落在完整交互回合的边界上。在 Google ADK 等成熟框架里，这被称为“未闭合的义务（Unfulfilled Obligations）”—— 凡是等待工具返回、等待用户确认或者等待鉴权的节点，统统算作不可切断的整体。
暗坑 2 · 复印件的复印件（传话游戏式信息失真） 长任务往往会运行几十甚至上百轮，压缩会被触发很多次。如果你每次都是简单地“把上一份摘要再拿去重新总结一遍”，就会发生像复印件反复复印一样的严重信息衰退 —— 传到第十次，最初用户提的核心约束早就被磨灭得面目全非。

避坑解法：把任务从“从头重新写总结”，转变成“以旧摘要为基准做增量修改”。在 Prompt 里清楚写明：PRESERVE（旧摘要里的核心事实原样保留） / ADD（填入最新阶段的新进展） / REMOVE（擦掉已失效的临时假设）。利用大模型的特长：LLM 做“对照修改与增删”的准确度，远高于让它“凭空重新发挥”。
暗坑 3 · 捡了芝麻丢了西瓜：Prompt Cache 被硬生生打穿 我们在 Step 02 里埋下的伏笔，在这里变成了真金白银的代价。Prompt Cache 认的是前缀一字不差的精准对齐。压缩必然要改写历史开头，这就注定了缓存会被打破重算：5 分钟 TTL 重新写入要收 1.25 倍基础价，1 小时 TTL 甚至要收 2 倍！

更要命的是，很多人为了做摘要，专门搞了一个独立的 Summarizer Prompt，把历史展平成纯文本发出去 —— 这样一来，摘要请求从第一个字起就跟刚才的对话完全不同，整段缓存直接作废，在历史最庞大、最昂贵的那个瞬间，你全价把几十万 Token 读了两遍！

神仙解法（值得抄进你的代码里）：把摘要指令不要放在请求的最开头，而是作为一条 User 消息追加在对话的最末端！ 这样前面的 System Prompt、工具列表和历史消息一字没变，摘要调用就成了上一轮对话的前缀延续，能以一折白菜价直接复用刚刚跑完的缓存！唯一的限制是摘要必须用同一款主模型跑（换模型就换了 Cache Key）。

但是！这里还有一个和 Step 05 物理粗剪相撞的连环套：如果在摘要前先剪裁了超长的工具输出，且把剪裁结果存回了持久化历史，那么发给摘要的请求就跟刚才没剪裁的对话请求在第一个剪裁字符处分家了，缓存照样会被当场打穿！

牢记这个核心判据：决定能不能蹭到缓存的，永远是发到网线上的 Token 序列和上次一不一样，跟你把数据存在内存还是硬盘毫无关系。 想两全其美，要么把剪裁推迟到摘要之后做，要么在对话发出去之前就把工具输出规范化。
暗坑 4 · 越压反而越庞大：请来了一位“话痨”摘要员 有时候原本的对话其实挺简短，或者调用的摘要模型废话极多，铺垫了一大堆客套话，结果“生成的摘要 + 保留的尾部”算下来，Token 数量居然比压缩前还要多！

避坑解法：在代码里加上两行朴素但救命的护栏 —— 组装完成后重新数一遍 Token，一旦发现没有变小甚至变大了，立刻原地回滚撤销，当什么都没发生过。同理加上防抖：连续两次压缩收益低于 10%，就老老实实进入冷却期，别在阈值边上来回拉扯。
暗坑 5 · 小书童装不下大账本：摘要模型自己爆仓了 主任务跑到了 180K，你想找个便宜的 64K 小模型帮它做压缩 —— 结果压缩请求自己直接因超出 64K 窗口而报错崩溃了！

避坑解法有三个灵活的调音旋钮：其一是把警报拉早（根据小模型的容量提前触发）；其二是剥洋葱机制（Goose 开源项目的经典做法）：遇到超限，按 [0, 10, 20, 50, 100]% 的阶梯逐步丢弃最不重要的历史工具输出，直到小模型能咽得下；其三是切片分块：按比例把历史切成两三份分别总结，最后再拼装融合。
STEP 07

三个关键十字路口：决定你的系统走向何方

在触发、削减与持久化中做取舍

地基打牢之后，接下来的架构选择没有绝对的对错之分，就像选跑车还是越野车，完全取决于你的具体场景。

抉择一：随手整理 vs 憋到极限大扫除？

策略倾向核心优势代价与隐患
随手轻度整理（用了 50%–70% 就动手）每次需要处理的历史很短，摘要质量极高，单次用时少压缩太频繁，反复打碎 Prompt Cache，多轮级联易导致记忆失真
憋到极限大扫除（用到 85%–95% 临界才动手）最大化压榨长上下文能力，压缩次数少，充分享受缓存红利每次要处理巨量文本，必须上复杂分块，容错缓冲极小，容易撞墙

这个选择会直接决定系统代码复杂度：早点收拾，单次调用配合头尾保护就能搞定；憋到最后才收拾，你就必须在系统里完整实现一套分块并发合并的重型引擎。开源界两种流派都有优秀实践，量力而行即可。

抉择二：能剪多狠？为什么敢丢助理的思考，却死保用户的每一句话？

在激进的压缩流派里（例如 Codex 原型和 kimi-code），压缩之后会把 Assistant 说的每一句推理和所有工具输出彻底清空，仅仅留下有限预算内的用户原话和一份最新总结。

底层的思考：可再生性的不对称 为什么激进方案敢把 Assistant 的发言当垃圾一样删掉，却要把用户的每一句话当宝贝供着？
开源项目 Hermes 在源码注释里给出了极其深刻的解释：
Assistant 的发言和工具调用，本质上是解题过程中的草稿纸，只要有了最终总结，草稿纸丢了随时可以重新推导；
但用户最初说的那几句话，是一切逻辑推演的原点与终极评判标准！ 一旦丢了用户的真实原意，再聪明的大脑也猜不出来主人最初要的到底是什么。

抉择三：压掉的旧档案，是丢进碎纸机还是放进地下室？

被移出活跃窗口的旧细节，以后还需不需要找回来？业界主要有三条路：

  • 扔进碎纸机（彻底覆盖） —— 直接在内存数组里用摘要替换旧消息。实现最简单，但丢失的信息永远回不来。
  • 加把锁留个底（界面可见，模型看不见） —— 消息打上“已归档”标签，前端人眼查看时还能翻阅全量历史，但发给模型的上下文里不再包含。
  • 建个图书索引室（可寻址检索） —— 原始细节落盘存储并建立索引；摘要里专门附带检索关键字和索引编号，模型需要精确线索时，自己随时调用查询工具去档案室捞回来！

第三条正是 Letta（MemGPT）的核心设计哲学：它把摘要当成了“外部记忆的导航目录”而不是“一次性替代品”。这与学界前沿的 ARC（Addressable Recall Compaction）理论完全一致，代表了长记忆系统的演进高地。

STEP 08

治标更要治本：真正的高手如何让信息“别挤进来”

最好的收纳，是根本不把杂物堆上桌面

上下文压缩是事后补救，而最高明的架构设计，是在信息进门之前就做好节流。

掌握了前面的方法，你已经能做出一套很棒的压缩管线。但工程里有一类问题，无论压缩做得多巧妙也解决不了 —— 因为它们在逻辑上就根本不该参与压缩！

别指望摘要模型帮你背负“规章制度”

还记得 Step 03 里提到的真实数据吗：压缩之后，规则违规率从 0% 飙升至 30%。这不是模型笨，而是信息论的客观规律：把规则混进一大堆流水账里做有损浓缩，它必然会有概率被漏掉。

聪明的系统解法 千万别把团队核心规范丢给摘要模型去转述。把“不可压缩区”做成系统级配置，让合规制度走一条完全独立的输入通道；或者在每次压缩重组完成后，由代码自动把规则前缀原模原样重新贴上去。
在调研的 11 个开源平台里，目前只有极少数做了重注入机制（一家重新挂任务待办，一家重新挂工程规范），这正是目前很多企业级 Agent 最值得补齐的关键短板。

三招从源头防膨胀的优雅架构

与其等桌子堆满再花力气大扫除，不如从源头减少堆到桌上的东西：

抽屉法则（状态外置）
中间分析成果随时写进本地 Markdown 或 JSON 文件，跨会话知识写入数据库。需要时再按需读回来，而不是整天背在脑子里。
外包小弟（子任务沙盒）
要跑几千行日志的模糊检索？派一个独立的 Sub-agent 去做！它跑完全部脏活，只给主 Agent 递上一张纸条：“第 42 行报错”，主桌面上干净清爽。
折叠菜单（渐进式披露）
三十个工具的庞大说明书，先只暴露工具名字加一句简短描述。模型真正挑中某个工具时，再把具体的参数说明书翻给它看。从根源上省掉上万 Token！

这三招凝聚成一句话：上下文压缩是系统底层的防御兜底，而优秀的架构设计才是让 Agent 轻装前行的解法。

STEP 09

怎么知道自己到底压得对不对？

别拿人类的语文眼光，去给 AI 的工作备忘录打分

很多团队做完压缩，第一反应是：“拿生成的摘要跟原文比比看，看文字通不通顺、语义像不像” —— 甚至去算 ROUGE 相似度。

在 Agent 工程里，这是彻底南辕北辙的评估口径。

摘要的读者不是人类，而是接棒推理的大模型。
唯一的衡量准绳只有一条：Agent 拿着这份压缩后的便签，到底还能不能准确无误地把下面的动作序列做对？ 这是业界一线工程实践收敛出的唯一共识

一份文采飞扬、总结得极漂亮的文字，如果随手漏掉了一个不起眼的文件路径或 Git Commit ID，Agent 下一步就会改错文件、提交错分支 —— 这份摘要在工程上就是零分。
反过来，一份读起来干瘪枯燥、全是一串串符号、路径和错误码的备忘录，人类读起来极其痛苦，但 Agent 拿起来立刻能无缝接着修 Bug，它就是无可挑剔的顶级好摘要。

三条极低成本的工程自查规则 1. 核心专有名词还在不在 —— 用最简单的正则，把原文里的 Commit Hash、文件路径、端口号、Issue 编号全提取出来，检查它们在摘要里有没有精准出现。纯代码跑，不花一分钱调模型，防翻车效果极强。

2. 老板最近的要求覆盖了没有 —— 把摘要和用户最后发的那一两句话做词汇重叠度检查，如果重叠过低，说明摘要模型走神了，漏掉了最新的紧急需求。

3. 到底有没有变小 —— Step 06 坑 4 的硬性门槛：压缩后总 Token 数没减少甚至变胖了，直接报警并回滚！

值得一提的是：调研的 11 个开源平台里，目前只有一家在运行时对摘要结果做了自动化的事实保真度校验与重试机制。这也意味着，在这个关键细节上稍微下点功夫，你的系统就能轻松拉开同行一个档次。

STEP 10

恭喜通关：接下来该往哪走？

前沿演进方向与知识库查阅指南

学完并实现前九步，你的 Agent 已经具备从容应对复杂长任务的硬核内功了。再往前看，业界有三个激动人心的探索方向：

  • 摘要即索引（Summary-as-Index） —— 不再幻想用短短几百字包揽一切细节，而是让摘要成为一张清晰的外部导航地图，真正的原文落盘持久化。把“有损替代”升维成“冷热分层的外部长记忆”。
  • 把繁重的收纳搬出主执行线程 —— 别让压缩拖慢用户的交互节奏。有的项目在后台做增量回收，甚至有平台把全量压缩做成了独立的后台 Worker 进程，与主逻辑并发运行，需要时随时可以优雅中止。
  • 让模型自己记账（自主状态持久化） —— 在触发系统压缩之前，主动提示 Agent：“请把当前的核心结论先写进本地文档”。自己整理的笔记，永远比别的模型事后瞎猜要准确十倍。
