把上下文压小
而不压坏

每一个能连续工作几小时的 AI agent，背后都有一套上下文压缩机制。它不是优化项，是让 agent 存在的前提。 这篇从「为什么必须压」讲到「怎么知道自己压对了」，每一步都有十一个开源平台的真实做法作参照。

STEP 01

先看一次死亡现场

问题长什么样

在理解任何机制之前，你得先亲眼看见它要解决的问题。

假设你写了个 coding agent，让它「修复这个仓库里的登录 bug」。它开始工作：

# 第 1 轮
用户: 修复登录 bug                                    ~20 token
agent: 我先看看项目结构                                ~30 token
工具: ls -R                     → 返回 800 个文件路径   ~9,000 token

# 第 2 轮
agent: 读一下 auth 模块
工具: read auth/session.ts      → 返回整个文件         ~14,000 token

# 第 3 轮
agent: 搜一下相关调用
工具: grep -rn "validateSession" → 返回 60 处匹配      ~7,000 token

# 第 4 轮 …… 第 12 轮
                                                     累计 ~180,000 token
# 第 13 轮
provider: 400 Bad Request — context_length_exceeded

十三轮，任务还没做完，agent 死了。注意看那些数字的比例：用户说的话是 20 token， 一次文件读取是 14,000 token —— 相差七百倍。

关键观察 Agent 的上下文不是被「对话」撑爆的，是被工具返回值撑爆的。这个事实决定了后面所有设计。 人类聊天记录增长是线性且缓慢的；agent 轨迹里每一次工具调用都可能塞进几万 token。

而且这不是「加大窗口就能解决」的问题。窗口从 8K 涨到 200K 再到 1M，agent 的胃口涨得更快 —— 因为窗口一大，你就敢让它读更大的文件、跑更宽的搜索、开更多子任务。 约束会被填满，这是工程里的常态。

STEP 02

上下文窗口是一堵什么样的墙

硬约束的三个性质

要设计对策，先得准确理解这个约束。它有三个反直觉的性质。

性质一：历史是一个前缀，不是一份日志

LLM 是无状态的。第 13 轮请求不是「接着第 12 轮说」，而是把前 12 轮的全部内容重新发一遍， 再加上新的一句。

这句话本身是常识。要紧的是它的三个后果——而其中只有一个跟钱有关：

  • 它必须每一轮都装得下，而不是「最后一次装得下」。这才是墙之所以是墙 —— 不是终点线，是每一步都要迈过去的门槛。
  • 它是一段稳定前缀。provider 的 prompt cache 正是按前缀命中，命中部分按约 0.1 倍计价 —— 所以「一直背着历史」这件事本身很便宜。
  • 也正因为是前缀，改它的代价不是局部的。前缀一变，后面全部作废。
第三条就是压缩的结构性代价 压缩必然要重写历史开头 —— 那正是缓存前缀所在的位置。压一次，缓存作废， 下一次请求得重新写入：5 分钟 TTL 收 1.25 倍全价，1 小时 TTL 收 2 倍。

你省下的是本来只花 0.1 倍的部分，付出的是一次全价重写。 这不是实现得好不好的问题，是「压缩」和「缓存」都建立在同一个前缀上导致的结构性冲突。

所以别把「省钱」当成压缩的理由 —— 它经常算不过来。 压缩的理由是第一条（每一轮都要装得下）和下面的性质二（装得下也未必用得好）。 这也是本篇后面所有取舍的出发点：你是在为「能不能跑下去」和「跑得好不好」付钱，不是在省钱。

性质二：装得下 ≠ 用得好

这是最容易被忽略的一条。学界有个著名发现叫 Lost in the Middle： 模型对上下文开头和结尾的信息利用得好，对中间的信息利用得差 —— 检索准确率呈 U 形曲线。

所以「还没到 200K，不用压」是错的。一段塞到 90% 的上下文，中间那 60% 可能模型根本没在看。 压缩不只是为了不撞墙，也是为了让留下的东西真的被用上。

性质三：墙的位置未必是文档写的那个

provider 声明的窗口大小不一定等于实际可用。十一个平台里有一家（kimi-code）干脆不信任声明值： 一旦请求撞上溢出错误，它就把本次请求大小的 85% 记为该模型的真实窗口，并永久下调自己的预算。 它靠撞墙来学墙在哪。

STEP 03

不压会怎么死，压了会怎么伤

两边的代价都要先看清

先别急着写压缩代码。先搞清楚你在两种痛苦之间做交换。

不压缩的三种死法

硬失败
provider 报 400。会话直接中断，且这一轮的钱已经花了。最干脆也最难看的一种。
软失败
缓存过期。缓存默认只活 5 分钟，而 agent 的一个回合常常更久 —— 工具调用、长思考。间隔一超 TTL，整段历史就是全价重来一次。
静默失败
质量下滑。没报错，但模型开始忘记早先的决定、重复已做过的工作。最危险，因为你看不见。

压缩的代价：三个实证数字

2026 年有几项工作第一次把压缩的代价量化了。这些数字应该在你动手前就知道：

6.5
其他一切不变，只换摘要器模型，
SWE-bench Verified 相差 6.5 分
0→30%
压缩后治理约束的违规率
（单模型最高 59%）
8.3×
软性组织策略的衰减速度
是硬性安全规范的 8.3 倍
第一个坑 很多人把摘要器当成「随便挑个便宜模型跑一下」的预处理步骤。上面第一个数字说明它不是 —— 摘要器的选择是一个和主模型选择同量级的性能变量。省摘要器的钱，可能比省下来的更贵。
第二个坑 第二、三个数字说的是同一件事：压缩会静默地删掉规则。而且越是「这个项目的特殊约定」这类 没有模型先验兜底的软约束，掉得越快 —— 因为摘要器不知道它重要。 安全规范模型自己还记得，你们团队「所有 API 必须走 v2 路由」这种，摘要一转述就没了。
STEP 04

建立坐标系：压缩的六个层

先有语言，才能比较

各家管这件事叫的名字都不一样 —— compaction、compression、condensation、pruning、eviction。 术语打架的时候，先建坐标系。任何一套压缩机制都可以拆成这六层：

L1Measurement 测量现在用了多少？靠 provider 上报、字符估算，还是真跑一遍 tokenizer
L2Trigger 触发 ⭐什么时候动手？百分比阈值、绝对余量、事件计数、固定节拍，还是撞墙后补救
L3Selection 选点压哪一段、留哪一段？切点划在哪里才不破坏结构
L4Reduction 减法 ⭐怎么变小？LLM 摘要、确定性裁剪、去重，还是直接丢弃
L5Reassembly 重组压完怎么拼回去？角色交替是否合法、工具调用配对是否完整
L6Persistence 持久化 ⭐被压掉的原文去哪了？删除、归档、标记不可见，还是可以再捞回来
读完十一家源码后的结论 各家在 L1 / L3 / L5 上高度趋同 —— 几乎是同一套工程解法，抄就完了。 真正拉开差距、也真正体现设计哲学的是标 ⭐ 的三层：什么时候压（L2）、用什么方式减（L4）、原文留不留（L6）。 你自己设计时，把精力花在这三层上。
STEP 05

动手：最小可用的一套

六步，每步给一个能直接抄的默认值

先把最简单的版本跑起来，再逐层加固。这六步走完，你就有一个能用的压缩器了。

测量：优先信 provider，回落到估算

每次请求后 provider 会返回 usage，那是最准的。拿不到就退到本地估算 —— 最粗糙但够用的是 字符数 / 4。别一开始就上真 tokenizer，它慢，而且触发判断不需要那么精确。

但有一件事必须做对：把 system prompt 和 tools schema 一起算进去。 很多人只数对话消息，结果一个塞了 30 个工具定义的 agent，光 schema 就吃掉 15K，估算全错。

触发：用「还剩多少」而不是「用了百分之几」

直觉会让你写 if (used > 0.8 * window)。但想一想：200K 窗口的 20% 是 40K，1M 窗口的 20% 是 200K —— 后者白白空着 200K 不用。

更好的口径是绝对余量：if (window - used < 20000)。 问题变成「还装不装得下下一次响应」，这个问题的答案跟窗口多大无关。

20,000 这个数字有交叉验证：OpenClaw 和 opencode 两个独立项目、不同语言、不同作者， 都收敛到了同一个常数。

但别把它当成裸常数抄 —— 它必须配一个小窗口保护： 
reserve = min(20000, window * 0.15)   // 小窗口时按比例退让
if (window - used < reserve) compact()
没有这个 cap 的话，一个 16K 窗口的本地模型会出事：20,000 的余量要求超过了整个窗口， 于是连空 prompt 都被判为「余量不足」，每一轮都触发压缩，压完还是不足 —— 无限压缩循环。 这不是假想，OpenClaw 的源码里就为此专门加了 cap 并写了注释说明。

先做免费的那一层：裁掉超长 tool 输出，然后重测

触发之后别急着叫摘要器。先把超长的 tool result 按「头 + 中间挖掉 + 尾」裁一遍 —— 这一步不调 LLM、不要钱、结果确定、可单测。tool 输出往往就是 token 大头：一次 grep、 一次测试日志，几万字符很常见，而其中真正有用的通常只在开头和结尾。

可以直接抄的默认值：超过 8192 字符就裁 → 留头 4096 + 尾 1024，中间换成一行 [... tool result middle pruned ...]。

关键是裁完要用同一个计量器重测一遍：如果压力已经回到阈值以下， 整个摘要调用就跳过了 —— 省下的是一次 LLM 调用、一次 cache 失效，以及一次不可逆的信息损失。 「读了几个大文件然后跑了个测试」这类回合，光这一步就有可能把压力压回阈值以下。

一个容易写错的细节：按 Unicode code point 切，不要按 UTF-16 code unit —— 否则落在代理对（surrogate pair）上的字符会被劈成半个，大量 emoji 和生僻汉字都在此列（常用汉字在 BMP 内，不受影响）。 注意这只挡住代理对：由多个 code point 组成的字素簇（比如 ZWJ 拼出来的 emoji）仍可能被切开。

选点：保护头尾，压中间

最简单有效的策略：system prompt 永远留、最近 N token 的原文永远留、中间那段拿去摘要。 这直接对应 Step 02 讲的 U 形曲线 —— 把模型用得最好的两端保住，压模型本来就用不好的中段。

注意是按 token 预算保护尾部，不是按消息条数。「保留最近 20 条」在消息大小跨三个数量级的场景里毫无意义 —— 可能是 2K，也可能是 200K。默认值可以抄 8,000–20,000 token。

减法：让摘要器填一张固定的表

不要写「summarize the conversation above」。十一家里没有一家这么干。 给它固定的 section，缺了能被程序检查出来：

## 目标 — 用户到底要什么
## 进度 — 分 已完成 / 进行中 / 受阻 三栏
## 关键决策 — 决定了什么，以及为什么
## 下一步 — 具体动作，不是方向
## 相关文件 — 路径 + 为什么相关

这五栏是十一家收敛出来的最小可用集。其中「进度分三栏」特别值钱 —— 它逼模型区分「做完了」和「以为做完了」。

重组：摘要进去，再给一句续接词

把摘要作为一条消息放回历史开头，后面接上保留的原文尾部。然后加一句续接指令， 告诉模型「上文已被压缩，接着干，不要提起压缩这件事」。

最后这半句不是客套。不加的话，模型下一句经常是「根据您提供的摘要……」—— 它会把压缩本身当成对话内容来回应。
现在可以试 这六步做完就能跑。先别加任何优化 —— 拿一个真实的长会话喂进去， 看压缩前后 agent 能不能接着干活。能，你就有基线了；不能，问题一定在第 5 步的摘要模板上。
STEP 06

五个必踩的坑

基线跑通之后，这些会依次找上门
坑 1 · 工具配对被切断 如果切点落在「模型说要调用工具」和「工具返回结果」之间，你会得到一条有 call 没有 result 的历史。 provider 直接返回 400。

修法：切之前往回找，确保切点落在一个完整回合的边界上。更严格的做法是把「未闭合的义务」概念推广 —— ADK 连「等待用户确认的工具调用」和「未完成的鉴权请求」都算作不能切开的义务。
坑 2 · 摘要的摘要的摘要 长会话会压很多次。如果每次都是「把上一份摘要重新摘要一遍」，就是有损压缩的级联 —— 复印件的复印件，压到第十次，最初的信息基本面目全非。

修法：把任务从「重新概括」改成「保留旧摘要 + 增补新事实」。 prompt 里写清楚 PRESERVE 已有内容 / ADD 新进展 / REMOVE 已过期的。 这利用了一个能力不对称：LLM 做「复制并编辑」比做「重新创作」保真得多。
坑 3 · prompt cache 被打穿 这条在 Step 02 已经埋过伏笔，这里是它的工程形态。provider 的 prompt cache 按前缀命中， 而压缩必然重写历史开头 —— 那正是缓存前缀所在的位置。压一次，缓存就得重建： 5 分钟 TTL 收 1.25 倍全价，1 小时 TTL 收 2 倍。

修法：这是压缩与缓存的根本张力，消不掉，只能管理。 一种做法是只裁剪已经超过 cache TTL 的部分（反正也要过期了）；另一种是把压缩频率当成显式旋钮， 承认「每压一次要付一次 cache break」，然后决定多久付一次。

还有一笔账几乎所有人都漏了：压缩本身要多发一次请求去做摘要，而那次请求处理的 正好是整个会话最长的那一刻的历史。常规写法是「专门的 summarizer system prompt + 压平成一段文本的历史」—— 第一个 token 就与刚跑完的对话请求不同，于是整段缓存前缀作废，最大的那段历史被全价读两遍。 有一家的修法值得抄，而且几乎不要钱：把摘要指令从请求最前面挪到对话最后面（变成最后一条 user 消息）， system prompt、tools schema、历史消息全部原样复用 —— 这样摘要调用就成了对话请求的前缀延长，缓存照常命中。 代价是摘要必须用主模型：换模型就换 cache key，红利立刻归零。所以这条与「用便宜的小模型做摘要」是互斥的， 得自己称一下哪边更重。
坑 4 · 压完反而更大了 摘要器话痨，或者历史本来就短，都可能让「摘要 + 保留段」比原文还长。

修法：压完数一遍 token，变多就整体回滚，什么都不做。几行代码的护栏。 同类的还有防抖：连续两次压缩的收益低于 10% 就停手，别在阈值边缘反复触发。
坑 5 · 摘要器装不下要摘要的东西 你要压的是 180K 的历史，但摘要器窗口只有 64K —— 压缩请求自己溢出了。

修法有三个方向，动的杠杆各不相同：改触发（降低本次会话阈值去适配摘要器窗口）、 改输入（逐级剥掉工具返回值再重试，Goose 的梯子是 [0, 10, 20, 50, 100]%）、 改比例（整体按 [0.7, 0.5, 0.35] 缩小请求重试）。三者正交，可以叠加。
STEP 07

三个设计选择，决定你的系统长什么样

L2 / L4 / L6，也就是标 ⭐ 的那三层

到这里基线已经稳了。接下来的选择没有标准答案，但每个选择都有明确的后果。

选择一：早压还是晚压

取向好处代价
早压（用到 50–75% 就动手）每次处理的历史少，摘要质量高，单次成本低压缩次数多，cache 反复失效，信息经多轮摘要累积失真
晚压（用到 85–100% 才动手）最大化利用窗口，压缩次数少每次要处理巨量历史，必须做分块 map-reduce，且离撞墙很近

这个选择会往下传导：压得早，才敢用单次调用加头尾保留这种简单做法；压得晚，就必须先解决「摘要器装不下」的问题。 十一家里两种都有产品在跑，没有对错。

选择二：减法减到什么程度

光谱的一端是「只压中段，头尾原文全留」；另一端是 Codex 和 kimi-code 的做法 —— 压缩后 assistant 和工具消息一条不留，只保留 20K token 预算内的用户原话加一份摘要。

背后的信息论 为什么敢丢 assistant 消息却死保用户消息？因为两者的可再生性不对称。 Hermes 的源码注释说得最清楚：assistant 输出的大多是「我做了什么」的记账，摘要能存活； 用户的话是一切的推导起点，丢了就永远回不来。同理，工具返回值可以重新跑一遍拿到， 用户的原始意图不能。

选择三：原文删不删

这是最容易被草率决定、后果又最大的一层。十一家给出了七类答案，但真正的分野只有一条： 被压掉的内容，还能不能捞回来？

  • 不能 —— 直接替换内存里的历史数组。最简单，也最不可逆。
  • 能看不能搜 —— 打个「已压缩」标记或可见性标志，UI 里还看得到全量，但模型和检索都够不着。
  • 能搜回来 —— 原文落盘并建索引，摘要里专门写上检索关键词，模型需要时自己捞。

第三种是 Letta 的做法，也是整批项目里唯一把摘要当成「索引」而不是「替代品」的架构。 它的价值现在有独立研究背书 —— 学界的 Addressable Recall Compaction 基本是同一思路的形式化版本。

STEP 08

压缩解决不了什么

边界比技巧更重要

最好的压缩，是不需要压缩。

到这里你已经能把压缩做得不错了。但有一类问题，无论压缩做得多好都解决不了 —— 因为它们根本不该经过摘要器。

治理约束：会掉，而且掉得最快

回到 Step 03 那两个数字：违规率 0% → 30%，软策略衰减是硬规范的 8.3 倍。 这不是摘要器不够好的问题 —— 你把一条规则丢进有损压缩管道，它就是会以某个概率消失。

正确的解法 别指望摘要器转述你的约束。把「不可压缩区」做成显式配置，让治理规则走一条完全独立的通道， 或者在每次压缩后重新注入。十一家里只有两家做了压缩后重注入 —— 一家注入项目约定，一家重新挂载任务列表，而没有一家重注入的是治理约束本身。 这是目前整个领域最明显的空白。

更彻底的思路：让信息别进来

压缩是在信息进入上下文之后做减法。还有一整类手段是在它进来之前就做取舍：

状态外置
工作产物写文件、跨会话知识入库。需要时再读回来，而不是一直背着。
上下文分区
把会产生大量工具输出的子任务整个丢给 subagent，它不继承父会话历史，输出只回传结论。
渐进披露
技能/工具先只暴露 名字 + 一句描述，匹配上了才加载全文。从源头避免「加载了又被压掉」。

这三条合起来指向同一个判断：压缩是补救，架构才是解法。 一个把状态外置做好的 agent，压缩触发得更晚、压掉的东西更不重要、出问题的概率更低。

STEP 09

怎么知道自己压对了

评测口径，比评测本身更容易搞错

最自然的想法是：拿摘要和原文比一比，看内容保留了多少 —— 用 ROUGE，或者让另一个模型打个相似度分。

这是错的口径。

摘要的读者不是人，是模型。判据不该是「读起来像不像」，而是「agent 拿着这份摘要， 还能不能复现出正确的动作序列」。 这是 2026 年评测工作收敛出的共识

一份文字优美、覆盖全面的摘要，如果丢掉了一个文件路径，agent 下一步就会去改错文件 —— 这份摘要的分数应该是零。 反过来，一份读起来干巴巴、全是标识符和路径的摘要，只要 agent 能接着干活，它就是好摘要。

可以直接用的三条自查 1. 标识符还在吗 —— 用正则从原文提取 commit hash、文件路径、issue 编号、错误码， 检查它们是否在摘要里原样出现。这是性价比最高的一条，纯代码，不用调模型。

2. 最近的诉求覆盖了吗 —— 摘要与用户最后几条消息做词汇重叠检查，太低说明摘要跑题了。

3. 压完变大了吗 —— Step 06 坑 4 那条护栏，同时也是最简单的质量信号。

值得一提的是：十一家里只有一家对摘要产物做在线的内容保真度校验并在失败时重试（另有一家会校验「摘要必须比它替换的内容更小」，但那查的是收缩，不是保真）。 这既说明这件事不容易，也说明它是一个还没被卷的位置。

STEP 10

走完之后往哪走

前沿方向与知识库入口

把前九步做完，你的 agent 已经能稳定跑长任务了。再往前有三个方向：

  • 摘要即索引 —— 不追求「摘要包含一切」，而是让摘要成为一张可寻址的目录，原文落盘可检索。压缩从「有损替换」变成「分层存储」。
  • 把压缩挪出关键路径 —— 十一家里已经有三条路径这么做了：两条增量回收在后台跑，还有一家的全量压缩本身就是后台 worker，与回合并发且可中止。学界也有并行化压缩的工作。
  • 让模型自己管 —— 压缩前先让 agent 把要紧的写进文件，比让摘要器去猜什么重要更可靠。这条几乎零成本，但做的人不多。
接下来读什么 这篇是学习路径，给的是取舍和顺序。具体到某一家怎么实现、常量是多少、源码在哪一行， 去看配套的知识库：开源 Agent 平台的 Context Compression 机制研究 —— 横向核对十五个平台与生态；其中开源项逐文件读源码，附版本快照与一致性说明。

建议读法：先按本篇的六层模型建立坐标系，再拿知识库当参考手册查， 而不是从头读到尾。那篇三千多行，是拿来查的，不是拿来通读的。

本篇的所有机制、常量与实证数字均来自配套知识库，后者横向核对十五个平台与生态， 其中开源项逐文件阅读源码并标注版本快照；文档与源码冲突处以源码为准。
