Chapter 01
先看论文到底改写了哪个问题

不是更聪明地压历史，
而是不再依赖历史

传统 Agent 把“当前状态”散落在整段对话里；SKILL.state 把它提炼成一个由运行时拥有、由程序校验的结构化对象。

Before · implicit state
对话历史就是状态
O₁ → R₁ → a₁重读
O₂ → R₂ → a₂重读
O₃ → R₃ → a₃重读
… 旧事实与失败假设 …重读
Ot → ?现在
每一步重新解释整段过去
After · explicit state
状态是一个明确的 API
P
程序规范不变：目标、规则、动作空间
Σ
当前执行状态可变：只保留未来决策需要的事实
O
最新观察只给这一轮，不回放旧观察
At = (P, Σt, Ot)
论文事实 单步内仍然允许完整的多步推理。被丢弃的是跨步携带的推理痕迹，不是模型在这一轮里思考的能力。模型输出 (Rₜ, ΔΣₜ, aₜ)；运行时校验并合并 ΔΣₜ 后，只让更新后的 Σₜ₊₁ 进入下一轮。
Chapter 02
拖动步数，直观看见二次增长

为什么会从 O(T²)
掉到 O(T)

如果第 t 步要重读前面 t 步的历史，把所有请求加起来就是三角形面积；若每一步只读固定大小的状态，总量就是一条直线。

在 T = 100 时，相比 Stateful 基线，SKILL.state 的累计 token 少 16.2 倍，同时准确率从 0.91 升到 0.94。
关键条件 固定 schema 不等于固定 state 大小。论文的 O(1) 单步结论要求 |P|、|Σ|、|O| 都不随 T 增长。 如果 tested_hypotheses 这样的列表无限追加，状态本身仍会重新长成一段历史。这是公式成立的工程前提，不是自动获得的性质。

Chapter 04
把论文放回你的六层坐标系

SKILL.state 不是第十二种压缩器

你的 compression research 把系统拆成测量、触发、选点、减法、重组、持久化六层。SKILL.state 的特别之处是：它把“偶尔压一次”改成“每轮投影一次”。

六层映射
紫色代表替换了传统机制；绿色代表绕过；橙色代表风险仍然存在
研究对照
L1
Measurement 测量
不再等窗口接近上限；每轮输入由 schema 直接决定。
基本绕过
L2
Trigger 触发
没有 75% / 20K reserve / overflow 触发；每一个 step 都做状态投影。
改成逐轮
L3
Selection 选点
选择规则极硬：只留 P、Σₜ、Oₜ；过去的 R、a、O 不进入下一轮。
固定白名单
L4
Reduction 减法
不是摘要旧文本，而是让模型生成结构化 ΔΣ，再由运行时合并。
状态投影
L5
Reassembly 重组
下一轮永远重组为同一个三段式 prompt；tool pair 与角色交替问题消失。
结构更简单
L6

Σ 成为跨步执行记忆；但审计、回捞和来源证明不能只靠 Σ。

为什么不是魔法

新观察能否准确纠正状态
旧历史仍写着“item 在 A”，会和新告警打架；SKILL.state 只更新当前 Σ，下一轮看不到旧事实。但如果告警没有被识别为相关事实并写入 Σ，它同样会失败。
论文边界在 Canceled Order 场景里，所有 runtime 都失败。显式状态可以消除旧文本的干扰，却不能弥补环境没有提供、schema 没表达或模型没识别的信息。
Chapter 06
什么时候不该用纯 SKILL.state

“状态是充分统计量”
什么时候会破

论文自己给了三个明确反例。它们不是小瑕疵，而是决定这套架构是否适用的入口条件。

Schema unknown
你事先不知道该记什么
开放式研究、探索性 debug、科学发现里，关键变量本身要在执行中才被发现。固定 schema 可能过早锁死问题空间。
Deferred relevance
当时看着没用，后来才关键
某条旧观察第一次出现时没被写入 Σ，后面再发现它重要也已经捞不回来。纯状态投影没有“回看原文”的机会。
History is output
过去本身就是交付物
审计、溯源、解释“为什么这样做”、复盘失败轨迹时，历史不是开销，而是你要保留和检索的证据。

新的瓶颈：模型能不能稳定维护结构化状态

68%过早覆盖 / 删除既有 key
20%schema 理解 / 类型转换错误
12%JSON 语法与格式错误
论文事实 Gemma-4-31B 在 T = 100 的 score 为 0.42。作者把失败主要归因于结构化输出遵从，并建议未来接 grammar-constrained decoding。 但 68% 的“错误删除状态”并不只是语法问题：即使 JSON 完全合法，语义上也可能把正确状态覆盖掉。
Chapter 07
结合既有研究后的工程结论

我会采用它的“模型视图”，
不会采用它的“唯一记忆”

对程序化、长程、可建模的任务，SKILL.state 是比滚动摘要更干净的执行语义；对生产系统，最好再补上你已有研究强调的可逆性与证据链。

Layer A · canonical
只追加的事件日志
保存观察、动作、工具结果、状态版本与验证结果。不给模型常驻读取，但支持审计、回放和定向 recall。
→
Layer B · projector
确定性状态投影器
校验 ΔΣ、执行 null-delete merge、维护版本号与不变量；必要时从事件重建状态。
→
Layer C · model-visible
有界 P + Σ + O
模型每轮只看当前执行所需的最小视图；缺信息时拿 evidence ref 定向回捞，不把全历史重新塞回来。
适合直接用 SKILL.state
  • 动作空间稳定、状态字段能预先枚举
  • 环境每一步都会给出可靠的新观察
  • 目标是完成任务，而不是解释完整历史
  • 运行时能严格校验 patch 与业务不变量
应该加 history / recall 层
  • 研究与 debug 中，事实价值会延迟显现
  • 需要审计、回滚、来源证明与复盘
  • schema 会在任务执行中演化
  • 多 Agent 会并发写同一个状态
最终定位 SKILL.state 不是 compression research 的反例，而是它最上游的一步：先把“当前执行事实”从对话里独立出来，再决定剩余历史要不要压、怎么存、何时回捞。 它解决的是 working context；canonical trace、provenance 和 evolving intent 仍需要独立机制。
