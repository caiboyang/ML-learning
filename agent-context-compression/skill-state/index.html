01

从“讲一遍经历”到“更新一张表”

把 agent 想成仓库管理员。发货时，它需要知道货物现在在哪，而不一定需要重读货物每一次搬家的对话。

完整历史

翻工作日记

① A 到了 → 放 12 号架② 12 号维修 → 搬到 42 号③ 又聊了很多其他事情…④ 顾客要 A → 重新找位置

旧状态和新状态同时出现，每轮都要重新辨别。

摘要 + 最近几轮

读一份交接笔记

摘要：A 已完成入库和转移最近：42 号架仍可用最新：顾客要 A→ 摘要有没有留下精确位置？

可以压得很好；关键取决于摘要有没有保住将来需要的信息。

SKILL.state

直接读当前账本

规则 P：从所在货架发货状态 Σ：A → shelf_42观察 O：顾客要 A→ 发货，然后删掉库存项

把“现在在哪”显式记下来，不再从旧叙事里推出来。

区别不在于 JSON 长得像不像摘要。 区别在执行合同：状态由 runtime 管理，每轮输出增量补丁；后续输入完全依赖规则、状态和最新观察。结构化摘要也可以逐渐接近这种设计，二者不是天然互斥的类别。论文 §3 ↗
P · Procedure

不变的操作说明、可用动作、环境规则。不是学出来的新技能。

+
Σ · State

运行中不断变化的“账本”。读作 sigma：它只是状态变量的名字。

+
O · Observation

环境刚刚告诉你的事。旧观察里有用的部分应已进入状态。

→
LLM · 决策

这一轮照常推理，产出状态变化与下一步动作。

⊕ 是什么意思？
这里是 runtime 的“合并”操作：新值更新指定键；null 表示删除；没提到的键应保留。模型提出补丁，程序决定是否接纳。
本轮推理用于产出更新，随后被丢弃，不进入后续 prompt。状态里的“失败过哪些假设”可以保留，和保留整段推理不是一回事。
校验通过 ≠ 事实正确
{"shelf_42": null} 可以格式合法却删错货物。类型检查挡住坏 JSON；业务不变量和环境反馈才能发现部分语义错误。
论文 Algorithm 1 先应用状态补丁再执行动作。工具失败时的事务回滚、部分成功与重试幂等性没有在该算法中完整给出；不能据此声称生产一致性已经解决。





 
03
为什么 O(T²) 会变成 O(T)？
关键是“每一轮都重发”。如果第 1 轮的信息在后面反复发送，同一段历史就会被累计计算很多次。

 
100 步理论示意 / 非论文测量
到第 T 步，共发出了多少输入？
纵轴：累计输入 token（万）

固定状态
示意输入量之比
假设：固定规则 1,000 token；每轮新增历史 200 token；固定状态 800 token；新观察 200 token。不含输出、缓存折扣、工具调用或延迟，不能当作实际账单。

 
每轮输入越来越长
Σ (1,000 + 200t)
 = 1,000T + 100T(T+1)
随着 T 增大，T² 那一项占主导。这是全历史重复输入的累计复杂度。
每轮输入长度固定
Σ (1,000 + 800 + 200)
 = 2,000T
每轮都只有规则、状态和最新观察，总量随步数线性增加。

 
“O(1)”有前提：状态和观察的大小不能随着任务无限增长。 固定 5 个字段，不等于固定大小：tested_hypotheses 可以越写越长。若必须保存的实体数量 N 随 T 增长，输入仍可能增长。论文 §3.3 的推导应理解为在 |P|、|Σ|、|O| 有界时成立；固定窗口或固定预算摘要的累计输入也可以是 O(T)。推导 ↗

机制对照：旧研究中的实现快照 × 本文阅读解释；不是跨平台跑分
你原来观察到的设计与 SKILL.state 的联系关键区别 / 还缺什么

 
Goose：JSON 摘要 + 双可见性都用结构帮助模型读当前任务信息JSON 输出本身不等于执行状态；还要看逐步 patch、runtime 校验和是否继续携带旧对话

 
OpenHands / ADK / DeepSeek Harness：事件日志与模型视图分离“模型只看当前状态”可以作为新的视图策略保存日志、UI 能看、模型能检索是三层能力，不能相互推导

 
Hermes / Letta：压缩后保留检索入口为状态漏掉的早期细节提供回捞方向本文基本循环没有给出等价的通用历史 recall；加上它属于混合方案

 
OpenClaw：摘要质量审计与约定重注入重要不变量应由独立机制保护检查 section / JSON 形式不等于验证每条状态更新符合事实

 
DeepSeek Harness：压缩调用复用缓存前缀提醒我们“少输入”与“实际更便宜”还隔着计费与缓存本文没有给出充分的缓存命中、延迟或货币成本实验

 
LangGraph core / LangChain middleware：原语与策略分层可以把 SKILL.state 理解为一种可实现的运行策略论文 Stateful 只是“状态块 + 历史”的特定对照，不是对整个框架的结论

CompactionRL 的问题
“怎样学会写对未来动作有用的摘要？”
与本文的连接：都应该用后续任务表现评价记忆，而不是只看可读性。不是本文已胜过它。
ConstraintRot 的问题
“压缩时，项目特有约束有没有消失？”
与本文的连接：把不变规则放进 P 是一种保护方向；执行中新增的约束仍需要可靠写入和持续保留。
Slipstream 的问题
“换成压缩后的信息，还能做对后续动作吗？”
与本文的连接：同样应检查状态是否支持正确决策。任务、模型与评测口径不同，不拼成一张跨论文排行榜。





 
06
最重要的前提：状态真的“够用”吗？
论文把 Σ 当成未来执行的 sufficient statistic（充分统计量）。通俗地说：只看现在这份状态，也不会缺少做下一步决定所需的过去信息。

 
用两段不同历史，测试一份状态
历史 A：货物入库，放到 42 号架历史 B：货物先到 12 号，再搬到 42 号
→
{ "item_12": "shelf_42" }
发货只需要当前位置：这份状态可能够用。
现在改一个问题：“这件货是谁搬过去的？” 两段历史投影成了同一份状态，答案却不同。被扔掉的历史突然成了任务本身。失效点是信息没留下，而不只是模型不够聪明。

 
边界 1 / schema 未知
不知道将来要记什么
开放式科研、探索陌生代码库，重要字段可能边做边发现。提前固定 schema 容易装不下新关系。
边界 2 / 后见之明
当时无关，后来关键
早期日志里的一个异常字符串，十轮后才发现是根因。没写入状态，又没有回捞入口，就找不回。
边界 3 / 历史就是目标
要解释“为什么这么做”
审计、归因、复盘依赖过程证据。最终状态无法替代动作、观察与来源的记录。

 
这三条是论文 §7 自己列出的限制。多 agent 并发写入也未在本文单 agent 实验中验证；共享状态需要版本与冲突处理。Limitations ↗

这是本页拟定的 schema。证据索引不替代证据内容；数组也需要明确的容量、归档与检索策略。
先做一个小而有判别力的实验
① 固定模型、工具、任务、输出预算② 比较：摘要+尾部 / 纯状态 / 状态+回捞③ 埋入：晚相关信息、用户新约束、工具失败④ 测：成功率、约束保留、证据可追溯⑤ 同时报：状态大小、输入/输出、缓存、重试、延迟
用可以重放的轨迹定位第一次丢信息的位置。不要只比较最后摘要读起来是否“清晰”。并发分支与自动 schema 演化可以等单 agent 基线跑通后再考虑。

 
值得保留的判断：状态空间明确、动作规则稳定的流程，适合试纯状态循环。开放式 research 更需要给“现在还不知道重要”的信息留一个可寻址的后路。

用一道题，检查有没有真正理解
你把 agent 改成固定 5 个 JSON 字段，其中 all_findings 每轮追加一千字。能宣布它的每轮输入是 O(1) 吗？

 
先做判断，再展开解释。
再想两题（含答案）
Q：程序拒绝坏 JSON，就能保证库存始终正确吗？
A：不能。合法补丁也可能删错键；还需要业务检查和环境反馈。
Q：这篇论文证明应该在磁盘上删除所有历史吗？
A：没有。它的核心比较发生在每轮输入与状态维护；论文明确丢弃中间推理，也明确承认审计与轨迹任务不适用。原始工具观察的审计日志是另一个工程层面的选择。
