把历史扔掉
只留一份可改写的状态

SKILL.state 提出一个反直觉的运行时：agent 每一步只看到三样东西——技能说明书、一份结构化状态、最新一条观测。 之前的推理、动作、工具输出全部不进下一次 prompt。 这不是「把历史压小」，是不让历史存在。本文逐图拆解它的方法与全部实验数据， 并把它放回我此前十五平台压缩机制研究的坐标系里，看它到底证实了什么、又绕开了什么。

01

一分钟看懂：它到底改了什么

一张图就是全部论点

今天几乎所有 agent 运行时都是「往下接」的：每一步把新的推理、动作、观测追加到一条越来越长的记录后面，然后整条重新发给模型。SKILL.state 说：别接了。

三句话版本

  • 做法：每一步的 prompt 只由三部分构成 —— 不变的技能说明书 P、结构化执行状态 Σ_t、最新观测 O_t。模型输出推理 R_t、状态补丁 ΔΣ_t、动作 a_t；状态更新完，推理立刻被永久丢弃。
  • 结果：单步 prompt 恒定，累计 token 从 O(T²) 降到 O(T)。T=100 时 65,408 token vs LangGraph 式基线 1,062,387 —— 16.2 倍；同时准确率 0.94 vs 0.91。
  • 代价：你必须提前为这个领域写好 schema。论文自己的 Limitations 第一条就说：schema 事先不知道、必须边跑边发现时，这套方法不成立。

02

问题：历史为什么必然膨胀

O(T²) 是怎么来的

LLM 是无状态的。第 t 步不是「接着第 t-1 步说」，而是把前面所有内容重新发一遍。所以单步 prompt 长度 |C_t| = O(t)，把 T 步加起来：

我的第一条补充 · 论文的渐进复杂度框架被夸大了 论文把对手统一写成 O(T²)，把自己写成 O(T)，读起来像是一个数量级的改进。 但 O(T²) 只对完全不压缩的 ReAct 成立。任何做了压缩的运行时，单步 prompt 都被窗口 W 卡住，累计是 O(T·W) —— 同样是线性的。

所以 SKILL.state 与真实生产系统的差距不是渐进阶数的差距，是常数的差距：W 从 ~30,000 token 降到 ~500。 这个常数很大（论文实测 16–40 倍），值得做；但把它讲成「二次降一次」，比较的是一个没人在生产里跑的对手。

除了钱，还有两件更要紧的事

论文真正有说服力的部分不在 token 账上。历史膨胀会带来两个只有长程任务才暴露的失效，而它们都不是「加大窗口」能解决的：

失效一 · 注意力被噪声拖走
环境每一步都会吐出无关遥测（电量、CPU、syslog）。它们一旦进了历史就永久留在那里，并在后面每一步继续消耗注意力。论文实测：注入 50 条/轮噪声，ReAct 从 0.68 掉到 0.53；软件仓库环境更狠，0.76 → 0.11。
失效二 · 过期事实压倒新观测
外部世界在 agent 的动作循环之外被改动（别人 force push 了、货被人搬走了）。历史里写着「货在 shelf_42」的那句话不会消失，于是模型要花 5–14 步才肯相信新的观测。论文管这叫 hallucination lag。
这两条都指向同一个机制 历史是只增不减的，所以任何一次错误、噪声、或已经过期的事实，代价都不是一次性的，而是要在剩下每一步里反复付。 这正是我此前研究里 Lost in the Middle 那节的动力学版本：不只是「中间的东西读不到」，而是「中间的坏东西一直在读」。
03

方法：把推理投影成状态补丁

Algorithm 1 只有九行

整套方法的全部内容是：让模型每一步都回答「这次观测改变了世界的哪一格」，而不是「到目前为止都发生了什么」。

状态怎么改：字典合并 + null 即删除

更新规则只有一条：Σ_t⁺¹ = Σ_t ⊕ ΔΣ_t，其中 ⊕ 是带 null 删除语义的字典合并。把一个 key 设成 null 就等于把它从状态里抹掉。

schema 是按领域写一次，不是按任务写

最容易被误解的一点：这不是给每个任务手写状态结构。论文的说法是 schemas are authored once per domain，并给了最有说服力的一个例子 —— InterCode CTF 的 100 道互不相同的题，共用同一个五字段 schema：

discovered_flags
已拿到的 flag
tested_hypotheses
试过且失败的思路 —— 防止重复试同一条命令
active_files & working_dir
当前在看哪些文件、在哪个目录
cmd_summary
命令历史的压缩形态
这五个字段值得盯着看一会儿 它们不是「仓库有几个货架」那种玩具状态，而是一套通用的探索型任务状态：做过什么、当前在哪、已排除什么。 我此前研究里十一家的结构化摘要模板（Goal / Progress / Done / In‑Progress / Blocked / Next Step） 要表达的其实是同一批槽位 —— 区别只在于：模板产出的是自然语言段落，schema 产出的是可程序化校验的字典。

四种运行时的 prompt 长什么样

论文 Appendix A 给了四份模板。把它们并排放，差异一目了然：

运行时prompt 结构历史怎么处理
Prompt (ReAct)Instructions + History[全部观测与响应] + Latest Observation全部保留
Memory (Summary)Instructions + Summarized History + 最近 3 轮原文 + Latest Observation摘要 + 3 轮滚动窗口
Stateful (LangGraph)Instructions + Current State (JSON) + History[全部] + Latest Observation状态与全量历史并存
SKILL.stateInstructions + Σ_t (JSON) + Latest Observation没有历史这个字段

论文强调 skill.instructions 在四种运行时里逐字相同，以此把「上下文管理方式」隔离成唯一自变量。这个控制做得是干净的。 但请记住第三行：它们的 Stateful 基线是「状态 + 全量历史」 —— 这一点后面第 10 节会变成主要的争议点。

数据一：长程扩展

先看最核心的那张图。横轴是任务步数，纵轴是整场任务烧掉的 token 总量 —— 注意纵轴是对数刻度，否则黄线会贴在地板上看不见。

把两张图合起来读 T=100 那一列：Stateful 基线花 1,062,387 token 换到 0.91，SKILL.state 花 65,408 token 换到 0.94。 16.2 倍的成本差，外加 3 个点的准确率。这不是一个需要权衡的取舍，在这个 benchmark 上它是单方面更好。

换到关系型环境：优势变小，而且出现了唯一一次落败

Warehouse 是 500 个互不相干的格子，天然就是一个字典。论文的第二个环境（Software Repository：Git 分支、PR、CI 状态构成的纠缠图）才是更像真实任务的那个。

我的读法 这个交叉点很有信息量。它说明 SKILL.state 的收益不是从第一步就存在的，而是在 T 大到一定程度后才追上并超过 —— 因为丢掉历史本身有信息代价，只有当历史长到开始伤害模型时，这个代价才转为收益。

换句话说：存在一个盈亏平衡的 T。Warehouse 上它小于 10（一开始就赢），Software Repository 上它落在 25 到 50 之间。 环境的关系纠缠度越高，这个平衡点越靠后。论文没有给出估算这个平衡点的方法，而这恰恰是工程上最需要的那个数。

数据三：噪声、状态漂移、公开 benchmark

Table 2 / 3 / 4 / 9 / 10

噪声鲁棒性：不是「抗住了」，是「根本没进来」

环境每一步往观测里塞 5/20/50 条无关遥测（机器人电量、HVAC 传感器、摄像头 OCR、syslog），全部随机生成、与任务无关、不改变真实世界状态。

机制上的差别值得说清 Memory 与 Stateful 也扛住了噪声，但它们是把噪声摘要掉或稀释掉；SKILL.state 是噪声从来没有机会进入下一次 prompt —— 它在生成 ΔΣ 的那一刻就被过滤了，因为 schema 里根本没有「电池电量」这个字段。

这是 schema 最被低估的作用：它是一个白名单。 摘要器面对的是「什么该删」的开放问题，schema 面对的是「什么该留」的封闭问题。 这正是我研究 §2.13「最好的压缩是不压缩」那条的机制版本。

状态漂移恢复：从 5–14 步到 0 步

实验设计得很干净：在 agent 的动作循环之外改变真实世界（别人把货搬走了、别人 force push 了、CI 变成 flaky），然后只通过一条普通观测告诉 agent。

别忽略最后那一行 两个环境各有一个场景是所有运行时都失败的：Warehouse 的「订单被取消」、Software Repo 的「PR 被关闭」。 这两种都属于「某个已经开始的义务被外部撤销」——不是状态值变了，是任务目标变了。SKILL.state 也救不了。 这与我研究里 ADK 那条「把未闭合的义务而不只是 tool pair 作为切点约束」指向同一个盲区。

公开 benchmark：从玩具环境走出来

前面全是论文自建的 SkillExecBench。这一组用的是别人的题：InterCode CTF（100 道 Linux 渗透题）与 Sierra τ-Bench（零售/航空客服，要查真实 SQLite 库、受业务政策约束）。

数据表 · 论文 Table 4
  • InterCode CTF 是最漂亮的一格：54.2% vs 次优 46.4%，同时 token 只有 ReAct 的 40%。论文给的解释是 tested_hypotheses 这个字段——把「试过且失败的思路」显式记下来，模型就不会重复试同一条命令。这是五个字段里最像通用能力的一个。
  • τ-Bench Airline 提升最大但绝对值最低：32.4% vs 28.1%。论文说这里基线的单步 prompt 会冲到 11,000 token 以上（数据库返回体很大），而 SKILL.state 稳在 ~2,800。
  • τ-Bench Retail 有一个反常点：SKILL.state 的单步 prompt 是四种里最大的（3,325 字符 vs ReAct 2,819），却仍然总 token 最低——因为它用更少的步数完成。这说明「prompt 更小」并不是它在真实任务上取胜的唯一机制。
  • Memory 基线在 τ-Retail 崩了：29.9%，比 ReAct 的 48.2% 低 18 个点。摘要在这里是净负作用。这一格与我研究 §21.1 引的 CompactionRL 那条「只换摘要器就有 6.5 分区间」互为佐证：摘要器不是中性的预处理，做坏了比不做还差。

为什么会这样：错误分类给了答案

论文 §5.7 对 Gemma 的失败日志做了归类，这是全文我认为最有工程价值的一段：

我认为这里藏着整篇论文最重要的一句话 68% 的错误是「更新状态时误删了本该保留的 key」（premature state overwrite / deletion）。 请把它和我研究 §21.2 引的 ConstraintRot 那条放在一起看：约束存活时违规率 0%，被丢弃时 38% —— 存不存活几乎就是全部。

压缩式系统里，摘要漏了一条约束，你还有未被压缩的 tail 兜底，失效是渐进的； SKILL.state 里，一个 key 被 null 掉就是真的没了，没有第二份拷贝，失效是二值的。

所以这套架构把「信息存活」从一个概率问题变成了一个程序问题——同时也变成了一个单点。 这是它最大的优点和最大的风险，而且是同一件事。
08

对照我的压缩研究：六层坐标系里它站在哪

这一节是本文的主体

我此前那篇研究把十五个平台的压缩机制统一到六层：测量、触发、选点、减法、重组、持久化。把 SKILL.state 放进这个坐标系，会发现一件比「它更省 token」有意思得多的事。

SKILL.state 不是在这六层里做得更好。它是把 L1/L2/L5 整层删掉，把 L3/L4 从运行时决策搬到设计时决策。 这一句是我读完全文最想留下的总结

再逐条对照：哪些平台其实已经在做「半个 SKILL.state」

这个方法并不是凭空出现的。我研究里有四家已经在做同一件事的局部版本，只是没把它当成架构主张：

平台已有的做法和 SKILL.state 的关系
kimi-code TODO 列表由系统从活数据源重新挂载，并在摘要 prompt 里明令禁止摘要器转抄 最接近的一个。这就是一个单字段的 Σ：任务状态不走摘要通道，由运行时直接注入当前值。SKILL.state 只是把这个做法从一个字段推广到整个状态
Goose 摘要产物是受 schema 约束的 JSON，再用可覆盖的 Jinja 模板渲染 状态的形态已经到位（结构化、可校验），但它仍然是「对历史做摘要」的产物，而不是「对世界的当前描述」。差的是那一步语义转换
Codex CLI WorldState 承载工具状态；压缩后丢弃全部 assistant/tool 消息，只留 canonical context + 用户原话 + 摘要 减法的激进程度已经很接近了。区别在于它保留的是「用户说过什么」（历史），SKILL.state 保留的是「世界现在什么样」（状态）
Google ADK 摘要 prompt 里两条独有指令：显式声明对话语言、列出用过的工具名 我当时的评语是「把隐式统计状态显式化」。SKILL.state 是这条原则的完全体：凡是需要跨步存活的东西，都必须有一个显式字段，不许靠上下文里的统计痕迹残留
所以这篇论文的贡献要怎么定位 它不是发明了「用结构化状态代替历史」——四家产品已经在做局部版本。 它的贡献是：把这件事推到极端（一份历史都不留）、给了一个干净的形式化（Σ⊕ΔΣ，Algorithm 1 九行）、并且第一次量化了它值多少。 对我这篇研究来说，它填的是「效果评测」那一节里最缺的一格：不压缩的那条路，到底比压缩好多少。
09

我的分析：论文没测的那一维

prompt cache · 全文出现 0 次

论文报的全部成本指标都是裸 token 计数。但没有人是按裸 token 付钱的 —— 所有主流 provider 都有 prompt cache，命中部分按约 0.1 倍计价。这一维一旦计入，倍率会明显收窄。

为什么这一维正好打在 ReAct 的强项上 ReAct 的历史是纯追加的 —— 第 t 步的 prompt 是第 t-1 步的严格前缀延长。 这正是 prompt cache 的理想形态：每一步都能命中前一步的全部内容，只有新增的那一小段按全价写入。

换句话说，论文那条「ReAct 烧了 1,245,413 token」的柱子，其中 90% 以上是按 0.1 倍计价的。
项ReAct（纯追加）SKILL.state
单步 prompt线性增长，T=100 时均值 9,090 token恒定 ~476 token
裸输入 token 合计909,00047,600
可缓存部分前一步的整个 prompt（严格前缀）只有 P（~350 token）；Σ 与 O 每步都变
折算算式0.1 × 890,300 + 1.25 × 18,700100 × (0.1×350 + 126) + 1.25×350
有效成本~112,400~16,500
倍率裸 token 19.1× → 计入缓存后 6.8×

结论没有被推翻，但被砍掉了三分之二。6.8 倍仍然是一个非常值得做的改进；19 倍则是一个不该用来做决策的数字。

推论一：压缩式系统在这一维上是最差的

这是我那篇研究 §2.11 的核心张力，在这里刚好闭环 压缩必然要重写历史的开头，而那正是缓存前缀所在的位置。前缀一变，后面全部作废，下一次请求要按 1.25×（5 分钟档）或 2×（1 小时档）全价重写。

于是三种运行时在缓存这一维上的排序是：

ReAct 最好（前缀永不改变，全程命中） → SKILL.state 次之（前缀恒定但很短，动态部分小） → 压缩式最差（前缀既大又会被周期性打掉）。

压缩是三者里唯一同时付两笔钱的：既要付摘要调用，又要付缓存重建。 这一条论文没有讨论，但它是我这篇研究里最想让人记住的一条，而 SKILL.state 恰好给它提供了一个逃逸出口 —— 因为它根本不重写前缀，它只是让前缀之后的东西一直很小。

推论二：τ-Bench Retail 那一格的 token 优势不稳

再看论文 Table 4 里最不起眼的一行。τ-Bench Retail 上，SKILL.state 的裸 token 优势只有 22%（4.48M → 3.47M），而它的单步 prompt 反而是四种里最大的（3,325 vs ReAct 2,819 字符）。

  • ReAct 的每一步都命中前缀缓存，有效成本远低于裸计数；
  • SKILL.state 每一步都改写 Σ，可缓存的只有 P，其余全价；
  • 而它的单步 prompt 又更大。

三条叠加，在这个 benchmark 上把 cache 计入后，ReAct 很可能反而更便宜。我没有足够信息把这个反转算到小数点（论文没给每任务步数，也没给 P 的实际大小），所以这里只给方向：22% 的裸 token 差距，扛不住任何一个合理的缓存折价模型。

口径声明 本节全部数字为建模推演，基于：4 字符 ≈ 1 token；缓存命中 0.1×、写入 1.25×；缓存全程不过期（这对 ReAct 最有利）。 真实情况下 5 分钟 TTL 常常在一次工具调用之间就过期——这是我研究 §3「不压缩的三种死法」里的软失败那一条——所以实际的 ReAct 缓存命中率会低于这里假设的理想值，真实倍率落在 6.8× 与 19× 之间。

我把它写出来不是为了给出精确数字，而是为了指出：论文用裸 token 作为唯一成本指标，系统性地高估了自己的优势，而这个高估在不同 benchmark 上的幅度并不一样。

它不成立的地方：五条我要反驳的

读完全文之后我真正的保留意见

前面九节我基本在替这篇论文说话，因为它的核心主张确实成立。这一节讲它不能推广到哪里——而这恰恰是我最关心的部分，因为我研究的那十五个平台，几乎全都落在它不成立的那一侧。

反驳一 · 最该有的那个基线不存在

论文的 Stateful 基线是 「结构化状态 + 全量历史」。而我研究的十五个平台，没有一家是这么跑的——它们跑的是「结构化摘要 + 20K token 的原文 tail」。

反驳二 · 预算对齐实验把对手掐到真实系统的 1/40

已在第 5 节展开：1,800 字符 ≈ 450 token，而 OpenClaw / opencode 的缓冲是 20,000 token，Codex CLI 光保留用户原话就给 20,000 token。「Summary-capped = 0.52」测的是 450 token 的摘要，不是生产级 compaction。这个实验证明了「统计式压缩器会毁掉标识符」（这条我完全同意），但没有证明「压缩式路线打不过状态式路线」。

反驳三 · Warehouse 与方法同构

Warehouse 的真实世界状态本身就是一个字典：500 个互不相干的格子，每格一个字符串或 null。而 SKILL.state 的状态表示也是一个字典。这不是「方法在这个任务上表现好」，这是方法与任务共用同一个数据结构。

论文自己其实给出了这个偏差的量：换到关系纠缠的 Software Repository 环境，优势从「一开始就赢」退化到「T≥50 才赢」，中间还出现一次落败。SkillExecBench 是论文自建的，而它的两个环境里，被反复用来做主图的那个恰好是对方法最友好的那个。

反驳四 · 正文的措辞覆盖了两处不利结果

未提及 · 之一
Gemma-4-31B 在 T=100 时 SKILL.state 与 Stateful 同为 0.42；Qwen-3-8B 是 0.34 vs 0.31。正文只写「across both proprietary and open-weight models」，没有一处说明准确率优势在长程 + 小模型上会消失。
未提及 · 之二
Software Repository T=25 处 SKILL.state 0.88 < Stateful 0.94，是全文唯一落败。这个数据在附录 Table 6 里，正文与附录文字都未提及。

两处都不是造假——数据都在表里。但它们都是读者需要主动去附录找才会发现的不利证据，而正文的概括性措辞恰好把它们盖住了。

反驳五 · 它自己的前提就排除了我研究的那批系统

论文 Limitations 第一条写得很清楚（这一点我要给它记一功——写得诚实）：

……失效于三种情形：(1) 事先不知道固定 schema、状态结构必须在执行中动态发现时；(2) 一次正确的状态更新依赖于某条更早的观测，而它的相关性在当时未被识别、因而从未被写入状态时；(3) 任务目标本身定义在历史轨迹之上时（审计、追溯 provenance、解释过去的动作）。 论文 §7 Limitations

把这三条翻译成工程语言：

  • 第 (1) 条 = coding agent。「修复这个仓库里的登录 bug」没有事先可写的 schema——你不知道会碰到哪些文件、哪些框架、哪种错误。而我研究的十五个平台里，OpenClaw、Hermes、Codex CLI、opencode、kimi-code、Cline、Goose、OpenHands 八家的主场就是这个。
  • 第 (2) 条是最狠的一条，它承认了状态式路线的根本脆弱性：投影是不可逆的。压缩式系统里，一条当时没看出重要性的信息还躺在未压缩的 tail 里，后面可能被用上；SKILL.state 里，它在第一步就被丢了。「事后才知道重要」这件事，是投影范式无解的。
  • 第 (3) 条对应我研究 §17.7「压缩不销毁数据」那条共识。十一家都保留原始数据（append-only session tree、soft archive、双可见性、事件溯源）。SKILL.state 的 Σ 不是日志，要留档得另建一套。
还有一件论文明明占优、却没测的事 延迟。全文没有任何 wall-clock 数字。但 prompt 从 36,362 字符降到 1,905 字符，TTFT 几乎必然大幅下降——而长程 agent 的体感成本主要就是延迟。 论文的 Introduction 第一段甚至把 latency degradation 写成了它要解决的问题之一，然后一个延迟数字都没给。这是它自己漏掉的一个优势。

不用等到有 schema 才能用上这篇论文

自测 · 来源 · 口径

读完了检查一下

八道自测题

SKILL.state 每一步给模型看的三样东西是什么？哪一样是可变的？
P（技能说明书，不变）、Σ_t（结构化执行状态，唯一可变的那个）、O_t（最新一条观测）。之前的推理、动作、观测一律不进 prompt。
模型每步产出三样东西，它们的去向分别是什么？
R_t 推理 → 验证通过后永久丢弃；ΔΣ_t 状态补丁 → 确定性校验后合并进 Σ；a_t 动作 → 交给环境执行。 关键在第一条：步内推理是完整的，但它不跨步存活。
论文说自己把 O(T²) 降到 O(T)。这个说法对压缩式系统成立吗？
不成立。O(T²) 只对完全不压缩的 ReAct 成立。任何做了压缩的运行时，单步 prompt 都被窗口 W 卡住，累计是 O(T·W)——同样是线性。 SKILL.state 与生产系统的差距是常数（W 从 ~30,000 token 降到 ~500），不是阶数。这个常数值 16–40 倍，很大，但不是「二次降一次」。
预算对齐实验里，LLMLingua 掉到 0.22 的原因是什么？它对应我压缩研究里的哪条共识？
统计熵过滤删掉了「看起来冗余、语义上却至关重要的槽位标识符」。 对应 §17.2「保留精确标识符是共同焦虑」——十一家都在摘要 prompt 里写死「逐字保留路径 / ID / 错误码」。 当时这条只有源码一致性作为证据，这篇论文提供了反证：不这么做会掉到 0.22。
为什么说这套架构把「信息存活」从概率问题变成了程序问题，同时也变成了单点？
压缩式系统里，摘要漏了一条约束，还有未被压缩的 tail 兜底，失效是渐进的； SKILL.state 里，一个 key 被 null 掉就是真的没了，没有第二份拷贝，失效是二值的。 实证：开源权重模型 68% 的错误正是「误删了本该保留的 key」。
把 prompt cache 计入后，Warehouse T=100 的倍率会变成多少？为什么会变？
裸 token 19.1× → 计入缓存约 6.8×（本页第 9 节的建模推演，非论文数据）。 因为 ReAct 的历史是纯追加的，第 t 步 prompt 是第 t-1 步的严格前缀延长，每一步都能命中缓存、按 0.1× 计价。 论文只报裸 token，系统性高估了自己的优势。而压缩式系统在这一维上是三者里最差的——它既付摘要调用，又周期性打掉缓存前缀。
论文自己承认的三种失效情形是什么？其中哪一条排除了 coding agent？
(1) 事先没有固定 schema、结构必须动态发现；(2) 正确的更新依赖某条当时未识别出相关性的更早观测；(3) 任务目标定义在历史轨迹本身之上（审计、provenance）。 第 (1) 条就是 coding agent——「修复这个仓库的登录 bug」没有事先可写的 schema。我研究的十五个平台里有八家主场在这里。 第 (2) 条最狠：它承认投影是不可逆的，「事后才知道重要」这件事投影范式无解。
如果今天要把这篇论文用进一个已有的压缩系统，第一步做什么？
把任务状态（TODO / 当前目录 / 打开的文件）从摘要通道里拿出来，改由运行时从活数据源每步重新挂载，并禁止摘要器转抄。 这不需要改架构，只是把一个字段换个来源；kimi-code 对 TODO 已经这么做了。 判据是一句话：凡是你能写出稳定字段名的东西，都不该经过摘要器。
