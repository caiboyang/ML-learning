SKILL.state 提出了一种颠覆常规的智能体运行时范式：Agent 每一步的输入上下文严格收敛于三要素——静态技能规范、结构化执行状态、最新单步环境观测。 历史推理轨迹、中间动作及工具调用回包全部不进入后续 Prompt。 这绝非传统意义上的“历史上下文压缩”，而是在架构层面彻底消除对话历史的物理存在。本文逐图拆解其算法机制与全部 11 组实验实测数据， 并将其置于工业界十五大平台上下文压缩机制研究的坐标系中，审视其究竟证实了何种假设，又在何处回避了真实的工程挑战。

01

核心脉络：它究竟改变了什么

架构范式的根本分歧：一张图解析核心论点

当前主流的 Agent 运行时普遍采用“只增不减（Append-only）”的追加模式：每完成一步，便将新的思维链、动作与工具观测追加至历史记录尾部，并在下一步全量重发给模型。SKILL.state 明确指出：这一范式在长程任务中不可持续，应当彻底切断历史追加通道。

核心结论提要

  • 核心范式：每一步输入上下文仅由三要素构成——静态技能规范 P、当前结构化执行状态 Σ_t 以及最新环境观测 O_t。模型在步内生成中间推理 R_t、状态更新补丁 ΔΣ_t 与物理动作 a_t；状态更新合入后，步内推理轨迹立刻被确定性丢弃，绝不向后传递。
  • 实测收益：单步 Prompt 长度保持恒定，累积 Token 消耗从 O(T²) 降至 O(T)。在 T=100 步的长程任务中，总消耗由 LangGraph 式基线的 1,062,387 Token 骤降至 65,408 Token（降低 16.2 倍），动作准确率逆势提升至 0.94（基线为 0.91）。
  • 工程代价与边界：系统高度依赖预先人工定义完备的领域 Schema。正如论文在局限性章节所坦承：若领域状态结构无法预先固化、必须在探索中动态发现，该架构的前提将不复存在。

问题根源：对话历史为何注定线性膨胀

累积开销的平方级膨胀推演：从 O(T) 单步到 O(T²) 总体成本

大语言模型本质是无状态的黑盒函数。在多轮交互中，第 t 步并非在上一轮思维隐状态上的自然延续，而是依赖宿主系统将过往全部轨迹拼接后全量重新输入。若单步上下文长度 |C_t| = O(t)，在执行 T 步后，总体处理量将发生积分效应：

深度批判一 · 论文关于渐进复杂度的叙事存在概念偷换 论文将现有竞争架构泛化定义为 O(T²)，并将自身标榜为 O(T)，在叙事上营造出跨越阶数的理论突破。 然而，O(T²) 仅仅成立于毫无上下文治理策略的原始 ReAct 实现。工业级生产系统中，任何具备上下文管理的平台均会引入窗口上限 W，其累积复杂度严格受控于 O(T·W) —— 本质上同样是线性增长。

因此，SKILL.state 相对真实生产系统的真正优势并非计算复杂度的阶数跃迁，而是常数项的断崖式削减：将单步窗口 W 从 ~30,000 Token 压缩至 ~500 Token 级别。 这一常数改善在经济账上带来了 16–40 倍的实测节省，极具工程价值；但将其包装为“二次方到线性的降维打击”，无异于在与一个工业界从未实际部署的稻草人基线打擂。

长程任务中的双重致命退化

除了算力开销外，论文更有价值的发现揭示了历史过度膨胀所诱发的两类长程特有失效模式。这两种失效无法通过单纯扩充上下文物理窗口得到缓解：

失效一 · 注意力被环境噪声稀释与干扰
环境在交互过程中频繁产出与核心目标无关的遥测数据（例如电量、CPU 负载、网络波动及诊断日志）。此类信息一旦沉淀在对话历史中便获得永久可见性，在后续每一步推理中持续分散注意力。实验显示：当每轮注入 50 条无关噪声时，ReAct 的动作准确率从 0.68 跌至 0.53；在复杂的软件仓库任务中，甚至出现 0.76 暴跌至 0.11 的雪崩。
失效二 · 历史失效事实压制最新动态观测
当外部物理环境在 Agent 控制回路之外发生异步变更（例如上游代码被强制推送、货架货物被外部操作移走），历史记录中关于“旧状态”的陈述依然高权重存在。模型需要耗费 5–14 步的重复错误尝试，才能摆脱旧历史的认知惯性，采信新观测。论文将这一现象定义为“幻觉滞后（Hallucination Lag）”。
核心病理剖析 对话历史的只增不减（Append-only）特性决定了：单次判断失误、环境瞬态噪声或已过期的陈旧事实，其惩罚绝非一次性结算，而是转化为注意力污染，在后续的每一个步骤中被无休止地重现和放大。 这正是上下文压缩研究中“中间迷失（Lost in the Middle）”效应在长程动态交互中的动力学表现：问题不仅在于“找不到历史中的有效信息”，更在于“历史中的无效信息在持续制造认知干扰”。
03

核心机制：将步内推理投影为状态补丁

极简循环背后的状态投影逻辑：让模型只答“改变了哪一格”

试想一个老练的仓库调度员：当接到新任务时，他是去翻阅从建仓第一天起堆积如山的流水账单，还是直接扫一眼墙上随时更新的实时库存白板？SKILL.state 的思路正是这块白板——每一步不再让模型写‘日记’，而是强迫它回答：‘刚刚这一条新观测，究竟改变了世界的哪一个具体格子？’

关键工程隐患 · Algorithm 1 中不可忽视的状态与动作倒置 仔细审视循环体的执行次序（第 7 行与第 8 行）：Σ_t⁺¹ ← Σ_t ⊕ ΔΣ_t 在前，Execute a_t 在后。 这意味着：系统先在白板上把状态改了，随后才真正发出外部执行指令。

在确定性模拟器（如论文中的 Warehouse）中这看似可行，但在真实分布式环境里，外部调用可能网络超时、权限不足或部分成功。一旦“发货动作失败”，状态库里却已经认定货物出库，而论文完全没有定义任何事务回滚、补偿机制或幂等确认语义。

这与 Schema 的合法性校验有着本质区别：校验只能检查补丁格式是否合法（防“语法写坏”），根本防不住现实执行失败（防“物理脱节”）。 若要将该方案引入严谨生产环境，状态更新与动作执行必须被封装在两阶段提交（2PC）中，或者显式引入 pending/confirmed 双态机制。

状态演变：带 null 擦除语义的字典原子合并

其核心更新公式极其简练：Σ_t⁺¹ = Σ_t ⊕ ΔΣ_t。其中 ⊕ 运算定义为带有 null 删除特性的字典合并。若要表示某货架清空，模型只需在增量补丁中将该键设为 null，该项便直接从状态集中被永久擦除——就像板擦拭去粉笔字一样干净利落，绝不需要像传统对话那样记录‘货架之前有货、后来在第 15 步被挪空了’的长篇叙事。

破除误区：Schema 是按领域定义一次，绝非按任务逐个编写

初读论文最常见的疑虑是：‘难道每接到一个任务，工程师都要人工手写一套状态 Schema 吗？’ 论文在此给出了明确答复：Schemas are authored once per domain。以 InterCode CTF 为例，面对 100 道解法迥异的网络安全渗透题，系统始终复用同一套包含 5 个核心字段的领域级 Schema：

discovered_flags
战果登记：已捕获的 Flag 标识
tested_hypotheses
避坑备忘：已验证失败的假说，防止重复撞墙试错
active_files & working_dir
现场定位：当前正分析的文件集合与工作目录路径
cmd_summary
阶段沉淀：关键命令的执行产物与有效输出压缩
思维链伏笔 · 状态本身是否真能做到 O(1)？ 请注意这五个字段中的 discovered_flags 与 tested_hypotheses：从业务逻辑上看，它们本质上是只增不减的累加型列表。 论文推导 O(1) 复杂度的核心假设是 |Σ| 严格有界，但论文从未在长程累加场景下验证过状态体积是否会失控膨胀 —— 详见第 10 节反驳一。
这五个字段背后的通用设计哲学 这绝非特定任务的玩具字段，而是一套极具概括力的自主探索型任务通用状态骨架：我达成了什么、我现在身处何处、我已经排除了哪些错误路线。 工业界十五大平台在自然语言摘要模板中规定的核心槽位（Goal / Progress / Blocked），本质上是在试图捕捉同一批状态信息； 两者的唯一分野在于：传统方案要求模型吐出难以程序化约束的自然语言叙述，而 SKILL.state 产出的是严谨、类型安全、可确定性合并的结构化键值对。

关键指标口径纠偏 · Score 绝非最终“任务完成率” 在审视所有准确率曲线之前，必须首先澄清论文在指标命名上的误导性倾向： SkillExecBench 的 Score 绝不是传统端到端任务的成功率（Success Rate）。论文 §4.3 给出的严格计算公式是： Score = Successful Actions ÷ Total Actionable Events —— 即单步可操作事件中动作执行正确的比例。

这意味着：一个长程任务即使在中途错漏了关键步骤、导致最终业务目标彻底泡汤，只要前序大部分动作合规，它依然能拿到 0.9 以上的虚高评分。 因此，T=100 时汇报的“0.94”，准确含义是在整条执行流中 94% 的单步动作符合规则，绝不能解读为“94% 的任务最终成功交付”。 真正的端到端全局成功率，在全篇论文中仅存在于 InterCode CTF（pass@1 标志着拿到 Flag）与 τ-Bench（由官方评测器核验最终数据库状态）两组基准中。

这一结论对工程选型具有决定性指导意义： 它彻底否定了短程任务的技术选型意义 —— 在 T=10 与 T=25 时，各方案在统计上完全处于噪声重叠区，谁好谁差纯属随机波动； 唯有任务步数深推到 50 步以上，架构层面的抗衰减与低成本优势才真正变成显著事实。

综合能效核算 聚焦至 T=100 步的工业典型跨度：Stateful 基线消耗高达 1,062,387 Token 换得 0.91 的动作正确率，而 SKILL.state 仅凭 65,408 Token 实现了 0.94。 不仅算力开销缩减达 16.2 倍，动作执行质量还提升了 3 个百分点。在该场景下，状态投影范式展现出单方面的全胜姿态。

复杂关系拓扑环境下的表现：优势显著收敛，且出现唯一一次落败凹陷

仓储管理（Warehouse）环境本质上由 500 个彼此完全独立的货架格子构成，在底层数学上天然同构于一个 Key-Value 字典。相比之下，论文引入的第二个环境——软件工程仓库（Software Repository，涉及 Git 分支图、PR 依赖链、CI 流水线状态等强耦合关系网络），才更贴近工业界软件工程的真实复杂面貌。

深度推演 · 摒弃历史的信息损失与“盈亏平衡步数” 即使将 T=25 的性能凹陷归因于测量噪声，两张曲线所展现出的宏观动力学分歧却是无可争议的客观规律： 在彼此孤立的仓储环境中，SKILL.state 从 T=10 开始便与基准并列第一；而在关系高度交织的软件仓库中，它必须苦战至 T=50 才以 0.86±0.04 明确反超 Stateful 基线的 0.74±0.08。

背后的技术本质十分清晰：在任务执行初期，彻底抹杀交互历史会带来直接的信息截断损失；只有当历史滚雪球般膨胀到足以引发模型的‘注意力迷航’与‘上下文污染’时，抹杀历史所带来的信噪比收益才会超越信息丢失的代价。

因此，架构选型必然存在一个盈亏平衡步数 T_break-even：任务内部元素耦合度越高、上下文隐式关联越强，这个临界点就越靠后。 遗憾的是，论文未提供任何估算该临界点的量化模型，而这恰恰是架构师在设计工业级 Agent 调度策略时最渴望获取的决断指标。

噪声免疫机制：并非“抗噪能力强”，而是“噪声根本拿不到入场券”

测试环境在每一轮观测中故意掺杂 5/20/50 条无关遥测指标（如搬运机器人电量、机房温湿度读数、摄像头实时 OCR 乱码、底层操作系统 syslog）。这些数据纯属随机生成，与当前搬运调度任务毫无因果关系。

白名单与黑名单的底层哲学差异 尽管最终得分打平，但两种机制的工程代价大相径庭： Memory 与 Stateful 是在噪声进入后，试图通过调用大模型做摘要来“稀释”或“过滤”噪声，既耗算力又有遗漏概率； 而 SKILL.state 则是凭借 Schema 构筑了一道绝对白名单——因为 Schema 里根本没有‘机器人剩余电量’这一字段，所以杂音从诞生之初就没有任何通道能够写入后续状态字典。

横向映射：放入 Agent 上下文压缩六层模型坐标系

解构六层生命周期：它简化了什么，又将什么转移到了设计期

在我此前关于开源 Agent 平台的系统研究中，十五大主流系统的上下文压缩逻辑被统一解构为六层拓扑：测量、触发、选点、减法、重组与持久化。将 SKILL.state 投射进这套宏观坐标系，会发现它带来了一场更具颠覆性的工程重组。

SKILL.state 的本质并非在六层生命周期中把传统步骤执行得更精细，而是彻底解构并重组了生命周期本身：它唯一彻底删除的是 L2 触发层；将 L1 测量与 L5 重组简化为静态的常量动作；最深远的变革，是将原本在运行时动态博弈的 L3 选点与 L4 减法，提前固化为了设计期的 Schema 架构决策。 贯穿全篇架构对照的核心洞见

这绝非字面上的学术分类游戏。“彻底删除”意味着运行时不再需要为此耗费系统心智，“简化”意味着工程负担显著减轻，而“前移”则意味着系统将原本由大模型动态决策的不可控风险，收拢到了人类工程师可以编写单测、静态类型约束的设计阶段。 以 L1 测量层为例：原论文因假定 |Σ| 恒定有界而认为无需测量；但后文的反驳一揭示，累加型字段的存在使得该假设难以自洽 —— 于是 L1 测量不仅没有多余，反而演变为验证状态字典有界性的关键断言监控。

深度推演：论文未测量的隐性维度（Prompt Cache 成本）

全文出现 0 次的致命变数：当极短 Prompt 撞上云端缓存起征门槛

论文通篇汇报的成本数据，均建立在纯粹的裸 Token 计数（Raw Token Count）之上。然而在真实的工业级 API 计费体系中，几乎没有开发者按裸 Token 付费——主流前沿模型普遍配备了 Prompt Cache（提示词前缀缓存），命中部分享受高达 90% 的折扣（仅按 0.1× 计价）。一旦将缓存计费模型纳入考量，原本看似绝对的能耗倍率将发生出人意料的逆转。

破除直觉常识：云端缓存并不是“只要有前缀就能打折”，它有硬性门槛

Prompt Cache 并不像许多人想象的那样“只要第二轮重合就能命中”。云厂商为了防止显存碎裂与检索开销，普遍设定了最小可缓存前缀起征点（Min Cache Threshold），未达到该门槛时系统一律按 100% 全价计费。Google ADK 的 ContextCacheConfig 规范对此有白纸黑字的定义：

缓存最早从会话的第二轮开始，且要求可缓存前缀达到该模型的最小值：Gemini 2.5 为 2,048 token，Gemini 3 为 4,096 token。因此短会话或单轮会话永远不会被缓存。 Google ADK · ContextCacheConfig docstring（见配套研究 §12.7）

两个无法从论文补齐的缺口 缺口一 · 论文没有公开 input / output 拆分。它的指标定义只有一句 Total Token Cost: the cumulative token burn。 而缓存只折扣 input，output 永远全价。我原来那两个数（909,000 / 47,600）是拿平均 prompt 字符数按 4 字符≈1 token 反推的输入量， 不是论文表里的总量 —— 把它们直接当总成本比，等于让 output 从账上消失了。

缺口二 · 本节没有按任何单一 provider 的完整价目表建模。门槛取自 ADK 文档记载的 Gemini 3 值， 而「命中 0.1×、写入 1.25×」是一档通用的缓存计价形态。Gemini 自己的 context caching 另有创建费、按小时的存储费与它自己的 cached-input 单价， 与这里的算式不是同一套。所以下面给的是敏感性区间，不是某个 provider 的账单。

推论一：压缩式系统在这一维上仍然是最差的

这是我那篇研究 §2.11 的核心张力，在这里闭环 压缩必然要重写历史的开头，而那正是缓存前缀所在的位置。前缀一变，后面全部作废，下一次请求按 1.25×（5 分钟档）或 2×（1 小时档）全价重写。

加上门槛这一条之后，三种运行时的排序是：

ReAct 最好（前缀大、稳定，长程上几乎全程命中）→ 压缩式次之（前缀够大能命中，但每次压缩打掉一次）→ SKILL.state 最差（前缀太小，一次都命不中）。

注意这个排序和裸 token 的排序正好相反。SKILL.state 依然总成本最低 —— 但它是靠「少发」赢的，不是靠「发得便宜」赢的，而且它把「发得便宜」这条路整个堵死了。

工程落地破局：别盲目灌水，真正的杠杆是“稳定前缀工程”

既然单步 Prompt 太短拿不到折扣，是不是要故意往 P 里面注水灌入无意义垃圾话，强行凑满 4,096 Token？这在工程上是极度危险的下策。刻意 padding 会导致首次建连延迟暴涨、拉高首字时间（TTFT），且更长的无关背景会严重摊薄模型的注意力专注度。

  • 公共前缀不仅限于 P 本身：缓存命中判定的是两次请求之间自头部起始、逐字完全相同的一致序列。只要序列化时保持严格的 Key 字典序，Σ 中那些跨步不变的前导字段同样能无缝计入公共前缀！
  • 结构排布远重于体积膨胀：应当将状态字典 Σ 显式划分为“只读/低频不可变区（Immutable）”与“高频变动区（Mutable）”。将不可变区紧贴在 P 后面排布，便能自然而然地拼装出一条超长且极度稳定的黄金前缀。
  • 顺路搭乘免费便车：系统固有的工具集声明、不可篡改的组织治理策略，天然属于不可变信息。将其置于前导位置，是顺带将前缀自然推过门槛，这与第 11 节的“通道 A”不谋而合。
收敛后的说法 不是「P 要写大」，而是：要让 P + Σ 中逐字不变的前导部分合起来越过门槛。

落到工程上是三件具体的事：(1) 序列化用确定的 key 顺序，别让 JSON 序列化顺序随机漂； (2) 把 Σ 显式切成 immutable 区与 mutable 区，immutable 区排在前面； (3) 真正不变的东西（工具定义、项目约定、治理约束）本来就该放进 P —— 它们进去是顺带把前缀撑过门槛，不是为了撑门槛才塞进去。

第三条正好与第 11 节的「通道 A」重合：那些内容你本来就要每步重发，放进稳定前缀是免费的顺风车。
口径声明 本节全部数字为建模推演，基于：4 字符 ≈ 1 token；命中 0.1×、写入 1.25×（一档通用形态，不是任何单一 provider 的完整价目表，Gemini 自己的 context caching 另有创建与存储计费）； 缓存全程不过期（对 ReAct 最有利）；单步 prompt 按 Table 1 拟合成 180·t；门槛取 ADK 文档记载的 Gemini 3 的 4,096 token。

门槛与折扣都是 provider 相关的：若某 provider 的下限低到几百 token，SKILL.state 的前缀就能进缓存，倍率会再往下走。 真实的短 TTL 也常在一次工具调用之间就过期（配套研究 §3 的「软失败」），那会削弱 ReAct 一侧。

我写这一节不是为了给出精确数字，而是为了指出：论文用裸 token 作为唯一成本指标，并且没有公开 input/output 拆分，读者无法据此推出真实成本， 而按任何合理的缓存模型折算，它的成本优势都会从「近二十倍」掉到「个位数倍」。

论证盲区：六个值得商榷的关键反驳点

读完全文之后我真正的保留意见与技术质疑

前面九节我们客观梳理了 SKILL.state 的优势与数据支撑，它的核心主张在受控实验下确实展现了强大的生命力。但一项技术能走多远，往往取决于它的边界在哪里。本节将深入探讨它在理论推导与工程推广上的六大盲区与反驳点——而这恰恰是最关键的部分，因为工业级真实业务场景，大部分都落在了它无法覆盖的那一侧。

反驳一 · O(1) 成立的前提是 Σ 自身有界，而论文从未真正证明这一点

论文的核心公式是 |P_t| = O(|P| + |Σ| + |O|)，并据此得出单步 Prompt 规模「与任务步数 t 无关」的结论。但这一数学推导能够成立的关键前提，是 |Σ| 状态字典体积本身具备有限上界 —— 然而论文通篇没有任何一处对此进行过数学论证或实际轨迹测量。

固定 Schema 仅仅约束了「包含哪些字段」，却丝毫约束不了「每个字段值的具体长度」。 这就像给仓库管理员发了一张只有 5 个栏目的固定账本，表格栏目是固定的，但如果其中一栏写的是“每次尝试失败的详细排错记录”，随着任务不断试错，这一栏就能被写满成千上万行字。这两件在工程上截然不同的事，被论文悄悄混为一谈。

划清证据边界：推断逻辑 vs 论文事实 论文仅公布了 CTF 场景下 Schema 的五个字段名，未公布具体的字段数据类型与更新策略，也未给出 |Σ| 随任务步数（Horizon）演进的实际变化轨迹。 其正文对 CTF 性能提升的归因原文为「maintaining explicit hypotheses and discovered flags」—— 将两个字段合并归因，且未做任何单字段消融实验。

因此下表关于「增长性」的判定是基于字段工程语义的客观推断，而非论文直接陈述。这一反驳的严密形式是条件命题： 如果这些字段在实际实现中按只增列表（append-only）处理，那么单步 O(1) 的理论复杂度即告破产；而论文没有提供任何实验数据让读者排除这种可能性。
O(1) 复杂度是特定环境带来的天然红利，而非该算法的普适数学保证 Warehouse 场景下的 Σ 之所以能在整个评测中维持令人惊叹的平稳（1,775 → 1,811 字符，从 T=10 到 T=200 几乎纹丝不动），核心原因在于该实验环境的物理真实状态天然具备硬性上限：总共只有 500 个离散的货架格子，每个格子存储单个物品标签或 null，智能体的操作纯粹是基于键值的覆盖与删除，业务逻辑中根本不存在任何需要单向累积的字段。

换言之，Table 1 中那条近乎完美的水平线，是特定仓库环境赋予的结构红利，并不是 SKILL.state 算法本身自带的普适定理。 论文从未在任何需要动态累加探索历史的复杂领域，测量过 |Σ| 随步数的真实演进曲线 —— CTF 虽然包含此类累积字段，但实验仅汇报了 pass@1 与总 token，并未给出 Σ 随时间步变化的动态轨迹。

论文自身披露的真实基准数据，其实就已经显露出这种膨胀隐患。在更贴近真实多轮业务流的 τ-Bench Retail 测试中，SKILL.state 的单步 Prompt 规模反而是四种运行时中最为庞大的（3,325 字符 vs 朴素 ReAct 的 2,819 字符）—— 一个号称实现 O(1) 紧凑规模的方法，在最具工业代表性的业务评测上，单步 Prompt 占用竟然反超了未经压缩、直接硬追加历史的 ReAct 基线。

对工业实践的关键启示：Schema 治理绝不可缺位 这正是为什么我们在第 11 节的工程落地建议中，提出使用 tested_hypotheses 字段时必须强制搭配严格的封顶与清理策略：只增字段必须设立明确的条数上限（如仅保留最近 N 条，并辅以历史失败总数计数），或者定期提示模型将其归并抽象为更高维度的排除规则。 否则，开发者无非是把上下文膨胀的物理压力，从对话历史通道直接转移到了状态字典通道，在工程实质上一步没省。

严谨客观的定论不是「SKILL.state 自动实现了 O(1)」，而是：它成功将「运行时上下文是否会失控撑爆」这一不可控的动态随机问题，转化为了「静态 Schema 规范设计与字段长度治理」的可控工程问题。这确实是一个巨大的架构突破——因为 Schema 是可预先静态审计、可编写测试用例、可设置运行时断言的——但这绝不是开箱即得的免死金牌。

反驳二 · 工业界最具竞争力的真实基线在对比中遗憾缺席

论文设立的 Stateful 基线被定义为 「显式结构化状态 + 全量未压缩历史」。然而在当前主流的工业级智能体落地实践中，没有任何一个生产系统会采用如此低效的组合——工业界的真实标配早已演进为「结构化状态/摘要 + 滑动保留最近 20K token 的精确原文（即 Stateful + Compaction Tail 混合架构）」。

反驳三 · 预算对齐实验设置的极限阈值脱离工业级实用标准

论文在公平预算实验中，将所有竞争基线的单步 Prompt 上限强行压缩至 ~1,800 字符（折合仅约 450 token），并在指标单位上存在前述口径混淆（§5 已详述）。

口径纠偏说明 此前曾有粗糙推论直接将 450 token 与生产系统的 20,000 token 相比得出「相差 40 倍」，这一比较已被严格纠偏：因为 20,000 token 在工业级系统（如 OpenClaw / opencode）中代表压缩触发余量或单项原话保留预算，而论文中的 450 token 是压缩后整个 Prompt 的最终目标容量。两者分属完全不同的架构层级，不可做简单的除法换算。

真正站得住脚且足够说明问题的严谨论据在于：论文将全局 Prompt 暴力扼杀在极其苛刻的 450 token 极窄空间内，而成熟的生产级系统（如 Codex CLI）光是给「用户原话逐字保留」这一单项白名单规则就分配了高达 20,000 token 的预算 —— 工业系统单独一项关键信息保护的预算额度，就比论文中压缩基线的全局总容量大出一到两个数量级。

因此，「Summary-capped 准确率崩溃至 0.52」的实验结论，仅仅揭示了在极度窒息的 450 token 超低预算下，文本摘要器根本无法承载 100 步长程任务的上下文密度；它绝不能被偷换概念等同于「工业级上下文压缩体系败给了纯状态机方案」——在合理的工程预算下，二者的终极对决在第四格中依然悬而未决（参见反驳二）。

反驳四 · Warehouse 任务与键值字典方法存在天然同构偏差

Warehouse 基准测试的物理世界底层本质上就是一个离散的 Key-Value 字典：固定 500 个互不重叠的货架插槽，每个插槽对应一个字符串标签或空值。而 SKILL.state 所提出的状态表示模型，在数据结构上也恰好是一个 Key-Value 字典。这并不完全是“通用智能体算法在复杂通用场景中展现出优越性”，而是算法的数据抽象恰好与任务环境底层结构发生了完美同构。

论文自身的扩展实验其实已经诚实地揭示了这一偏差的影响量级：一旦切换到实体依赖与调用拓扑高度交织的真实场景（Software Repository），SKILL.state 的胜势立即从「全程压倒性领先」收缩为「步数推至 T≥50 以后才艰难确立优势」，甚至在早期还出现过被对手反超的凹陷。SkillExecBench 是论文专门自建的评测套件，而在仅有的两个评测环境中，被论文最频繁展示为主图证明卓越性能的 Warehouse，恰恰是对自身算法理论假设最友好、最容易打出高分的特例。

反驳六 · 论文自身列出的局限性直接划出了通用智能体的不可逾越之墙

论文在 Limitations 章节的第一段给出了极为坦诚的边界声明（这也是其治学值得肯定的一面）：

……失效于三种情形：(1) 事先不知道固定 schema、状态结构必须在执行中动态发现时；(2) 一次正确的状态更新依赖于某条更早的观测，而它的相关性在当时未被识别、因而从未被写入状态时；(3) 任务目标本身定义在历史轨迹之上时（审计、追溯 provenance、解释过去的动作）。 论文 §7 Limitations

将这三条局限性翻译为严密的工业工程语言：

  • 第一条绝不等于「所有编程智能体都无法采用状态机」：论文已经在 InterCode CTF 和 Software Repository 两项任务中成功验证，依靠的是人工针对特定领域预先提炼出的静态 Schema；像 Git 分支切换、PR 流转、CI 检查、Issue 状态这类流程固化的标准化工作流，完全可以写出高质量 Schema。 真正被无情排除在外的，是「状态拓扑结构必须在交互探索过程中被动态感知与构建」的开放式探索与排错场景 —— 典型的如「排查并修复线上某个偶发的死锁问题」：你无法在启动前预知这次排查究竟会涉及到哪些代码文件、第三方依赖库或底层错误栈。主流开源 Coding Agent（如 OpenClaw、Hermes、Codex CLI、opencode、kimi-code、Cline、Goose、OpenHands 等）所承接的核心日常任务，恰恰重度集中在这一无法预设 Schema 的开放侧。
  • 第二条是直击纯状态机范式软肋的致命弱点：即时信息投影是不可逆的单向操作。在传统的压缩式架构中，即使某条看似琐碎的日志未被提炼进当前摘要，它依然在近期未经压缩的原始上下文尾部（Tail）中静默存活，一旦后续步骤发现端倪，仍有机会被回溯提取；而在 SKILL.state 的纯净状态字典中，任何未被当前规则捕获的早期观测在发生的那一刻便被永久抹去。「事后方知关键」这一认知探索的不对称规律，是纯粹的状态即时投影架构在逻辑上根本无法解救的死穴。
  • 第三条对应了工程实践中「上下文压缩绝不能物理销毁原始数据」的核心底线。业界成熟框架普遍采用只追加会话树（Session Tree）、事件溯源（Event Sourcing）与软归档机制，确保任何时刻都能审计完整的决策链路。SKILL.state 维护的 Σ 本质上只是一张易失的最新状态表，而非审计日志；一旦系统需要追溯责任因果，必须在系统外平行架设一套独立的数据存储。
论文占据绝对优势却未予测量的隐形王牌 端到端执行延迟（Latency）。全文没有提供任何一条物理墙钟时间（Wall-clock Time）数据。但单步 Prompt 从 36,362 字符锐减至 1,905 字符，首字生成延迟（TTFT）与网络传输耗时几乎必然呈现断崖式下降——而在长程智能体的实际用户体验中，最敏感的痛点恰恰是多轮交互的等待延迟。 论文在 Introduction 首段甚至明确将“缓解延迟退化（Latency Degradation）”列为了核心研究动力之一，但在后续的详尽评测中竟然未给出任何实测延迟指标。这无疑是作者团队在论证过程中自身遗漏的一张极具说服力的关键底牌。

梳理核心认知边界与工程决策自查清单

九道核心自测题（深度复盘）

SKILL.state 在执行每一步时，输入给模型的三大要素是什么？哪一项是动态可变的？
P（技能静态说明书，全局固定不可变）、Σ_t（结构化执行状态字典，全流程中唯一动态演进的要素）、O_t（当前步环境给出的最新单条观测）。过往所有历史对话、探索动作以及中间推理痕迹，一律不进入当前 Prompt。
模型在每一步推理后产出哪三样要素，它们的最终生命周期与去向分别是什么？
R_t 步内思考推理 → 用于生成决策与补丁，当前步校验通过后立即丢弃，绝不跨步传递；
ΔΣ_t 增量状态补丁 → 经宿主运行时严格的确定性 Schema 校验后合并入全局状态字典 Σ；
a_t 执行动作 → 派发给外部环境执行并收集下一次观测。
最核心的认知在于：模型在步内保留了完整强大的深度推理能力，但该思考过程绝不跨轮留存。
论文宣称的单步 O(1) 空间复杂度，其成立的关键前提是什么？这一前提在论文中得到实证了吗？
前提是状态字典体积 |Σ| 本身具备严格的有限上界 —— 而论文通篇没有任何一处对此进行过数学证明或动态演进测量。

在实际的 CTF 任务中，discovered_flags 与 tested_hypotheses 语义上均为只增列表（Append-only）；尤其是论文重点归因的 tested_hypotheses，其核心价值恰恰来自于记录失败试错记录，天生具备随步数无限拉长的风险。

Warehouse 测试中展现出的绝对平稳水平线，是特定仓库离散物理空间带来的天然红利（500 货架，纯单值覆盖与删除，无累积字段），而非算法本身的普适数学保证。 更严谨的认知是：SKILL.state 并没有自动消灭上下文膨胀，而是将运行时的动态膨胀风险前移转化为了静态 Schema 规范与字段长度治理问题 —— 这是一个巨大的架构进步，但决非自动获得的免死金牌。
论文声称将累积上下文消耗从 O(T²) 降至 O(T)。这一结论面对现代工业级压缩系统依然成立吗？
并不成立。O(T²) 的二次方膨胀仅对完全不压缩、无限硬堆叠历史的朴素 ReAct 成立。任何引入了滑动窗口或压缩机制的现代系统，单步 Prompt 上限都被硬性限制在窗口常数 W 之内，长程累计消耗本质上都是 O(T·W) —— 同样严格保持线性增长。 SKILL.state 相较于现代压缩系统的优势，本质上是窗口常数大小的倍率优势（将常规压缩的 W ≈ 30,000 token 压缩至极简状态字典的 W ≈ 500 token），属于 16–40 倍的常数级优化，而非计算复杂度的阶数跨越。
在同预算对比实验中，LLMLingua 准确率崩塌至 0.22 的根因是什么？印证了工程实践中的哪条铁律？
根因在于基于统计信息熵的文本压缩算法，无差别地过滤掉了大量在统计学上看起来冗余、但在程序逻辑上至关重要的精细插槽标识符（如文件路径、资源 ID、细分错误码）。 这一结果以极端的反面实证，严厉印证了工业界的共识原则：「保留精确标识符是上下文压缩的绝对生命线」——主流平台在压缩 Prompt 中都会强制锁定「必须逐字无损保留路径与唯一标识符」。如果不设防地任由统计压缩器裁剪，准确率就会像实验中那样发生断崖式溃败。
为什么说状态字典架构将信息存活性从「概率问题」转变为「程序问题」，却同时也引入了「单点故障脆弱性」？
在传统基于滑动窗口的压缩系统中，即使自然语言摘要漏掉了某些信息，原始历史尾部（Tail）依然留有容错余地，信息遗失往往是平缓渐进的； 而在 SKILL.state 架构中，一个键值一旦被模型错误地置为 null，便在内存中物理消亡，不存在第二份历史副本可供容灾，其失效是非生即死的二值突变。 实证数据：开源轻量模型在长程任务中高达 68% 的失误，恰恰是因为在生成补丁时误删了本应继续保留的关键状态键。
主流大模型的 Prompt Cache 门槛机制，为什么反而对 SKILL.state 构成了结构性不利？
现代模型供应商的缓存计费通常设定有最小可缓存前缀门槛（例如 Gemini 2.5 为 2,048 token，Gemini 3 为 4,096 token），低于该门槛的请求完全无法激活缓存优惠。

SKILL.state 每步逐字不变的静态说明书 P 仅约 350 token，永远无法单凭自身迈过这一门槛；而传统长上下文基准在运行数十步后便能轻易越过门槛，后续每步均能享受高比例的缓存折扣。 这导致在实际账单核算中，Warehouse T=100 步时原本高达 19.0× 的原始 Token 差距，在计入缓存折扣后被收窄至 3–8× 的有限区间内。

这一工程悖论表明：使得 SKILL.state 在原始 Token 上极致便宜的特性（Prompt 极简），恰恰是使其在工业级缓存体系中无法吃到折扣的根源所在。 合理的工程解法并非盲目向 P 中灌水，而是构建跨步稳定的前缀序列：固定 Schema 字段排序，将字典划分为不可变前缀区与动态变动区，让静态说明书与高频不可变状态合并跨过缓存门槛。
论文自身坦承的三大失效场景是什么？其中哪一项直接排除了通用 Coding Agent 的核心主场？
三大失效场景：(1) 事先缺乏先验 Schema、状态结构必须在执行中动态发现；(2) 关键决策依赖于早期观测，但该观测在当时未被识别出相关性因而未写入状态；(3) 任务目标本身直接定义在完整的历史轨迹之上（如合规审计、因果追溯）。

第 (1) 项与第 (2) 项直接命中了通用 Coding Agent 的软肋：在开放式的代码排错与复杂系统调试中，开发者与智能体事先根本无法预知会遭遇哪些文件与异常分支；加之单向即时投影不可逆的物理特性，一旦早期把当时看似无关的日志丢弃，后续就再也无法回溯提取。工业界主力 Coding Agent 多数都处于这一充满不确定性的领域。
如果在现有的成熟 Agent 系统中渐进式采纳本论文的思想，最优先切入的第一步是什么？
将当前任务的核心执行状态（如待办清单 TODO、当前工作目录、活跃文件句柄）从易损的自然语言摘要中彻底解耦出来，改由宿主运行时直接挂载真实数据源，并严禁摘要器进行二次转述。 这一改造不需要对现有底层模型调用管线进行伤筋动骨的大改，仅需重定向单一结构化字段的数据源即可立即收效；kimi-code 对 TODO 清单的实现便印证了这一路径。 决策黄金法则只有一句话：凡是能够明确提炼出稳定字段名的核心状态，都绝不应经由文本摘要器进行有损转抄。

「关键字段纯属只增」「性能提升完全来自只增累积」 论文仅公开了 5 个字段名称，未披露底层类型与更新逻辑；CTF 的归因是假设和旗标两者合并，且缺乏单字段消融。此前将推断冒充成了事实 严格修改为条件命题：Schema 静态不代表字段值有界；若采用 Append-only 列表实现，则 O(1) 理论推导无法成立
「评测预算被恶意压低至工业系统的 1/40」 450 token 是论文中压缩后最终 Prompt 上限，而 20,000 token 是生产系统的压缩触发余量或单项原话保留额度，二者层级不同，直接做除法属于逻辑谬误 删除不严谨的比值；改为跨层级客观对照：工业系统单项关键信息的保护配额即可覆盖论文全量预算的一到两个数量级
「Limitations 第 (1) 条排除了所有 Coding Agent」 论文自身即在 InterCode CTF 和 Software Repo 两个代码环境中验证通过；被真正排除的是状态拓扑必须动态探索感知的任务，而非整个编程类别 精确收窄至缺乏先验固化 Schema 的开放式复杂排错与动态调试场景
