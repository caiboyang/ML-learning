把历史扔掉
只留一份可改写的状态

SKILL.state 提出一个反直觉的运行时：agent 每一步只看到三样东西——技能说明书、一份结构化状态、最新一条观测。 之前的推理、动作、工具输出全部不进下一次 prompt。 这不是「把历史压小」，是不让历史存在。本文逐图拆解它的方法与全部实验数据， 并把它放回我此前十五平台压缩机制研究的坐标系里，看它到底证实了什么、又绕开了什么。

01

一分钟看懂：它到底改了什么

一张图就是全部论点

今天几乎所有 agent 运行时都是「往下接」的：每一步把新的推理、动作、观测追加到一条越来越长的记录后面，然后整条重新发给模型。SKILL.state 说：别接了。

三句话版本

  • 做法：每一步的 prompt 只由三部分构成 —— 不变的技能说明书 P、结构化执行状态 Σ_t、最新观测 O_t。模型输出推理 R_t、状态补丁 ΔΣ_t、动作 a_t；状态更新完，推理立刻被永久丢弃。
  • 结果：单步 prompt 恒定，累计 token 从 O(T²) 降到 O(T)。T=100 时 65,408 token vs LangGraph 式基线 1,062,387 —— 16.2 倍；同时准确率 0.94 vs 0.91。
  • 代价：你必须提前为这个领域写好 schema。论文自己的 Limitations 第一条就说：schema 事先不知道、必须边跑边发现时，这套方法不成立。

02

问题：历史为什么必然膨胀

O(T²) 是怎么来的

LLM 是无状态的。第 t 步不是「接着第 t-1 步说」，而是把前面所有内容重新发一遍。所以单步 prompt 长度 |C_t| = O(t)，把 T 步加起来：

我的第一条补充 · 论文的渐进复杂度框架被夸大了 论文把对手统一写成 O(T²)，把自己写成 O(T)，读起来像是一个数量级的改进。 但 O(T²) 只对完全不压缩的 ReAct 成立。任何做了压缩的运行时，单步 prompt 都被窗口 W 卡住，累计是 O(T·W) —— 同样是线性的。

所以 SKILL.state 与真实生产系统的差距不是渐进阶数的差距，是常数的差距：W 从 ~30,000 token 降到 ~500。 这个常数很大（论文实测 16–40 倍），值得做；但把它讲成「二次降一次」，比较的是一个没人在生产里跑的对手。

除了钱，还有两件更要紧的事

论文真正有说服力的部分不在 token 账上。历史膨胀会带来两个只有长程任务才暴露的失效，而它们都不是「加大窗口」能解决的：

失效一 · 注意力被噪声拖走
环境每一步都会吐出无关遥测（电量、CPU、syslog）。它们一旦进了历史就永久留在那里，并在后面每一步继续消耗注意力。论文实测：注入 50 条/轮噪声，ReAct 从 0.68 掉到 0.53；软件仓库环境更狠，0.76 → 0.11。
失效二 · 过期事实压倒新观测
外部世界在 agent 的动作循环之外被改动（别人 force push 了、货被人搬走了）。历史里写着「货在 shelf_42」的那句话不会消失，于是模型要花 5–14 步才肯相信新的观测。论文管这叫 hallucination lag。
这两条都指向同一个机制 历史是只增不减的，所以任何一次错误、噪声、或已经过期的事实，代价都不是一次性的，而是要在剩下每一步里反复付。 这正是我此前研究里 Lost in the Middle 那节的动力学版本：不只是「中间的东西读不到」，而是「中间的坏东西一直在读」。

方法：把推理投影成状态补丁

Algorithm 1 只有九行

整套方法的全部内容是：让模型每一步都回答「这次观测改变了世界的哪一格」，而不是「到目前为止都发生了什么」。

状态怎么改：字典合并 + null 即删除

更新规则只有一条：Σ_t⁺¹ = Σ_t ⊕ ΔΣ_t，其中 ⊕ 是带 null 删除语义的字典合并。把一个 key 设成 null 就等于把它从状态里抹掉。

schema 是按领域写一次，不是按任务写

最容易被误解的一点：这不是给每个任务手写状态结构。论文的说法是 schemas are authored once per domain，并给了最有说服力的一个例子 —— InterCode CTF 的 100 道互不相同的题，共用同一个五字段 schema：

discovered_flags
已拿到的 flag
tested_hypotheses
试过且失败的思路 —— 防止重复试同一条命令
active_files & working_dir
当前在看哪些文件、在哪个目录
cmd_summary
命令历史的压缩形态
先记一笔，第 10 节会算这笔账 这五个字段里，discovered_flags 与 tested_hypotheses 都是只增列表。 论文的 O(1) 结论要求 |Σ| 有界，而它从没验证过这件事 —— 详见第 10 节反驳一。
这五个字段值得盯着看一会儿 它们不是「仓库有几个货架」那种玩具状态，而是一套通用的探索型任务状态：做过什么、当前在哪、已排除什么。 我此前研究里十一家的结构化摘要模板（Goal / Progress / Done / In‑Progress / Blocked / Next Step） 要表达的其实是同一批槽位 —— 区别只在于：模板产出的是自然语言段落，schema 产出的是可程序化校验的字典。

四种运行时的 prompt 长什么样

论文 Appendix A 给了四份模板。把它们并排放，差异一目了然：

运行时prompt 结构历史怎么处理
Prompt (ReAct)Instructions + History[全部观测与响应] + Latest Observation全部保留
Memory (Summary)Instructions + Summarized History + 最近 3 轮原文 + Latest Observation摘要 + 3 轮滚动窗口
Stateful (LangGraph)Instructions + Current State (JSON) + History[全部] + Latest Observation状态与全量历史并存
SKILL.stateInstructions + Σ_t (JSON) + Latest Observation没有历史这个字段

论文强调 skill.instructions 在四种运行时里逐字相同，以此把「上下文管理方式」隔离成唯一自变量。这个控制做得是干净的。 但请记住第三行：它们的 Stateful 基线是「状态 + 全量历史」 —— 这一点后面第 10 节会变成主要的争议点。

数据一：长程扩展

Table 1 & Table 6 · Gemini-3-Flash · 5 seeds
先把口径立住：这批合成实验带误差，也带显著性声明 论文 §5 有一段容易被跳过的 Statistical Significance：全部合成实验跑 5 个 procedural generator seed， 结果按 mean ± 样本标准差 报告，而 SKILL.state 与基线的差异只在 T≥50 才具统计显著性（paired t-test, p<0.01）。

这句话有两个方向的后果：它加强了长程结论（T≥50 的差距不是噪声），同时削弱了短程读数—— T=10 与 T=25 的排名不该当结论看。本页所有折线图都画了 ±SD 误差棒，展开的数据表也保留了标准差。 本页第一版只报了均值，是一处遗漏，已补。

先看最核心的那张图。横轴是任务步数，纵轴是整场任务烧掉的 token 总量 —— 注意纵轴是对数刻度，否则黄线会贴在地板上看不见。

把两张图合起来读 T=100 那一列：Stateful 基线花 1,062,387 token 换到 0.91，SKILL.state 花 65,408 token 换到 0.94。 16.2 倍的成本差，外加 3 个点的准确率。这不是一个需要权衡的取舍，在这个 benchmark 上它是单方面更好。

换到关系型环境：优势变小，而且出现了唯一一次落败

Warehouse 是 500 个互不相干的格子，天然就是一个字典。论文的第二个环境（Software Repository：Git 分支、PR、CI 状态构成的纠缠图）才是更像真实任务的那个。

我的读法（注意这是解释，不是论文结论） 即便把 T=25 那个凹陷算作噪声，两个环境的形状差异仍然是真的：Warehouse 上 SKILL.state 从 T=10 就并列第一， Software Repository 上要到 T=50 才明确领先（0.86±0.04 vs 0.74±0.08），而这正好是论文显著性区间的起点。

合理的解释是：丢掉历史本身有信息代价，只有当历史长到开始伤害模型时，这个代价才转为收益，所以存在一个盈亏平衡的 T， 且环境的关系纠缠度越高，它越靠后。

论文没有给出估算这个平衡点的方法，而这恰恰是工程上最需要的那个数。 我也无法从这两条曲线把它定到一个具体值——只有两个环境、四个 horizon，不足以拟合。这里给的是方向，不是公式。

数据三：噪声、状态漂移、公开 benchmark

Table 2 / 3 / 4 / 9 / 10

噪声鲁棒性：不是「抗住了」，是「根本没进来」

环境每一步往观测里塞 5/20/50 条无关遥测（机器人电量、HVAC 传感器、摄像头 OCR、syslog），全部随机生成、与任务无关、不改变真实世界状态。

先说清楚：这一组不是 SKILL.state 的独占优势 高噪声下 Memory 是 0.96、Stateful 是 0.98、SKILL.state 是 0.98 —— 三者基本打平。崩掉的只有纯 ReAct 一家。

所以这组实验证明的是「别把无关 telemetry 留在未来的 prompt 里」，而不是「结构化状态优于摘要」。 论文 Appendix C 也写明它只测了 Condition 1（irrelevant context），不是所有类型的上下文污染 —— 「看起来相关但其实误导」的那一类完全没测，而那才是真实环境里更难的。
但机制上的差别仍然值得说清 Memory 与 Stateful 是把噪声摘要掉或稀释掉；SKILL.state 是噪声从来没有机会进入下一次 prompt —— 它在生成 ΔΣ 的那一刻就被过滤了，因为 schema 里根本没有「电池电量」这个字段。

这是 schema 最被低估的作用：它是一个白名单。 摘要器面对的是「什么该删」的开放问题，schema 面对的是「什么该留」的封闭问题。 这正是我研究 §2.13「最好的压缩是不压缩」那条的机制版本。

差别落在成本而不是分数上：三家都能抗噪，但只有 SKILL.state 是免费抗的 —— 不需要额外的摘要调用。

状态漂移恢复：从 5–14 步到 0 步

实验设计得很干净：在 agent 的动作循环之外改变真实世界（别人把货搬走了、别人 force push 了、CI 变成 flaky），然后只通过一条普通观测告诉 agent。

别忽略最后那一行 两个环境各有一个场景是所有运行时都失败的：Warehouse 的「订单被取消」、Software Repo 的「PR 被关闭」。 这两种都属于「某个已经开始的义务被外部撤销」——不是状态值变了，是任务目标变了。SKILL.state 也救不了。 这与我研究里 ADK 那条「把未闭合的义务而不只是 tool pair 作为切点约束」指向同一个盲区。

数据表 · 论文 Table 4
  • InterCode CTF 是最漂亮的一格：54.2% vs 次优 46.4%，同时 token 只有 ReAct 的 40%。论文给的解释是 tested_hypotheses 这个字段——把「试过且失败的思路」显式记下来，模型就不会重复试同一条命令。这是五个字段里最像通用能力的一个。

论文的呈现方式是把这两张表放进附录 D，正文只写「across both proprietary and open-weight models」。技术上没说错，但正文没有一处提到 T=100 的那个平手。

为什么会这样：错误分类给了答案

论文 §5.7 对 Gemma 的失败日志做了归类，这是全文我认为最有工程价值的一段：

我认为这里藏着整篇论文最重要的一句话 68% 的错误是「更新状态时误删了本该保留的 key」（premature state overwrite / deletion）。 请把它和我研究 §21.2 引的 ConstraintRot 那条放在一起看：约束存活时违规率 0%，被丢弃时 38% —— 存不存活几乎就是全部。

压缩式系统里，摘要漏了一条约束，你还有未被压缩的 tail 兜底，失效是渐进的； SKILL.state 里，一个 key 被 null 掉就是真的没了，没有第二份拷贝，失效是二值的。

所以这套架构把「信息存活」从一个概率问题变成了一个程序问题——同时也变成了一个单点。 这是它最大的优点和最大的风险，而且是同一件事。

对照我的压缩研究：六层坐标系里它站在哪

这一节是本文的主体

我此前那篇研究把十五个平台的压缩机制统一到六层：测量、触发、选点、减法、重组、持久化。把 SKILL.state 放进这个坐标系，会发现一件比「它更省 token」有意思得多的事。

SKILL.state 不是在这六层里做得更好。它真正取消的只有 L2 触发；L1 与 L5 被简化成常量级的固定动作； 而最关键的改变是把 L3/L4 从运行时决策前移成设计期决策。 这一句是我读完全文最想留下的总结

这个区分不是咬文嚼字。「删掉」意味着你不用再想这件事，「简化」意味着你还得想、只是变简单了。 L1 就是最好的例子：论文因为假定 |Σ| 有界而不需要测量，但反驳一说明这个假定没被验证 —— 于是 L1 不但没消失，反而成了这套架构最该补上的那一层监控。

两种哲学：事后减法 vs 事前投影

逐条对照：我研究里的哪些结论被验证了

我那篇研究的全部结论来自逐文件读源码，回答的是「谁怎么做的」；做得好不好，源码答不了。这篇论文补上了其中几格：

我的分析：论文没测的那一维

prompt cache · 全文出现 0 次

论文报的全部成本指标都是裸 token 计数。但没有人按裸 token 付钱 —— 所有主流 provider 都有 prompt cache，命中部分按约 0.1 倍计价。这一维一旦计入，结论会变，而且变的方向不是我一开始以为的那个。

先讲一个几乎所有人都会忽略的前提：缓存有门槛

prompt cache 不是「有前缀就能命中」。它有一条最小可缓存前缀的硬性下限，低于它一个 token 都不缓存。Google ADK 的 ContextCacheConfig 把这条写在 docstring 里：

缓存最早从会话的第二轮开始，且要求可缓存前缀达到该模型的最小值：Gemini 2.5 为 2,048 token，Gemini 3 为 4,096 token。因此短会话或单轮会话永远不会被缓存。 Google ADK · ContextCacheConfig docstring（见配套研究 §12.7）

论文全部主实验都跑在 Gemini-3-Flash 上，门槛就是 4,096 token。于是：

这是本页最反直觉的一条，也是我第一版写错了的一条 我最初假设 SKILL.state 的 P（~350 token）能拿到缓存折扣。在 Gemini 3 上不可能 —— 350 远低于 4,096。

换句话说：让 SKILL.state 便宜的那个性质（prompt 极小），正是让它拿不到缓存折扣的那个性质。 它不是「缓存得差一点」，是结构性地被排除在缓存之外。

但这个折算算不出一个精确数字 —— 只能给区间

两个无法从论文补齐的缺口 缺口一 · 论文没有公开 input / output 拆分。它的指标定义只有一句 Total Token Cost: the cumulative token burn。 而缓存只折扣 input，output 永远全价。我原来那两个数（909,000 / 47,600）是拿平均 prompt 字符数按 4 字符≈1 token 反推的输入量， 不是论文表里的总量 —— 把它们直接当总成本比，等于让 output 从账上消失了。

缺口二 · 本节没有按任何单一 provider 的完整价目表建模。门槛取自 ADK 文档记载的 Gemini 3 值， 而「命中 0.1×、写入 1.25×」是一档通用的缓存计价形态。Gemini 自己的 context caching 另有创建费、按小时的存储费与它自己的 cached-input 单价， 与这里的算式不是同一套。所以下面给的是敏感性区间，不是某个 provider 的账单。

把口径摆正之后重算。锚定在论文公开的总量上（T=100：ReAct 1,245,413，SKILL.state 65,408，裸比 19.0×）， 设 f 为总量中属于 input 的比例（未知），ReAct 的 input 在门槛模型下的有效系数是 0.172，SKILL.state 拿不到任何折扣：

# 有效成本
ReAct       = 0.172 × f × 1,245,413  +  (1 − f) × 1,245,413
SKILL.state = 65,408                                  # 全程无缓存
input 占总量的比例 fReAct 有效成本SKILL.state倍率
1.00（全部是 input，下界）214,70065,4083.3×
0.90317,80065,4084.9×
0.80420,90065,4086.4×
0.73（4 字符≈1 token 反推，上界）493,00065,4087.5×
所以正确的说法是 裸 token 19.0× → 计入缓存门槛后大致落在 3–8×。精确值取决于论文未公开的 input/output 拆分，拿不到原始 usage 就推不出来。

值得记一笔的是方向：我上一版报的 3.3× 其实是这个区间的下界，不是中点 —— 因为 output 永远全价、永不缓存，而 ReAct 的 output 绝对量更大， 把它算进来反而抬高倍率。两次修订我都把自己的批评做过了头，这次是往回收。

不受这个不确定性影响的是定性结论：量级从「近二十倍」掉到「个位数倍」，而且下面这条排序反转是稳的。

推论一：压缩式系统在这一维上仍然是最差的

这是我那篇研究 §2.11 的核心张力，在这里闭环 压缩必然要重写历史的开头，而那正是缓存前缀所在的位置。前缀一变，后面全部作废，下一次请求按 1.25×（5 分钟档）或 2×（1 小时档）全价重写。

加上门槛这一条之后，三种运行时的排序是：

ReAct 最好（前缀大、稳定，长程上几乎全程命中）→ 压缩式次之（前缀够大能命中，但每次压缩打掉一次）→ SKILL.state 最差（前缀太小，一次都命不中）。

注意这个排序和裸 token 的排序正好相反。SKILL.state 依然总成本最低 —— 但它是靠「少发」赢的，不是靠「发得便宜」赢的，而且它把「发得便宜」这条路整个堵死了。

推论二：要越过门槛，动的不一定是 P，而是稳定前缀

我第一版从上面那条推出了「P 必须自己超过门槛，所以要故意把说明书写大」。这个推论下得太急了。缓存命中要求的是两次请求之间逐字相同的那段前缀够长 —— 它不一定在 P 结束的地方就断掉。

  • 它可以延伸进 Σ 里不变的那一段。只要序列化时 key 顺序稳定，Σ 中本轮没被改动的前导字段仍然逐字相同，照样算在公共前缀里。
  • 所以真正的杠杆是排布，不是体积。把 Σ 按「几乎不变 / 经常变」分区，不变的那半放前面、易变的放后面，公共前缀就能自然变长 —— 论文那个把整个 inventory 混在一起、每步改一格的序列化方式，恰恰是最坏的一种排布。
  • Google 的公开建议也只是「把大而共用的内容放在 prompt 开头」，并没有说 P 自己必须超过门槛。
  • 刻意 padding 有真实代价：首次写入与未命中时按全价计，而且更长的 prompt 会摊薄注意力、抬高延迟。为了凑门槛去灌水是负收益的。
收敛后的说法 不是「P 要写大」，而是：要让 P + Σ 中逐字不变的前导部分合起来越过门槛。

落到工程上是三件具体的事：(1) 序列化用确定的 key 顺序，别让 JSON 序列化顺序随机漂； (2) 把 Σ 显式切成 immutable 区与 mutable 区，immutable 区排在前面； (3) 真正不变的东西（工具定义、项目约定、治理约束）本来就该放进 P —— 它们进去是顺带把前缀撑过门槛，不是为了撑门槛才塞进去。

第三条正好与第 11 节的「通道 A」重合：那些内容你本来就要每步重发，放进稳定前缀是免费的顺风车。
口径声明 本节全部数字为建模推演，基于：4 字符 ≈ 1 token；命中 0.1×、写入 1.25×（一档通用形态，不是任何单一 provider 的完整价目表，Gemini 自己的 context caching 另有创建与存储计费）； 缓存全程不过期（对 ReAct 最有利）；单步 prompt 按 Table 1 拟合成 180·t；门槛取 ADK 文档记载的 Gemini 3 的 4,096 token。

门槛与折扣都是 provider 相关的：若某 provider 的下限低到几百 token，SKILL.state 的前缀就能进缓存，倍率会再往下走。 真实的短 TTL 也常在一次工具调用之间就过期（配套研究 §3 的「软失败」），那会削弱 ReAct 一侧。

我写这一节不是为了给出精确数字，而是为了指出：论文用裸 token 作为唯一成本指标，并且没有公开 input/output 拆分，读者无法据此推出真实成本， 而按任何合理的缓存模型折算，它的成本优势都会从「近二十倍」掉到「个位数倍」。

它不成立的地方：六条我要反驳的

读完全文之后我真正的保留意见

前面九节我基本在替这篇论文说话，因为它的核心主张确实成立。这一节讲它不能推广到哪里——而这恰恰是我最关心的部分，因为我研究的那十五个平台，几乎全都落在它不成立的那一侧。

反驳一 · O(1) 只在 Σ 自己不增长时成立，而论文从未验证这一点

论文的核心公式是 |P_t| = O(|P| + |Σ| + |O|)，「与 t 无关」。但这个式子成立的前提是 |Σ| 本身有界 —— 而论文没有任何一处论证或测量这件事。

固定 schema 只约束字段的集合，不约束字段值的长度。这两件事被论文当成了一件。

先划清证据边界：下面这张表是推断，不是来源事实 论文只公布了 CTF schema 的五个字段名，没有公布字段类型、更新策略，也没有给出 |Σ| 随 horizon 变化的轨迹。 它对 CTF 提升的归因原文是「maintaining explicit hypotheses and discovered flags」—— 两个字段一起，而且没有做字段消融。

所以下表的「增长性」一列是我按字段语义推断的，不是论文陈述。这条反驳的正确形式是条件式： 如果这些字段按 append-only 实现，那么 O(1) 就不成立；而论文没有提供任何证据让读者排除这种实现。
所以 O(1) 是环境的性质，不是方法的性质 Warehouse 的 Σ 之所以恒定（1,775 → 1,811 字符，T=10 到 T=200 几乎不动），是因为那个环境的真实状态本来就有界：500 个格子，每格一个物品或 null，动作只是覆盖和删除，没有任何一个字段会累积。

换句话说，Table 1 里那条漂亮的水平线是 Warehouse 给的，不是 SKILL.state 给的。 论文没有在任何一个需要累积字段的领域测过 |Σ| 的增长 —— CTF 有这样的字段，但那一组只报了 pass@1 与总 token，没报 Σ 随步数的轨迹。

论文自己的数据里就有这个苗头。τ-Bench Retail 上，SKILL.state 的单步 prompt 是四种运行时里最大的（3,325 字符 vs ReAct 2,819）—— 一个号称 O(1) 的方法，在最接近真实业务的那个 benchmark 上，prompt 比纯追加的 ReAct 还大。

这条怎么改写本页其他部分 第 11 节推荐 tested_hypotheses 那条动作，必须附一个封顶策略：只增字段要么设条数上限（保留最近 N 条 + 一个计数），要么定期让模型把它归并成更抽象的排除规则。 否则你只是把上下文膨胀从对话通道搬到了状态通道，一步没省。

正确的说法不是「SKILL.state 是 O(1)」，而是：它把「上下文会不会爆」从一个运行时问题，变成了一个 schema 设计问题。这是个巨大的进步 —— 因为 schema 是你能审、能测、能加断言的 —— 但它不是一个自动获得的保证。

反驳二 · 最该有的那个基线不存在

论文的 Stateful 基线是 「结构化状态 + 全量历史」。而我研究的十五个平台，没有一家是这么跑的——它们跑的是「结构化摘要 + 20K token 的原文 tail」。

反驳三 · 预算对齐实验的预算远低于任何生产系统的保留量

论文的预算是 ~1,800 字符 ≈ 450 token，而且表头写 tokens、正文写 characters、指标定义又说 characters（§5 已列）。

这里我上一版做了一个不成立的除法，已删除 我原来写「掐到真实系统的 1/40」，用的是 450 token 对 OpenClaw / opencode 的 20,000 token。 这两个数不是同一个量：20,000 是压缩触发余量（还剩多少空间就动手），Codex 那个 20,000 是用户原话保留预算； 论文那个 450 是压缩之后整个 prompt 的目标大小。分属不同机制层，直接相除得不出「生产系统信息预算多 40 倍」。

能站得住的说法是这个，而且它已经够了：论文把整个 prompt 压到约 450 token，而 Codex CLI 光是逐字保留的用户原话一项就给到 20,000 token 预算 —— 生产系统单独一个保留项就比论文压缩基线的全部预算大一到两个数量级。

所以「Summary-capped = 0.52」告诉我们的是450 token 的摘要撑不住 100 步，不是「生产级 compaction 撑不住 100 步」。这个实验确实证明了「统计式压缩器会毁掉精确标识符」（这条我完全同意，见第 5 节），但没有证明「压缩式路线打不过状态式路线」—— 那一格仍然是空的（反驳二）。

反驳四 · Warehouse 与方法同构

Warehouse 的真实世界状态本身就是一个字典：500 个互不相干的格子，每格一个字符串或 null。而 SKILL.state 的状态表示也是一个字典。这不是「方法在这个任务上表现好」，这是方法与任务共用同一个数据结构。

论文自己其实给出了这个偏差的量：换到关系纠缠的 Software Repository 环境，优势从「一开始就赢」退化到「T≥50 才赢」，中间还出现一次落败。SkillExecBench 是论文自建的，而它的两个环境里，被反复用来做主图的那个恰好是对方法最友好的那个。

两处都不是造假——数据都在表里。但它们都是读者需要主动去附录找才会发现的不利证据，而正文的概括性措辞恰好把它们盖住了。

反驳六 · 它自己的前提就排除了我研究的那批系统

论文 Limitations 第一条写得很清楚（这一点我要给它记一功——写得诚实）：

……失效于三种情形：(1) 事先不知道固定 schema、状态结构必须在执行中动态发现时；(2) 一次正确的状态更新依赖于某条更早的观测，而它的相关性在当时未被识别、因而从未被写入状态时；(3) 任务目标本身定义在历史轨迹之上时（审计、追溯 provenance、解释过去的动作）。 论文 §7 Limitations

把这三条翻译成工程语言：

  • 第 (1) 条不等于「coding agent 全都不行」—— 这一点我第一版写窄了。论文自己就在两个 coding 相关环境上跑通了（InterCode CTF、Software Repository），靠的正是预先写好的领域 schema；分支 / PR / CI / issue 这类结构稳定的 workflow，schema 完全写得出来。 真正被排除的是「相关状态结构必须在执行中才被发现」的那部分开放式 coding 与 debugging ——「修复这个仓库里的登录 bug」属于这一类：你事先不知道会碰到哪些文件、哪些框架、哪种错误。 我研究的十五个平台里，OpenClaw、Hermes、Codex CLI、opencode、kimi-code、Cline、Goose、OpenHands 八家的入口任务恰好偏在这一侧 —— 不是它们不能用 schema，而是它们接到的任务通常还没有 schema。
  • 第 (2) 条是最狠的一条，它承认了状态式路线的根本脆弱性：投影是不可逆的。压缩式系统里，一条当时没看出重要性的信息还躺在未压缩的 tail 里，后面可能被用上；SKILL.state 里，它在第一步就被丢了。「事后才知道重要」这件事，是投影范式无解的。
  • 第 (3) 条对应我研究 §17.7「压缩不销毁数据」那条共识。十一家都保留原始数据（append-only session tree、soft archive、双可见性、事件溯源）。SKILL.state 的 Σ 不是日志，要留档得另建一套。
还有一件论文明明占优、却没测的事 延迟。全文没有任何 wall-clock 数字。但 prompt 从 36,362 字符降到 1,905 字符，TTFT 几乎必然大幅下降——而长程 agent 的体感成本主要就是延迟。 论文的 Introduction 第一段甚至把 latency degradation 写成了它要解决的问题之一，然后一个延迟数字都没给。这是它自己漏掉的一个优势。

今天能抄什么：混合架构

这篇论文最好的用法不是「照着换掉你的运行时」，而是把它的洞察拆下来，插进你已有的压缩系统里。因为它证明的那件事，其实是可以按字段增量采用的。

按投入产出比排序的六条动作

自测 · 来源 · 口径

读完了检查一下

八道自测题

SKILL.state 每一步给模型看的三样东西是什么？哪一样是可变的？
P（技能说明书，不变）、Σ_t（结构化执行状态，唯一可变的那个）、O_t（最新一条观测）。之前的推理、动作、观测一律不进 prompt。
模型每步产出三样东西，它们的去向分别是什么？
R_t 推理 → 验证通过后永久丢弃；ΔΣ_t 状态补丁 → 确定性校验后合并进 Σ；a_t 动作 → 交给环境执行。 关键在第一条：步内推理是完整的，但它不跨步存活。
论文的 O(1) 单步结论，前提是什么？这个前提被验证过吗？
前提是 |Σ| 本身有界 —— 而论文没有任何一处论证或测量它。

它自己的 CTF schema 里，discovered_flags 与 tested_hypotheses 都是只增列表； 而 tested_hypotheses 恰恰是论文归因 CTF 提升的那个字段 —— 它的价值就来自「什么都不忘」，所以按设计就会越来越长。

Warehouse 上那条水平线是环境给的（500 个格子，只有覆盖与删除，没有累积字段），不是方法给的。 正确说法是：SKILL.state 把「上下文会不会爆」从运行时问题变成了 schema 设计问题 —— 是进步，但不是自动保证。
论文说自己把 O(T²) 降到 O(T)。这个说法对压缩式系统成立吗？
不成立。O(T²) 只对完全不压缩的 ReAct 成立。任何做了压缩的运行时，单步 prompt 都被窗口 W 卡住，累计是 O(T·W)——同样是线性。 SKILL.state 与生产系统的差距是常数（W 从 ~30,000 token 降到 ~500），不是阶数。这个常数值 16–40 倍，很大，但不是「二次降一次」。
预算对齐实验里，LLMLingua 掉到 0.22 的原因是什么？它对应我压缩研究里的哪条共识？
统计熵过滤删掉了「看起来冗余、语义上却至关重要的槽位标识符」。 对应 §17.2「保留精确标识符是共同焦虑」——十一家都在摘要 prompt 里写死「逐字保留路径 / ID / 错误码」。 当时这条只有源码一致性作为证据，这篇论文提供了反证：不这么做会掉到 0.22。
为什么说这套架构把「信息存活」从概率问题变成了程序问题，同时也变成了单点？
压缩式系统里，摘要漏了一条约束，还有未被压缩的 tail 兜底，失效是渐进的； SKILL.state 里，一个 key 被 null 掉就是真的没了，没有第二份拷贝，失效是二值的。 实证：开源权重模型 68% 的错误正是「误删了本该保留的 key」。
prompt cache 有一条门槛。它为什么恰好卡死 SKILL.state？
缓存要求可缓存前缀达到最小值（ADK 文档：Gemini 2.5 是 2,048 token，Gemini 3 是 4,096），低于它一个 token 都不缓存。

SKILL.state 的稳定前缀只有 P（~350 token），永远够不着；ReAct 的 prompt 在第 24 步就越过门槛，此后每步命中。 于是 Warehouse T=100 的倍率从裸 token 的 19.0× 掉到 3–8× 区间（精确值取决于论文未公开的 input/output 拆分）。

反直觉之处：让 SKILL.state 便宜的那个性质（prompt 极小），正是让它拿不到缓存折扣的那个性质。 设计上的推论不是「把 P 灌水到 4,096」，而是：让 P 加上 Σ 中逐字不变的前导部分合起来越过门槛 —— 稳定 key 顺序、把 Σ 切成 immutable / mutable 两区、immutable 区排前面。
论文自己承认的三种失效情形是什么？其中哪一条排除了 coding agent？
(1) 事先没有固定 schema、结构必须动态发现；(2) 正确的更新依赖某条当时未识别出相关性的更早观测；(3) 任务目标定义在历史轨迹本身之上（审计、provenance）。 第 (1) 条就是 coding agent——「修复这个仓库的登录 bug」没有事先可写的 schema。我研究的十五个平台里有八家主场在这里。 第 (2) 条最狠：它承认投影是不可逆的，「事后才知道重要」这件事投影范式无解。
如果今天要把这篇论文用进一个已有的压缩系统，第一步做什么？
把任务状态（TODO / 当前目录 / 打开的文件）从摘要通道里拿出来，改由运行时从活数据源每步重新挂载，并禁止摘要器转抄。 这不需要改架构，只是把一个字段换个来源；kimi-code 对 TODO 已经这么做了。 判据是一句话：凡是你能写出稳定字段名的东西，都不该经过摘要器。

本页经过两轮 review。下面逐条列出改了什么、为什么 —— 其中八条是我原来写错或写过头的。

原来的说法问题现在的说法
缓存折算：19.1× → 6.8× 漏掉了最小可缓存前缀门槛。Gemini 3 是 4,096 token（ADK 文档），SKILL.state 的 ~350 token 前缀根本够不着 重算为区间；并指出让它便宜的性质正是让它拿不到缓存的性质
重算后的 3.3× 论文没有公开 input / output 拆分（指标只有 total token burn），而缓存只折扣 input。把输入估算当总成本比，等于让 output 从账上消失 改成敏感性区间 3–8×；3.3× 其实是下界不是中点
把 Gemini 门槛与 0.1×/1.25× 计价混用 不是同一个 provider 的价目表；Gemini 的 context caching 另有创建与存储计费 明确声明为通用形态的敏感性分析，不冒充任何单一 provider 的账单
「P 必须自己超过门槛，所以要故意写大」 公共前缀不一定在 P 末尾断掉，它可以延伸进 Σ 中逐字不变的前导部分；刻意 padding 还会抬高首次成本与延迟 改成稳定前缀：稳定 key 顺序 + immutable/mutable 分区 + 真不变的内容本就该进 P
「τ-Bench Retail 上 ReAct 可能反而更便宜」 该 benchmark 两边都够不着门槛（705 / 831 token），谁都拿不到缓存 已撤回；那三格论文的裸 token 比较基本成立
「两个字段只增」「收益恰恰来自只增性质」 论文只公布了五个字段名，没公布类型与更新策略；对 CTF 的归因是 hypotheses 和 flags 两者，且无字段消融。我把推断写成了事实 改成条件式：固定 schema 不约束字段值长度；若 append-only 实现，则 O(1) 不成立

「Limitations 第 (1) 条 = coding agent」 论文自己就用固定 schema 跑通了两个 coding 环境；被排除的是状态结构需动态发现的任务，不是 coding 这个类别 收窄到开放式 coding/debugging 中 schema 事先写不出来的那部分

  • 本页不修改那篇研究的任何既有结论。它补充的是「效果评测」一节里此前空着的一格：不压缩（状态外置到底）那条路线的量化证据。
  • 那篇研究 §20 的设计清单第 23 条「把状态外置而不是压缩」，此前只有 Antigravity 的架构取向与 OpenClaw memory flush 作为间接证据。本页第 5 节的 0.94 vs 0.52 是这条目前最强的实证，但要连同第 10 节的预算口径问题一起读。
  • 那篇研究 §2.11「压缩与 prompt cache 的根本张力」与 §12.7（ADK 记录的最小可缓存前缀）在本页第 9 节合并成一条新判断：缓存维度上的排序是 ReAct > 压缩式 > SKILL.state，与裸 token 的排序正好相反。论文未涉及这一维。这一节经过两轮更正（门槛、input/output 拆分、稳定前缀的构成），最终结论只保留到「量级从近二十倍降到个位数倍」这一层，详见文末更正记录。
