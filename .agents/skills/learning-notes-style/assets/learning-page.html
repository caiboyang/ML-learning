一次请求里有什么
从结构到变化

用同一份请求观察数据的位置和更新。本页展示布局与组件，所有字段都是教学构造；使用时替换为研究对象的真实结构与证据。

读者前提
知道请求与响应的区别
学习结果
指出哪些字段改变、哪些保持不变
证据范围
教学构造，不代表具体产品

主线：先定位，再追踪变化

先拆开请求 R1，区分稳定设置与任务输入；再观察下一次请求 R2，判断一次追加改变了什么。

阅读路径

  1. 请求由哪两部分组成？

    画出包含关系，找到每个字段的位置。

  2. 追加输入后，哪里发生变化？

    用同一对象的前后值核对结论。

01

请求由哪两部分组成？

读完能指出：设置与输入属于同一次请求，但承担不同职责。

先看包含关系，再读字段值。

示例把请求 R1 分成设置和输入两部分。设置保存语言偏好，输入保存本次要处理的任务；外层编号标识这一份请求。

设计取舍

把设置和输入分开便于解释各自的来源。这个分组本身不能证明系统会缓存设置，也不能证明传输成本下降。

展开字段示例 
{
  "id": "R1",
  "settings": { "language": "zh" },
  "input": { "task": "解释边界条件" }
}

位置明确后，下一步观察用户追加一个要求会改变哪些字段。

02

追加输入后，哪里发生变化？

读完能依据前后值解释变化，避免从表面相同推断实现机制。

用户接着要求“给出一个反例”。教学示例用 R2 表示下一次请求：语言偏好仍为中文，任务文字增加了这个要求。

表 1 · R1 与 R2 的构造值，窄屏可左右滚动
字段R1R2
settings.languagezhzh（未变）
input.task解释边界条件解释边界条件，并给出一个反例（改变）

反例：值未变，不等于无需发送

这份表只比较数据值，没有展示实际传输。因此不能单靠它判断设置是否被再次发送。

自测：这张表能证明缓存命中吗？

先说明已有证据，再指出还缺少什么。

查看答案与推理

不能。表中只有两个字段的前后值；判断缓存行为还需要对应实现或运行证据。相同的值可以来自重新发送，也可以来自其他机制。

回到整体：先用结构图找位置，再用前后对照追踪变化；机制结论需要另外核对证据。
