# 学习笔记写作

把材料组织成读者能一步步理解、解释和应用的学习路径。以用户当前的目标、已有知识和范围要求为准；默认中文讲解，保留必要的英文术语、接口名与源码符号。

## 1. 先读背景，再决定讲什么

动笔前完成以下阅读，避免看完目录就开始拼接段落：

- 回看本次任务的对话、反馈和范围变化。区分持续有效的偏好与已被后续要求修正的判断。
- 阅读仓库说明、相邻专题的学习入口和参考手册。理解它们的读者前提、叙事顺序、页面样式、导航与引用方式。
- 熟读用户给出的文章、论文、视频材料或源码中与任务相关的完整论证和执行路径。不能只读摘要、搜索片段、函数名或评论中的转述。
- 沿关键引用和调用关系追查结论的依据。源码研究检查调用方、数据结构、条件分支与相关测试；遇到关联旧文的冲突，核对并解释差异。

完成一份简短的研究摘要：研究对象、核心问题、主要机制、证据入口、尚未确认的边界。只有能用自己的话串起主线，并为关键结论找到依据，才进入正文写作；缺失材料可以先明确留白，同时继续不依赖它的部分。

对可能变化的实现记录仓库、版本或提交 SHA、核对日期，源码引用优先使用固定提交的具体位置。区分以下层次，在相关结论附近说明：

- **来源事实**：材料或源码直接支持什么，在哪些配置与条件下成立。
- **综合解释**：从机制推导出的意义，推导依据是什么。
- **实践建议**：推荐怎样取舍，还需要什么验证。

代码中存在、默认启用、某个产品实际部署和服务端内部实现是不同结论。看不到的部分不能用客户端代码补成事实；教学示意、构造数据与真实运行结果也要明确区分。

## 2. 明确读者与学习结果

在研究摘要后，用几句话写清：

- **读者已知什么**：概念、语言、系统或实践经验。不要把用户已知的内容重新设为主要课程。
- **这次要学会什么**：用可验证的动词表述，例如画出输入结构、追踪一次状态变化、解释某个设计取舍、完成一个实验。
- **范围与重点是什么**：重点决定深度，不自动删除题目中的其他必要组成部分。标题、目录和正文范围必须一致。

例如，用户要求“分析 Codex harness，重点是上下文与压缩”，且已经懂 harness，就直接讲 Codex 的构造；指令、Skills 和 MCP 如何加载仍需要在整体中有位置。

优先从已有对话和材料推断。若缺失的前提会实质改变教学路径，提出一个具体澄清问题，并继续独立的背景研究；否则简短说明合理假设后推进。大纲是工作产物，不默认增加一次等待批准的流程。

## 3. 先做教学大纲，再写正文

先给出简短大纲，让用户能看出整体教学思路。按理解依赖排列章节，而不是按源码目录、搜索结果或研究过程排列。

采用 **整体地图 → 分部分解释 → 回到完整过程与取舍** 的主线。系统分析通常先展示构成和边界，再追踪具体对象的来源、运行变化与恢复；数学或算法专题则从问题、直觉走到推导和实验。章节数量随主题调整。

用下面的结构检验大纲，各栏内容必须互相支持：

| 章节要回答的问题 | 承接的已知内容 | 核心图或具体例子 | 学完能完成的动作 |
|---|---|---|---|
| 用问句说明本节必要性 | 来自读者前提或上一节 | 说明图和案例实际展示什么 | 解释、预测、追踪、比较或验证 |

每章只推进一个核心问题；结尾用一句过渡说明下一章为什么必要。先解释内容如何产生，再解释如何管理、压缩或恢复它。术语在需要时解释，不单独堆一章词汇表阻断主线。

长专题可沿用本仓库的两层交付：

- **学习入口**：提供顺序、整体图、关键机制、案例与练习；深入细节可展开或跳转。
- **参考手册**：提供完整调用链、公式、字段、来源与适用条件，按同一主线组织，便于回查。

短笔记保持一份即可。不要为了套模板生成空章节、重复报告或固定数量的步骤。

## 4. 用图展示学习对象

优先用结构图、前后对照和表格承载关系、位置与变化，再用短段落解释原因。图必须回答一个具体问题；只有模块名的装饰卡片不能代替解释。

| 要理解的东西 | 适合的表现方式 | 必须看得出的信息 |
|---|---|---|
| 整体系统 | 架构图 | 模块职责、边界、数据与控制的方向 |
| 一次请求或数据结构 | 有序剖面、布局图 | 包含关系、位置、类型、来源、条件项 |
| 执行与协作 | 时序图、步骤轨迹 | 谁在何时读取、产生或修改什么 |
| 状态更新、压缩与恢复 | 同一对象的前后快照 | 哪些保留、删除、重建，哪些信息已丢失 |
| 实现差异与选择 | 对照表 | 相同问题下的不同机制、收益和代价 |
| 参数改变造成的影响 | 曲线或交互演示 | 控制变量、变化方向、阈值及假设 |

讲 context/history 时，不能只有执行流程图。要画出**模型可见输入的顺序、role、内容类别、来源**，并分开程序状态与持久化记录；标明按条件出现的槽位、视觉分组和真实协议项的区别。其他主题也应让图呈现被解释对象本身。

同一个对象在不同图中沿用名称、编号和颜色；图例不能只靠颜色区分。简化图应就近说明省略了什么，避免让示意顺序冒充实现事实。

当切换阶段、实现或参数能揭示变化时使用交互；静态图足够就保持静态。交互应有默认可读状态和明确标签，展开内容不能藏起理解下一节必需的前提。

## 5. 用贯穿案例和贴切类比讲机制

为多阶段主题选择一个具体、足够小的任务贯穿全文。固定输入、对象标识和成功条件，随着章节推进更新同一个案例，最后走通完整链路。不要每节换一个故事，或只在开头提到案例。

例如分析 coding agent，可以以“修复运费边界测试”为**教学构造**：展示初始要求和规则、失败的工具输出、代码修改、压缩前后历史以及恢复后的待办；让读者判断某条约束现在来自哪里、下一步应该验证什么。示例中的 PASS 不代表已经运行测试。

类比按读者已有知识选择：

- 对工程师，可以用熟悉的数据结构、运行时机制或具名 harness 的实现对照来解释新对象。
- 对缺少相关经验的读者，可以用生活例子先建立直觉，再落到真实机制。
- 写清类比双方哪些部分对应，以及在哪一点不再成立。若类比需要比原机制更多解释，换例子或直接展示真实对象；不要强制每节加入生活比喻。

实现比较按 **共同问题 → 具名实现的做法 → 当前实现的做法 → 收益、代价与适用条件** 展开，为双方提供来源和版本范围。不要用“多数 harness”“别家都这样”“最先进”替代证据，也不要把可选框架组件视为每个产品的默认行为。

解释值得学习的设计时，给出具体反例或状态变化：不用这个机制时哪里会出问题，它怎样改变结果，又引入什么成本。设计动机需要来源或推导；架构上的合理性不能直接证明速度、成本或模型效果更好。

## 6. 写成可以顺着读懂的正文

每节围绕一个问题展开：先交代问题和结论，再配图与案例解释机制，接着说明条件和取舍，最后承接下一节。按需要组合这些元素，不强制重复同一版式。

- 用明确的主体和动作解释技术：谁读取了什么、写到哪里、何时再次使用、条件变化会怎样。符号和源码入口跟在解释后面。
- 用短段落、比较表、清晰的局部导航降低阅读负担；必要的推导和证据保留在就近展开区或手册。
- “说人话”不等于改成强断言。发现实现使用某个阈值，可以解释计算过程，不能据此编造“否则必然死锁”的原因。
- 自测尽量让读者读图、预测下一步、追踪约束、解释边界情况或做选择。答案说明推理过程，不只要求背术语。
- 沿用周围页面的字体、色彩、目录、引用和展开样式。先修教学顺序与解释缺口，再考虑视觉装饰。

## 7. 验证理解路径与交付

完成后从读者入口重新走一遍，核对：

- **范围与顺序**：只看标题、大纲和主要图，是否能复述整体；每节需要的知识是否已经建立；题目中的重点与其他必要部分是否都覆盖。
- **案例与练习**：同一任务的输入、标识和结果是否前后一致；能否根据本节内容回答练习；示意是否被误写成真实运行证据。
- **来源与语义**：关键结论是否由引用直接支持；调用链、条件与版本是否相符；学习页、手册、关联旧文有没有相互冲突。链接可打开不等于论断已核实。
- **文档与页面**：检查相关链接、锚点、标题层级、图表和代码块。若改了网页，在真实浏览器查看桌面与窄屏，操作新增的切换、展开与导航，检查图的可读性及溢出；启动服务器不算完成页面验收。
- **实验与结果**：有可运行代码时，执行能验证教学结论的示例或边界检查。明确区分静态检查、浏览器验证、真实程序测试、模型效果评测和部署状态。

收到评论后先读取最新内容与当前文件或 PR 状态，再按用户目标和证据逐条判断。采纳成立的部分；不成立或只部分成立的建议要解释依据，不能为了 resolve 接受错误结论。回复、resolve、提交和发布按用户已有授权执行，本 skill 不额外授予外部操作权限。

交付时简短说明学习入口、教学顺序、主要图与案例，以及实际做过的验证和剩余缺口。只更新本次任务相关文件；范围变化后同步标题、目录、README 入口及已授权的 PR 描述。
