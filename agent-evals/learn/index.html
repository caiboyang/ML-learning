不再凭感觉
调 Agent

你的 agent 说「已经完成」，dashboard 也给了 100 分——但数据库里什么都没发生。 这篇从这个错误现场出发，十步建立一条能回答测什么、谁来判、为什么失败、能不能发布的证据链。

本篇唯一主线： Eval 不是一个分数，而是一条可以回钻的证据链—— Task → Trial → Transcript + Task Result → Graders → Decision。 任何 aggregate 如果回不到具体任务、具体运行和具体证据，就只能制造确定感，不能制造可靠性。

STEP 01

先看一次「100 分」的失败

The score is right. The eval is wrong.

最危险的不是 agent 失败，而是失败被 grader 判成成功。

假设你在评一个退款 agent。evaluation harness 的私有 fixture 已标明：用户身份已验证，订单 123 可退 42 美元；用户明确说：「Please refund order 123.」运行结束后出现三份证据：

这个例子揭示 eval 的第一原则：模型输出只是一个声明，outcome 才是世界有没有真的改变。 能查数据库、文件、API、浏览器状态时，不要让 agent 自己宣布成功。

四类问题
Agent failure：没完成任务。
Task / spec failure：题目歧义、要求互相冲突或正确答案不可达。
Grader failure：把坏结果判成好结果。
Evaluation harness / infrastructure failure：fixture、权限、超时、资源或残留状态让实验本身失真。
一个总分不会告诉你是哪一类。

普通单轮 LLM 常能用 prompt → response → score 表示；agent 会跨多轮调用工具并修改状态， 早期错误还会向后传播。于是被测对象从一句回答变成了一整段 trajectory + 一个最终 outcome。

来源：Anthropic Demystifying evals for AI agents 对 transcript 与 outcome 的区分；τ-bench 以最终数据库状态评分。
STEP 02

把 Eval 世界的对象摆对位置

Task, trial, trace, outcome, grader, harness

先统一证据链，后面所有工具名才不会把你带偏。

Agent harness
让模型能行动的系统
prompt、tools、循环、上下文、权限、重试与停止条件。所谓「评一个 agent」，实际在评 模型 × agent harness。
Evaluation harness
让实验能重复的系统
准备 fixture、启动 trial、保存 trace/output/outcome、运行 graders、聚合结果。框架能帮你跑，但不能替你定义成功。

在 observability 体系里，run 常表示一次模型调用、检索或工具执行； 一组 runs 构成一次 trace；多轮 traces 再组成 thread。 Anthropic 又把一次 trial 的完整记录称为 transcript，也承认 trace / trajectory 常被当作近义词。

迁移工具时别争名字
只问四件事：一次用户任务边界在哪？多轮如何关联？tool result 和最终 state 有没有保存？ grader 实际读到哪一层？粒度对上，术语差异就不重要。
来源：Anthropic 的 Agent eval 词典； LangChain Observability concepts。
STEP 03

把「成功」拆成三层合同

Task result first, obligations second, quality third

不要从“能算什么指标”出发，要从“用户究竟得到什么”出发。

一条 task 至少要写清：

id: refund_order_123
input: "Please refund order 123."
initial_state: fixture/refund_order_123.json  # identity_verified=true, amount_usd=42
success:
  outcome:
    refund_created: true
    order_id: 123
    amount_usd: 42
  obligations:
    authorization_valid: true
    duplicate_refund_count: 0
  quality:
    confirms_amount_and_status: true
slices: [refund, happy-path, should-act]

检查题目是否清楚有个简单标准：两位领域专家能否独立得出相同的 pass/fail？ 再为它写一份已知可行的 reference solution，并让这份解通过所有 graders。 如果 reference 都过不了，先修 task 或 grader。

题面与 Grader 的合同
Grader 检查的要求必须能从题面或明确的产品规范中得知。题目叫 agent 写脚本，却没说路径， 测试却硬编码某个文件名——测到的是猜题，不是能力。

什么时候必须评过程？

不要规定唯一工具顺序，但三类过程义务不能丢：安全/合规、信息依据、资源边界。 「先鉴权再读私有数据」是硬门；「必须先调用 A 再调用 B」若没有业务理由，只是脆弱测试。

来源：Anthropic 对 unambiguous tasks、reference solution 与 grade outcome 的建议。
STEP 04

先做 20–50 道真实题

Small, real, balanced, owned

第一版数据集的价值来自任务真实性，不来自行数。

从你本来就会手工检查的行为、bug、support ticket 和用户常见工作流开始。 Anthropic 给的实际起点是 20–50 道简单题；这足以在早期捕捉大变化。

Hamel 给了一个好用的展开坐标：feature × scenario × persona。 例如客服的 scenario 可包括多结果、无结果、歧义、系统错误与不支持功能； 但没有直接用户交互的 agent 未必需要 persona——它只是发现覆盖盲区的方法，不是标准 schema。

Capability suite
现在能做到多难？
应该保留失败空间，给优化一座山爬。适合模型、prompt、tool 与架构比较。
Regression suite
以前会的现在还会吗？
应接近 100%，下降就调查。已攻克的 capability tasks 应「毕业」到这里。
不要混成一个均分
capability 上升与 regression 下降可能相互抵消，最后 dashboard 显示「整体不变」。 但产品含义完全相反：一个是边界向外推，一个是既有承诺被破坏。
Dev ≠ Holdout
日常调 prompt、tools 与 harness 用可反复读失败的 dev suite；发布结论再用锁定的 holdout 确认。 每次根据 holdout 结果继续调系统，它都会逐渐耗损，因此要限制查看并定期用新案例刷新。
来源：Anthropic 20–50 tasks、平衡集合与 capability/regression； Hamel feature / scenario / persona。 Dev / holdout 是本文的实践扩展，参考 Google 对 validation / test 耗损 的说明。
STEP 05

按判断性质选择 Grader

Code where possible, models where necessary, humans as anchor

最强的 grader 不是最强模型，而是最便宜、最可复现、又刚好能判对这件事的方法。

先判产物，再判路径

任务是「退款成功且不超过 100 美元」，就检查退款记录、金额、身份验证与通知。 不要无理由强制模型按你预想的唯一工具序列行动。合法解法往往不止一条。

对 research agent，一套实用组合是：

维度优先 Grader证据
精确事实numeric / exact / tolerance冻结 reference
Groundednessclaim-source judge检索来源 + final answer
Coveragerequired facts + judge任务要求与参考面
Source qualitydomain rubric来源类型、权威性与时效
效率code metricsturns、tool calls、token、latency
来源：Anthropic 的 code / model / human grader 分类与 agent 类型示例。
STEP 06

让 LLM Judge 先跟着专家学会判

Critique shadowing before scaling

Judge 不是 ground truth；它只是另一位必须参加考试的模型。

Hamel 建议起步用二元 Pass/Fail + 足够详细的 critique。 八个含义模糊的 1–5 分，通常既不能稳定解释 3 与 4 的区别，也不直接告诉你该修什么。 

{
  "verdict": "fail",
  "critique": "回答声称订单 123 的 42 美元退款已完成，但退款工具校验失败，退款表仍为 0 rows。",
  "evidence": ["tool.process_refund.status=validation_error", "db.refunds[order_id=123]=[]"],
  "error_type": "claimed_action_without_outcome"
}

Judge 自己的成绩单

还要报告 Unknown rate 与关键 slices。允许 judge 在证据不足时拒判， 比逼它猜一个确定答案更可靠。

Unknown = Abstention
Unknown 不是第三个质量等级：它进入人工复核，并从 pass/fail confusion matrix 单列； 报告 precision/recall 时还要同时给全体样本上的 Unknown rate。

这里用于调 judge rubric 的 judge-calibration holdout，与 Step 4 用来确认系统发布结论的 system release holdout 是两套数据。先冻结 judge prompt、model 与 rubric，再运行 release holdout；前者不能替代后者。

四种必须专门测的偏差

Position · 交换 A/B 顺序，不一致就进入复核。
Verbosity · 放入短而正确与长而空的对照样本。
Self-enhancement · 隐藏模型身份，必要时换模型族 judge。
Reasoning / injection · 给 reference；把 agent 文本当不可信数据包裹。
Criteria drift
人需要标准才能评分，但看过真实输出后又会修改自己对标准的理解。 因此 rubric 是有版本、靠反例逐步收敛的产品规格，不是一次写完的真理。
来源：Hamel Critique Shadowing； Anthropic 对 Unknown 与多维 judges 的建议； Shankar et al. Who Validates the Validators?； Zheng et al. LLM judge 偏差研究。 留出样本是本文加上的校准护栏，不是 Hamel 原流程的固定步骤。
STEP 07

一次通过，不等于可靠

Trials, pass@k, pass^k, paired comparison

Agent 的基本单位不是一次 demo，而是同一道 task 上一组尽量隔离的重复 trials。

假设某 task 每次成功概率 p = 0.75，跑 3 次：

比较候选 A/B 时，用同一批 tasks、相同环境快照、相同 trial 数。 不只看 81% 与 84%，而要看每道题的迁移：

迁移含义动作
fail → pass候选带来的明确收益读 trace 确认不是 grader 漏洞
pass → fail潜在回归优先按风险与 slice 深挖
pass ↔ fail 随机跳边界任务或环境噪声增加 trials，检查隔离和资源
都失败capability 缺口或坏 task读 reference 与失败 transcript
报告分母和不确定性
写「43/50 tasks；150 trials 中 121 次成功」，并给区间与 slice。 小样本里 82% 对 86% 往往不足以支持「候选显著更好」。
来源：Anthropic 对 pass@k / pass^k 与多 trials 的解释；τ-bench 以 pass^k 衡量可靠性。
STEP 08

总分报警，Trace 定位

Observability provides evidence; eval provides judgment

Agent 的逻辑一半在代码里，另一半只在运行时轨迹里出现。

找第一处偏离，不要只修最后一句

intent → plan → tool selection → tool arguments
       → evidence / state → final response
       → grader inputs → verdict
              ↑
        first invariant violation

如果 tool 已经取回正确证据，最后回答却映射错，修 response boundary； 如果第一步就理解错意图，改最后一句只是在遮盖上游故障。 要找的是最早可观察的不变量违反，把它当作根因分析起点；它不是第一个与 reference 轨迹不同的动作，也不自动证明因果根因。 它还能帮你区分 agent、task/spec、grader 与 evaluation harness / infrastructure 问题。

生产 Trace 怎样变成回归题

三种时间维度
Offline：发布前，冻结数据上做回归与比较。
Online：生产 runs/threads 上做 reference-free 监控与异常发现。
Ad hoc：围绕用户反馈或怀疑的模式，对历史 traces 做探索分析。
来源：LangChain 视频 Observability and Evals for AI Agents: A Simple Breakdown 及其 官方文字版； LangSmith Evaluation concepts。
STEP 09

先做一个没有平台依赖的最小 Harness

Clean environment, immutable artifacts, replayable graders

第一版需要的是闭合证据链，不是 dashboard、插件系统与无限配置。

运行顺序只有六步：

for task in dataset:
    for trial in repetitions:
        env = make_clean_environment(task.fixture)
        trace = run_production_agent(task.prompt, env)
        output = collect_output_or_artifact(trace, env)
        outcome = snapshot_outcome(env)
        grades = run_graders(task, trace, output, outcome)
        save_immutable_artifacts(trace, output, outcome, grades)

compare_with_baseline()
report_per_task_and_slices()

每次 trial 必须保存：

  • model/provider、prompt、tools schema 与 agent harness commit；
  • dataset、grader 与环境 fixture 版本；
  • 完整 transcript、output/artifact、outcome snapshot 与每个 grader 的证据；
  • turns、tool calls、token、latency、cost 与 runtime errors。
环境隔离不是清洁癖
残留文件、共享缓存、git history、CPU/RAM 不足和资源耗尽都会制造相关失败或虚假优势。 如果 trials 不独立，你测到的可能是基础设施，不是 agent。
隔离 Eval Control Plane
整个 evals/ 都不得挂载进 trial workspace。Harness 用 fixture 初始化环境；agent 只能通过与生产一致的 tools / API 观察环境，不能读取 raw fixture。 Expected state、reference、grader、judge rubric 和 holdout 标签都留在控制面，否则会把「会完成任务」测成「会读测试」。

Grader 应能在保存的 artifacts 上独立重跑，这样改 rubric 时不用重新付一遍 agent 运行成本， 也能把「agent 变了」与「grader 变了」分开。

来源：Anthropic 对 stable isolated environment、完整 transcript 与 grader maintenance 的建议。目录与伪代码为本篇实践模板。
STEP 10

七天闭环，然后让 Suite 活下去

Eval-driven development, not eval theater

一套小而有人维护的 eval，比一套华丽但没人读失败的 dashboard 更可靠。

看到这些信号就停下来

只展示平均分，回不到 task 和 transcript。
Judge 从未与专家比较，却被当作 ground truth。
只测应该行动，从不测应该克制。
固定唯一工具路径，把合法解法判错。
Trials 共享环境，状态泄漏或相关失败。
Suite 永远 100%，却没有更难的 capability 题。
换了模型或 rubric，judge 不重新校准。
线上 trace 自动入库，没有确认、脱敏与冻结。

十问自测

1. Agent 最后说“已退款”，能直接判成功吗？

不能。应检查退款系统的最终状态；文本只是一份声明。

2. Agent 用了与预期不同的工具顺序，但结果正确，应该失败吗？

通常不该。优先评 outcome；只有安全、合规或业务义务要求具体过程时才设 hard gate。

3. 什么时候应该用 LLM judge？

确定性方法不足以判断的开放语义维度，例如 groundedness、完整性或语气；并且必须用专家样本校准。

4. Judge 与专家 90% agreement，就一定可靠吗？

不一定。还要看样本量、类别基准率、fail precision/recall、confusion matrix、unknown 与关键 slices。

5. 为什么同时需要 should-act 和 should-not-act？

只测一个方向会优化成极端策略，例如逢问必搜或什么都拒绝。

6. pass@3 很高，能证明客服 agent 很可靠吗？

不能。pass@3 只问三次里至少一次成功；客服更关心多次都成功的 pass^k 或 task-level reliability。

7. Observability 和 Eval 是同一件事吗？

不是。Observability 记录发生了什么；Eval 用任务与标准判断好不好。Trace 是证据，不自动是 verdict。

8. 一条生产 bad trace 可以自动进入 regression suite 吗？

不应自动进入。先由专家确认、脱敏、冻结依赖、补成功标准与 reference，并验证旧版红、修复版绿。

9. Capability suite 100% 是好消息吗？

对回归保护是好消息，对继续衡量进步则已饱和。把已攻克题转入 regression，再补更难 capability 题。

10. 一次分数变化至少应能解释到哪一层？

具体 task、trial、transcript、output/outcome、grader evidence，并区分 agent、task/spec、grader 与 evaluation harness / infrastructure 故障。

完成标准
不是「接上了一个 eval 平台」，而是：任何分数变化都能指出哪些真实任务发生了什么变化； 失败有 transcript、output/artifact 与 outcome 证据；judge 经过人类校准；候选与基线在同一环境配对比较； 发布决定能说明证据边界与已知未知。
