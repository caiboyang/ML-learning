    03.1

    How Codex selects and assembles base instructions

    Configuration priority + ModelMessages + provenance + wire branches

    Why does opening prompt.md in the repository still not identify this request's base instructions?

    Codex implementation takeawayModelMessages includes tool descriptions, approval wording, and mode messages in model metadata. Custom / Model provenance prevents model defaults from being mistaken for user overrides.

    Implementation comparison: LangChain's system_prompt accepts text or a SystemMessage; middleware can supply dynamic prompts. Codex embeds configuration, inheritance, model-catalog, and Custom/Model provenance handling in the client. The difference concerns lifecycle responsibility, not merely where a string lives. Comparison source ↗

    Design analysis · Save who the text came from

    Benefit: Custom / Model provenance protects user overrides while allowing a new model to use its own default template.

    Cost / boundary: Old history without provenance permits only limited inference; similar text cannot recover the user's actual intent.

    Self-check: does restoring an old session after a client update necessarily use the repository's latest default prompt?

    No. Without an explicit override, saved session base instructions take priority over the current model template. Inspect the actual model catalog and inherited session state too.

    Expand the source walkthrough and orders test example

    Finding a prompt.md on GitHub does not determine what a session uses. Session initialization chooses base instructions in this order, stopping at the first available source:

    1. 01Explicitly configured base instructions, including resolved instruction-file contents
    2. 02session_meta.base_instructions saved in restored or forked history
    3. 03The current model catalog's instructions_template

    The model catalog has a compiled-in version as well as remote metadata and a disk cache. model_instructions_file replaces the base source; developer_instructions is a separate path for additional content.

    ModelMessages also places tool descriptions, approval wording, mode messages, and budget hints in model metadata, so capability and behavior text can evolve together. Missing fields have their own built-in fallbacks; this does not mean prompts exist only on the server.

    When the same task switches from model A to B, which instructions should stay and which should change?

    Suppose the task changes models midway. The difficulty is deciding whether the text was chosen by the user or supplied as model A's default, not copying the string.

    • Custom: User-selected base instructions remain a user override after the switch.
    • Model { A }: A's default instructions should not prevent B from using its own template; configuration construction filters out this old-model override.
    • Unknown source: When old history cannot establish provenance reliably, the text cannot simply be treated as a replaceable default.

    Provenance metadata preserves evidence for this decision. New instructions may also enter history as model-switch developer messages; this does not directly rewrite the persisted SessionMeta base text into B's template.

    A further distinction · The wire structure can change tooStandard Responses uses top-level instructions and tools. A model branch with use_responses_lite puts base instructions in a developer message and tools in AdditionalTools ahead of input.

    So whenever someone says “system prompt,” ask whether they mean the server-side system layer, client base instructions, or developer/user context in history. These are different fields.

    MCP: from configuration to PreparedMcpCall

    runtime → initialize / list_tools → binding → exposure → call

    If a server is connected, why might tools still need discovery? Why check the binding again before a call?

    Codex implementation takeawayThe catalog binding used for sampling and the prepared execution binding are adjacent boundaries. Ordinary sources use Eager; a SubAgent's LazyWhenCached also requires the relevant cache conditions.

    Implementation comparison: OpenHands discovers tools from mcp_config during initialization and wraps them as MCPToolDefinition. Codex also distinguishes deferred connection, schema exposure, and PreparedMcpCall along this chain. Diagnose discovery, visibility, and execution binding separately. Comparison source ↗

    Design analysis · Maintain catalog visibility and call binding separately

    Benefit: Deferred exposure reduces resident schemas; call preparation binds the client and metadata for this execution.

    Cost / boundary: Search, connection, and invocation can fail independently, so diagnosis must locate the stage.

    Self-check: why might the model still need tool search when issue-tracker is connected?

    Connection handles communication with the server; search brings deferred definitions from an existing catalog into the model's available tools. They reduce different costs at different times. Search is not execution either.

    Expand the source walkthrough and orders test example

    Continue this teaching branch: suppose order rules must also be queried from a configured issue-tracker MCP. The Skill supplies the workflow; MCP supplies external actions. A plugin can contribute both, but they follow different loading chains.

    1. 01Gather server configurations from the session, plugins, and selected environment; apply policy constraints
    2. 02Connect over Stdio or Streamable HTTP and negotiate capabilities with initialize
    3. 03Fetch the tool catalog and metadata in pages, then construct an MCP binding
    4. 04ToolRouter combines built-in, extension, and dynamic tools to choose exposure for this request
    5. 05After the model proposes a call, check refresh state, prepare the binding, then handle approval and execution

    This is the ordinary connection path. The source also supports cached catalogs, prewarming, and conditional lazy initialization. Ordinary sources use Eager; SubAgent sources select LazyWhenCached, subject to cache and implementation conditions. Seeing a catalog does not prove that the server has finished initializing.

    04.1

    What run_turn does around each sampling step

    Input contributions → capture StepContext → sample → execution and budget checks

    Within one user turn, where does Codex prepare another request, receive input, and check for compaction?

    Codex implementation takeawayrun_turn decides whether execution continues; StepContext constrains the sampling plan. The MCP handler separately refreshes and captures PreparedMcpCall before execution. These bindings are not one permanent snapshot.

    Implementation comparison: OpenHands records model actions as ActionEvent and observations as ObservationEvent; Codex records calls/results as separate ResponseItem values. Both must preserve call associations. Tool-calling ability alone is not a structural difference. Comparison source ↗

    Self-check: does StepContext guarantee that the MCP catalog and connections never change after sending the request?

    No. It fixes the sampling plan. MCP still checks refresh state and prepares the current call before execution. The model having seen a definition and the call actually succeeding are separate facts to verify.

    Expand the source walkthrough and orders test example

    In this example, the agent reads code, runs the test, sees FAIL, then decides what to change. run_turn writes each tool result to history and asks the model for the next step. The loop continues while execution or pending input requires it. All these sampling steps and tool executions can occur within one user turn.

    Why prepare StepContext before each sampling step? Reading changing configuration separately while assembling one request could mix versions of tool definitions, environment, and rules. The snapshot supplies a consistent sampling plan. It does not lock external services: MCP still refreshes and obtains PreparedMcpCall before execution. Sampling-plan consistency and execution-time connection binding are separate boundaries.

    Self-check: with a 250k configured budget, does this example wait until 250k to compact?

    Expand the source walkthrough and orders test example

    Why not wait until the window is full? Summarizing compaction must construct another model request that fits both history and summarization instructions. Earlier triggering leaves some room, but the source's 90% threshold does not prove that every path needs exactly 10%, or guarantee success. Some overflow paths prepare input or retry; TokenBudget does not automatically call a model to summarize.

    The program decides when to compact. Counting combines the latest server usage report with estimates of subsequently added local content; the local estimator is not an exact tokenizer.

    Remote V2: compaction as a protocol action

    The server returns an opaque compaction item; the client validates, saves, and supplies it in later requests. The client need not implement the internal compression algorithm, but cannot directly inspect which facts it preserves.

    Codex request deltas and cache boundaries

    previous_response_id / stable prefix IDs / prompt_cache_key

    What can delta-only transmission, stable input IDs, and shortened history each prove?

    Codex implementation takeawayInstalling replacement history usually breaks strict extension of old history. Appending a V2 trigger helps preserve a prefix, but does not guarantee cache hits throughout compaction.

    Implementation comparison: LangChain lists provider caching as separate middleware. Here too, distinguish transport deltas, stable prefix identity, and cached tokens. Client structure establishes reuse conditions, not guaranteed hits. Comparison source ↗

    Self-check: if a network log shows only tool results in the second transmission, has the model lost the original requirement?

    Not necessarily. When delta conditions hold, the server continues accepted input through the previous response ID. Inspect the complete logical request, not just this transmission's delta.

    Expand the source walkthrough and orders test example

    A request can use delta transport, prefix caching, and compacted history together. Their units are transmitted bytes, reused computation, and active-context tokens; observe them separately.

    MechanismLayerWhat it primarily reducesWhat does not follow
    Prompt cacheServer-side computation reuseRepeated-prefix computation; benefits depend on hits and server policyReusing computation does not remove input or free the context window
    WebSocket deltasNetwork transportAvoid resending an accepted history prefix when conditions holdSending less does not mean seeing less: the server continues prior context, so visible input cannot be counted from the delta alone
    CompactionActive contextRewrite or reset history to reduce later inputShorter does not mean lossless or guaranteed cache hits; truncation and selection also reduce input

    The current WebSocket path supports previous_response_id: deltas are allowed when request properties match and input extends the prior request plus output. The older claim that Codex does not use previous_response_id does not apply to every path in this snapshot.

    A Remote V2 request that appends a trigger may preserve the original prefix. But pre-compaction preparation, tool changes, and model switches alter those conditions; replacement history after compaction usually no longer strictly extends the old history.

    Lite prefix IDs derive from UUIDv5(thread namespace, payload bytes). This stabilizes identity across retries in one task, but does not prove a cache hit. store:false also does not exclude temporary WebSocket connection state. In the example, appending ΔR may preserve the old prefix, while installing snapshot C rewrites history; the cache conditions differ.

    Inference boundaryCompression ratio is not task quality, and neither is cache-hit rate. Also record task completion, constraint retention, repeated actions, tokens, and latency.
