STEP 01

先划清模型和 harness 的边界

谁提出动作，谁执行动作，谁保存状态

朋友只说：周六来你家吃饭。谁把这句话变成一桌菜？

这一幕记住模型提出“去买菜”，harness 把请求交给工具，拿回实际结果；说过要做，不等于已经做完。

代码案例：修复“满 100 免运费”。提出改代码 → 工具修改文件 → 运行测试，三步都要走。

自测：模型说“测试已通过”，harness 就可以把任务标为成功吗？

不能仅凭这句话。应检查工具是否执行、输出和退出状态是什么；模型陈述与环境结果是两份证据。

展开源码推演与订单测试案例

你让模型修测试，它回答“改好了”，可本地测试还是红的。怎样让一次回答变成一次经过验证的修复？

先想象一张办公桌：模型根据桌上收到的材料提出下一步，harness 负责把请求交给工具执行器，再把结果送回桌面。模型写出“运行测试”还不算执行；要等工具真的跑完，才能知道结果。这里的 harness，就是把模型、工具、环境和会话串起来的运行程序。

MODEL

决定下一步

根据当前输入生成回答或工具调用。能看见什么，取决于这次请求。

HARNESS

组织与执行

构造请求、运行工具、处理取消和审批、管理历史与窗口。

ENVIRONMENT

承载实际结果

工作区里的文件、进程和外部服务。它们的状态不会随聊天摘要自动重置。

接下来沿一个订单测试看这套分工怎样运转，源码范围和版本说明见页末及参考手册。

贯穿案例 · 运费边界测试U1 用户请求：“修复 ShippingCostTest：订单金额满 100 免运费；保持 public API 不变。”
R0 项目规则：根目录 AGENTS.md 要求使用 JUnit 5。后文始终追踪这一个任务。代码、消息 ID 和输出均为教学构造，未运行真实项目；工具名称是简写，不是可直接发送的 API。

STEP 02

一条请求为什么会跑很多轮

一个用户回合，不等于一次模型采样

去买番茄，发现卖完了。你得根据新情况重新安排。

这一幕记住一次聚餐任务可以跑很多轮；Session 管整场任务，每次请求只拿到当时准备的材料。

代码案例：读实现 → 跑测试 → 看到 amount=100 失败 → 改比较符 → 再测。新结果推动下一轮。

自测：StepContext 是否保证请求发出后，MCP 目录和连接永不变化？

不保证。它固定采样使用的计划；MCP 执行前仍检查刷新并准备本次调用。模型看到过定义和实际成功执行，是两个需要分别核对的事实。

展开源码推演与订单测试案例

你只交来一张“修好运费测试”的任务单，完成它却可能需要多次往返：读测试 → 读实现 → 改代码 → 运行测试 → 看到新失败 → 继续修改。每次拿回的新材料都会影响下一步。run_turn 在一个用户回合内反复请求模型、执行工具，直到无需续跑且没有待处理输入；这些步骤不是多次独立的用户回合。

每次派发前，harness 会准备一张“本次工作单”，写明可用工具、环境与规则，这就是 StepContext。它为采样时的工具定义、环境和规则提供一致视图。MCP 调用还有执行前刷新与绑定：请求时看到的目录，不保证外部服务到执行时仍完全相同；第六步会展开这个边界。对 Java 开发者，它接近不可变的 request-scoped 对象；这不意味着外部文件和进程也被冻结。

快照 A：测试失败怎样进入下一次请求

当前初始上下文 I0：权限、环境、R0「JUnit 5」
U1：满 100 免运费，保持 public API

call c1：读取 ShippingCost.java
output c1：return amount > 100 ? 0 : 5;
call c2：运行 ShippingCostTest
output c2：amount=100，expected=0，actual=5，FAIL

下一次采样：看到以上历史，决定怎样修复

输出必须与调用共享 call_id。模型看到测试失败，才有根据把 > 100 改成 >= 100；生成修改建议、执行修改和确认测试通过是不同节点。

STEP 03

把 context 拆成三种状态

正在看见、可以重建、已经保存

发票收进柜子了，坐在桌前的你会自动知道每个数字吗？

这一幕记住保存、当前可见、可以重建，是三件事。柜里有记录，不等于模型此刻读到了。

代码案例：旧 FAIL 可能在归档里；WorldState 管规则与环境，不会因此自动备份这段日志。

自测：磁盘还保留完整对话，能否据此断言模型“没有忘记”？

不能。持久化解决的是保存，模型窗口解决的是当前可见性。还需要明确的检索或重注入路径，才能把保存的内容带回当前请求。

展开源码推演与订单测试案例

旧报错明明还在磁盘里，模型为什么又问一次？就像材料收进档案柜后，坐在桌前的人不会自动读到它。用办公桌、规则册、档案柜区分三种状态：

状态例子作用
办公桌上的材料
活跃模型历史		消息、工具调用、结果、reasoning、compaction item组成下一次请求的历史视图
程序保管的规则册
当前 canonical state		权限、AGENTS.md、环境、模式和能力把当前规则与环境复制进请求；变化时通知模型
档案柜里的记录
持久化记录		Rollout、replacement checkpoint、窗口标识用于会话恢复；模型回捞另需可用接口

清理桌面、更新规则册、查档案是三个动作。规则册要被复制进请求，模型才能看到；档案柜也只包含实际保存下来的内容，不代表所有原始输出都完整归档。ContextManager 给桌上的材料保留类型和元数据，才能识别真实用户输入、区分程序注入内容、维持工具的调用／结果配对。

R0 和 U1 都可能属于 role=user，但类别不同：R0 是 agents_md.instructions，U1 的文本是 user.text。注入 fragment 的 content_kind 会随 content 进入内部 wire metadata；合并多个片段时，每个 content item 仍有对应标签。对非 OpenAI provider，发送前会清掉这些内部 metadata。

案例判读 · 同一个 FAIL 的三个位置刚才的 FAIL 可以在活跃历史里，也可能保存在持久化记录中；WorldState 记录规则和环境，不会因此自动备份这段失败日志。稍后重跑测试得到 PASS，也不能还原那次 FAIL 的原始输出。

减小上下文也从工具结果入历史时开始：先限制大输出，发送前再修复配对和处理不支持的模态。你看到的“压缩提示”只是整套 context 管理中的一个环节。

STEP 04

基础指令究竟从哪里来

固定文件、模型目录和会话继承共同决定来源

换人筹办聚餐，“客人忌花生”不能被新人的默认菜单覆盖。

这一幕记住基础指令按来源选取；同时记住它是用户自定的 Custom，还是模型自带的 Model 默认值。

换 A → B：保留用户自定义约定；不能让 A 的默认文本冒充用户覆盖。项目 AGENTS.md 是另一路上下文。

自测：更新客户端后恢复旧会话，一定会采用仓库最新默认 prompt 吗？

不一定。没有显式覆盖时，保存的会话基础指令优先于当前模型模板。还要检查实际模型目录和会话继承状态。

展开源码推演与订单测试案例

你在 GitHub 找到一个 prompt.md，还不能据此确定某个会话用的是什么。Session 启动时按下面顺序选择基础指令，命中前一项就不再回退：

  1. 01显式配置的基础指令，包括指令文件解析结果
  2. 02恢复／fork 历史保存的 session_meta.base_instructions
  3. 03当前模型目录中的 instructions_template

模型目录既有编译打包的版本，也有远程元数据和磁盘缓存。model_instructions_file 替换基础来源；developer_instructions 则是另一条附加内容路径。

ModelMessages 还把工具描述、审批话术、模式消息和预算提示放在模型元数据里，让能力与行为文本可以配套更新。缺失字段有各自的内建 fallback；不能把它理解为“提示词只在服务器”。

同一任务换模型时，哪段指令可以变？

假设换了一个模型接手同一张办公桌。规则册中“用户特意指定的约定”应继续保留，“上一模型自带的默认说明”则不能冒充用户要求，阻止新模型采用自己的默认说明。只存最后那段文字，接手时就分不清这两种来源。

假设任务从模型 A 切到 B：标为 Model { A } 的继承文本不应成为 B 的用户 override；标为 Custom 的用户指令则应保留。系统保存 provenance（来源） 来区分二者，并可通过模型切换 developer 片段提供当前指令。持久化基础文本、请求副本与追加的切换消息要分开看。

特殊之处 · wire 结构也会变普通 Responses 使用顶层 instructions 和 tools。启用 use_responses_lite 的模型分支，会把基础指令作为 developer 消息、工具作为 AdditionalTools 放到 input 前面。

因此，日常说的“system prompt”至少要再问一句：说的是服务端 system、客户端基础指令，还是历史里的 developer／user 上下文？它们不是同一个字段。

完整优先级与 Lite 分支：手册 §7 · 指令加载、Custom / Model 来源

STEP 05

Skills 怎样被发现、选中和读取

目录、正文、引用资源和执行是四个阶段

想做一道陌生的菜：先看目录，选菜谱，需要时再翻附页。

这一幕记住显式点名 skill 时，运行时可以主动注入正文；模型也可以先判断相关，再自行读取。

菜谱可能在家里、另一处厨房或远程资料库，对应 Host / Executor / Orchestrator；读取要走各自来源。

自测：目录里已有 order-tests，能否断言模型读过正文、依赖也已安装？

不能。目录、正文、依赖安装和执行分别有入口。显式选择可能触发正文注入，但 MCP 依赖安装还受 feature、来源、策略与安装选择等条件约束。

展开源码推演与订单测试案例

现在给运费测试案例加一条教学分支：用户显式选择 $order-tests，一个说明如何补边界测试的假想 skill。模型怎样获得它的说明？先要区分来源，再区分谁触发读取。

来源发现入口读取边界
Host配置 roots、用户与仓库 .agents/skills、系统和插件目录通过相应文件系统读 SKILL.md
Executor所选执行环境的能力快照或目录在所属环境读取，校验 package 归属
OrchestratorMCP 中标为 mcp/skill 的资源通过资源接口读取；有单独启用条件

通常先放到办公桌上的是技能目录：名称、描述和来源。扫描器可能已经读过文件来提取元数据，但模型还没有收到整篇正文。目录有预算和短路径别名；Host 服务还有按 cwd 与配置缓存的快照。因此“渐进披露”说的是模型可见内容分阶段增加，不是进程从未读过文件。

显式选择不必等模型亲自读文件

selection 识别结构化 Skill 输入、资源／文件 mention 和文本显式提及；extension 可在回合输入阶段主动读取选中正文并注入。Core 也保留 Host 加载和去重路径。另一种情况是用户没有点名，模型从目录判断任务相关，再自行调用读取工具。这两条路不能混成“所有相关技能都会自动载入”。

Skills extension 的目录片段是 developer role，选中正文则是带 skills.selected_skill_instructions 分类的 user 片段。它没有把每篇技能正文都升级为 system prompt。自动注入、文件读取结果和后续脚本输出，也有不同的历史类型与预算。

案例分支：从技能名到真正的测试动作

用户：使用 $order-tests 补齐这次边界测试
目录：order-tests — 订单边界测试流程 — 来源位置
选中正文：先读 references/boundaries.md，再补测试
资源读取：检查阈值前、阈值处、阈值后的三个输入
模型提出动作：补 99 / 100 / 101 三个测试
工具实际执行：修改文件，运行测试，回传输出

技能名、正文和资源内容均为教学构造。资源来源的 skills.read 用 package 和可选 resource 寻址；省略 resource 读取主文件，引用资源按返回的标识读取。读取脚本说明不等于执行脚本；执行仍要使用已注册工具与对应环境。

和上下文管理的连接目录预算控制常驻线索，正文与资源按需进入历史，工具结果另有输出限制。稍后 compaction 整理的是这些已进入窗口的材料；它不会因为知道技能目录，就自动恢复每份已读资源的原文。

STEP 06

MCP 与工具怎样变成可调用能力

有配置、已连接、模型可见、执行成功并不是同一状态

手机里存了餐厅号码，不代表已接通，更不代表已经下单。

这一幕记住连接、工具定义进入模型视野、调用成功，是不同阶段。tool_search 在已有目录中找工具。

菜谱是 Skill，店铺提供动作是 MCP。插件可同时贡献两者；读菜谱不会自动完成依赖安装或授权。

自测：issue-tracker 已连接，为什么模型仍可能需要搜索工具？

连接负责与 server 通信，搜索负责将已有目录里的延迟工具定义带入模型可用范围。两者降低的成本、发生的时机都不同；搜索本身也不等于执行。

展开源码推演与订单测试案例

继续这个教学分支：假设订单规则还要从一个已配置的 issue-tracker MCP 查询。Skill 说明了工作方法，MCP 提供外部动作；插件可以同时贡献两者，它们却走不同的加载链。

  1. 01汇集会话、插件和所选执行环境的 server 配置，施加策略约束
  2. 02通过 Stdio 或 Streamable HTTP 建立连接，initialize 协商能力
  3. 03分页取得工具目录和元数据，构造 MCP binding
  4. 04ToolRouter 结合内建、扩展与动态工具，决定本次怎样曝光
  5. 05模型发起调用后，检查刷新状态，准备绑定，再处理审批与执行

这是常规连接路径；源码也有缓存目录、预热和条件性的延迟初始化。普通来源使用 Eager，SubAgent 来源选择 LazyWhenCached，后者还需缓存及实现条件满足。不能从“模型已经看到目录”推断 server 已完成初始化。

方式怎样进入模型可用范围在案例里的含义
Direct本次请求直接带工具 schema模型可直接提出查询规则的调用
Deferred先给目录线索，搜索后返回可加载定义先检索 issue 相关工具，再获得参数定义
Code Mode通过代码入口使用嵌套工具外层入口不必列出每个工具为顶层 schema
Hidden／排除受策略和预算等控制配置中存在并不保证模型可以调用

tool_search 在当前 deferred 工具目录上建立 BM25 索引，返回可加载的工具定义。它不是联网找一个新 MCP，也不是安装器。搜索是否启用、工具怎样曝光，还取决于模型支持、命名空间设置和工具计划。

同一个查询，在哪一层失败？

目录线索：issue-tracker 可以读取需求记录
搜索：查找读取订单规则的工具
加载定义：read_issue(id)       ← 教学简写
模型调用：read_issue("SHIP-42")
调用准备：刷新检查 → 当前 binding → PreparedMcpCall
实际结果：满 100 免运费        ← 假想外部返回

搜索有结果只证明找到了定义；连接失败、工具被移除或执行前审批未通过，都不能算查询成功。MCP handler 会在执行前检查 dirty refresh，并把 client、metadata 与配置绑定到本次 prepared call；不能把 StepContext 理解为把外部连接永远冻结。

两种 MCP 内容，别混成一种MCP tools 给出可调用动作；MCP resources 提供可读内容。Orchestrator skill 可以经 resource 接口读取，但这不意味着每个 skill 都注册成一个 MCP tool。读 skill、加载 schema、执行工具分别进入不同链路。

配置与调用绑定：手册 §7.7 · MCP 生命周期；曝光、Code Mode 与插件：手册 §7.8 · 工具加载

STEP 07

让变化进入上下文

第一次全量构造，之后比较状态

聚餐改成素食了，桌上的旧菜单要怎样处理？

写入 rollout 的是另一份数据：第一次 full snapshot，后续 JSON Merge Patch。比如 {"tools":{"db":null}} 表示从工具目录删除 db；它不是发给模型的自然语言通知，也不删除任何数据库数据。

机制主要减少什么不能推出什么
Prompt cache重复前缀的模型计算缓存命中不代表上下文不占窗口
WebSocket 增量重复传输的 payload网络只发增量不代表模型只看增量

Lite 前缀 ID 由 UUIDv5(thread namespace, payload 字节) 确定。它让同一任务重试时的身份稳定，但不是缓存命中证明；store:false 也不排除 WebSocket 的临时连接状态。案例里追加 ΔR 可能保留旧前缀，而安装快照 C 会重写历史结构，两者的缓存条件不同。

推论边界压缩比不是任务质量，缓存命中率也不是任务质量。应同时记录任务是否完成、约束是否保留、重复操作次数、token 与延迟。

  2. 到 compact_remote_v2_attempt.rs，找到压缩请求保留了哪些字段、追加了什么控制项。
  3. 到 compact_remote_v2.rs，检查输出数量、保留候选、64k 预算及顺序。
  4. 到 compact.rs，确认 BeforeLastUserMessage 的插入点。
  5. 到 session/mod.rs，追踪 replacement history、WorldState 基线与 token 重算。
  6. 最后读相关测试断言，检查请求路径和恢复视图；把“读过测试”和“运行通过”分别记录。

做自己的 harness 时，从这些不变量开始

保持调用与结果配对；区分采样时的工具计划与执行时的 MCP 调用绑定；把 Skills 的目录、正文和资源读取分层；把可恢复规则放在明确状态源中；为压缩请求本身留预算；用 replacement checkpoint 恢复模型视图。这些可以逐条验证，再讨论哪种摘要模型更好。
