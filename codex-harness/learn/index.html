STEP 01

先划清模型和 harness 的边界

谁提出动作，谁执行动作，谁保存状态

你说“修好这个测试”。模型可以提出修改，真正读文件、执行测试、限制权限和保留进度的，是运行时。

这里的 harness 指把模型、工具、环境和会话串起来的程序。模型返回一个工具调用，harness 才会把它派发到执行器，再把结果送回下一次模型请求。

MODEL

决定下一步

根据当前输入生成回答或工具调用。能看见什么，取决于这次请求。

HARNESS

组织与执行

构造请求、运行工具、处理取消和审批、管理历史与窗口。

ENVIRONMENT

承载实际结果

工作区里的文件、进程和外部服务。它们的状态不会随聊天摘要自动重置。

开源仓库让我们能追踪客户端的这些机制，但不能看到模型权重或远程压缩服务的内部算法。本页只解释固定源码快照，不把它推广成所有已发布版本和账户的实际配置。

自测：模型说“测试已通过”，harness 就可以把任务标为成功吗？

不能仅凭这句话。应检查工具是否执行、输出和退出状态是什么；模型陈述与环境结果是两份证据。

源码与边界：手册 §1 · 开源范围

STEP 02

一条请求为什么会跑很多轮

一个用户回合，不等于一次模型采样

假设修复过程是：读测试 → 读实现 → 改代码 → 运行测试 → 看到新失败 → 继续修改。每次工具结果都可能改变下一步选择，run_turn 因而要反复采样，而不是发完一次 API 请求就结束。

StepContext 是这一层的重要约束：本次模型看到的工具定义、实际使用的路由、环境、MCP 和 AGENTS.md 来自同一份请求快照。对 Java 开发者，它接近不可变的 request-scoped 对象。

自测：请求发出后工具目录刷新，为什么不应直接替换这次请求的执行表？

否则模型选择工具时看到的是旧定义，执行时却可能按新定义处理。请求快照把“这次看见什么”和“这次能执行什么”绑定起来。

沿调用链阅读：手册 §2 · Session 与 StepContext

STEP 03

把 context 拆成三种状态

正在看见、可以重建、已经保存

修复进行到第 80 次工具调用时，磁盘可能仍有旧日志，模型下一次却不一定能看到它们。要理解 compaction，先拆开三个容器：

状态例子作用
活跃模型历史消息、工具调用、结果、reasoning、compaction item组成下一次请求的历史视图
当前 canonical state权限、AGENTS.md、环境、模式和能力生成初始化上下文及后续差异
持久化记录Rollout、replacement checkpoint、窗口标识恢复会话与重建历史视图

ContextManager 保存有类型的 items 和元数据，而不是一大段字符串。这样才能识别真实用户输入、区分程序注入内容、维持工具的调用／结果配对。

减小上下文也从工具结果入历史时开始：先限制大输出，发送前再修复配对和处理不支持的模态。你看到的“压缩提示”只是整套 context 管理中的一个环节。

自测：磁盘还保留完整对话，能否据此断言模型“没有忘记”？

不能。持久化解决的是保存，模型窗口解决的是当前可见性。还需要明确的检索或重注入路径，才能把保存的内容带回当前请求。

结构与整理规则：手册 §3 · ContextManager

STEP 04

基础指令究竟从哪里来

固定文件、模型目录和会话继承共同决定来源

你在 GitHub 找到一个 prompt.md，还不能据此确定某个会话用的是什么。Session 启动时按下面顺序选择基础指令，命中前一项就不再回退：

  1. 01显式配置的基础指令，包括指令文件解析结果
  2. 02恢复／fork 历史保存的 session_meta.base_instructions
  3. 03当前模型目录中的 instructions_template

模型目录既有编译打包的版本，也有远程元数据和磁盘缓存。model_instructions_file 替换基础来源；developer_instructions 则是另一条附加内容路径。

特殊之处 · wire 结构也会变普通 Responses 使用顶层 instructions 和 tools。启用 use_responses_lite 的模型分支，会把基础指令作为 developer 消息、工具作为 AdditionalTools 放到 input 前面。

因此，日常说的“system prompt”至少要再问一句：说的是服务端 system、客户端基础指令，还是历史里的 developer／user 上下文？它们不是同一个字段。

自测：更新客户端后恢复旧会话，一定会采用仓库最新默认 prompt 吗？

不一定。没有显式覆盖时，保存的会话基础指令优先于当前模型模板。还要检查实际模型目录和会话继承状态。

完整优先级与 Lite 分支：手册 §7 · 指令加载

STEP 05

让变化进入上下文

第一次全量构造，之后比较状态

任务运行时，工作目录、规则或可用能力可能改变。Codex 用 WorldState 把这些内容分成可保存快照、可生成差异的 section。

项目 AGENTS.md 按 root → cwd 发现，同目录优先选 override，再选普通文件和配置的 fallback；项目内容有共享字节预算。它进入 user-role context，不会因为文件名而提升成 system 权限。

Skills 目录也不等于所有技能正文。目录主要告诉模型有哪些技能、描述与来源；正文随后按选择和加载规则读取。工具表还可以区分直接可见、Code Mode 和延迟发现，减少不必常驻的定义。

边界 · 状态更新不等于每次重新读盘AGENTS 管理器有缓存与刷新条件。不能把 WorldState 的差异比较解释成“每次采样都重新读取所有 AGENTS.md 和 SKILL.md”。
自测：为什么追加“当前权限变更”通常比修改历史开头更利于缓存？

追加可能保持原有前缀不变；修改前面的消息会让匹配在修改位置中断。但工具表、模型等其他字段也可能改变，不能因此保证一定命中缓存。

状态 section、发现与缓存：手册 §7.4–7.6

STEP 06

什么时候应该压缩

先问计数口径，再问阈值

自动压缩的判断由程序执行。计数结合最近一次服务端用量，以及其后新加入的本地内容估计；本地估计并非精确 tokenizer。

普通 Total 口径下，自动阈值默认是当前解析窗口的 90%，显式设置只能在这条公式内进一步收紧；完整可用窗口还有独立上限。

W = 当前解析的上下文窗口
C = 显式自动压缩预算（若配置）
p = effective_context_window_percent

A = 未配置 C 时取 floor(0.90 × W)
    否则取 min(C, floor(0.90 × W))
H = floor(p × W / 100)
测试输入自动阈值 A可用上限 H
W = 272,000
C = 250,000
p = 95		244,800258,400

以上数字来自源码测试 fixture，用于解释公式，不是当前账户的模型规格。

还有 BodyAfterPrefix 口径，只把初始 prefix 之后的增长计入自动预算，同时继续检查完整窗口。相应配置还可能加入 fallback buffer，不能把所有路径压成一个固定百分比。

检查点包括新回合采样前、需要继续执行的采样／工具结果之后，以及某些模型切换场景。手动压缩则走独立的 CompactTask。

自测：把配置预算设成 250k，上面的例子会等到 250k 才压缩吗？

不会。普通 Total 口径取 min(250,000, 272,000 × 0.9)，结果为 244,800。真实触发还要结合续跑条件与相关 buffer 配置。

公式、口径和调用点：手册 §4 · 压缩触发

STEP 07

沿三条 compaction 路径往下走

同一个生命周期名称，背后可能是不同机制

Remote V2：把压缩变成协议中的动作

客户端整理历史、保留基础指令和工具表，追加 {"type":"compaction_trigger"}，通过普通 Responses 流发出。它要求接收恰好一个 compaction item，再安装新的历史。

版本差异 · 别照搬早期文章此快照的 V2 集成测试检查 /v1/responses。早期资料里的独立 /responses/compact 是另一条描述，不能拿来替代当前调用链，也不能据此宣布公共 compact API 已取消。

Local：客户端编排交接总结

把进度、决策、约束、剩余步骤和关键引用总结出来，再与近期用户消息拼成新历史。“Local”描述的是客户端编排，模型本身仍可能运行在远程。

TokenBudget：直接切换窗口

它跳过自动总结，重建 initial context。公开仓库另有 history-notes extension 提供历史检索和笔记能力；启用需要看实际开关、模型、provider 与认证条件，不能把它与普通总结混用。

自测：读完 Local 的公开总结模板，能否说明 Remote V2 使用同样的内部 prompt？

不能。V2 交回不透明的 encrypted_content，公开客户端只展示控制项、传递和保留机制，不能揭示服务端内部摘要格式或算法。

三条实际调用链：手册 §5 · Compaction

STEP 08

压缩后怎样接着干活

原始保留、任务摘要、规则重建各司其职

假设第 80 次工具调用刚结束，模型还需要修测试。Remote V2 按候选筛选与共享 64k token 预算保留原始消息；Local 则按 20k 估算 token 预算保留用户文本，两者都偏向较新的内容。

这两个数字不是摘要大小，也不是窗口大小。V2 还有图片、agent 消息及客户端 developer 消息的不同规则，预算边界处可能截断消息。

关键是 REBUILD：当前规则从程序维护的 canonical state 重建。手动或回合前压缩会清除 reference baseline，下一次正常构造时再全量注入；回合中则立即插到最后一条真实用户消息之前。

之后保存 replacement_history 和窗口标识，恢复会话时重建这份模型视图。压缩完成不要求重启整个任务或重置真实工作区。

自测：重新注入 AGENTS.md，是否意味着所有早期用户约束都不会丢？

不意味着。AGENTS.md 有可靠状态源可重建；只出现在早期用户消息中的特殊要求仍受原文预算和摘要质量影响。需要以约束保留和实际行为评测。

筛选细节与恢复布局：手册 §5、§6

STEP 09

分清缓存、传输与记忆

少算一点、少发一点、少放一点，分别需要证据

机制主要减少什么不能推出什么
Prompt cache重复前缀的模型计算缓存命中不代表上下文不占窗口
WebSocket 增量重复传输的 payload网络只发增量不代表模型只看增量
Compaction活跃窗口中的历史内容变短不代表无损或下一轮必然命中缓存

当前 WebSocket 路径已支持 previous_response_id：请求属性匹配、input 是此前请求加输出的扩展时，才可发送增量。早期“Codex 不使用 previous_response_id”的说法不适用于这份源码的全部路径。

Remote V2 追加 trigger 的请求结构可能保留原前缀；但压缩前的整理、工具变化、模型切换都会改变条件，压缩后安装的新历史通常也不再是旧历史的严格扩展。

推论边界压缩比不是任务质量，缓存命中率也不是任务质量。应同时记录任务是否完成、约束是否保留、重复操作次数、token 与延迟。
自测：网络日志显示第二次只发送了工具结果，模型是否已经看不见最初需求？

不一定。满足增量条件时，服务端通过上一 response ID 延续已接受的输入。要看完整逻辑请求，不能只看本次传输的 delta。

缓存条件和增量匹配：手册 §8 · 三种机制

STEP 10

用一条调用链检验理解

从“仓库里有这个函数”走到“这次会经过它”

读开源 harness 时，最容易犯的错是看到一个函数，就把它当成产品默认行为。用下面这个练习把入口、条件、数据和结果连起来。

练习场景 · 人为指定条件TokenBudget 关闭，provider 声明 Remote V2；当前请求仍需续跑，窗口预算到限。你要解释下一次模型请求看见什么。这里是在分析假设路径，不是在描述当前账户的运行状态。
  1. 从 session/turn.rs 找到预算检查与 run_auto_compact，确认路由条件。
  2. 到 compact_remote_v2_attempt.rs，找到压缩请求保留了哪些字段、追加了什么控制项。
  3. 到 compact_remote_v2.rs，检查输出数量、保留候选、64k 预算及顺序。
  4. 到 compact.rs，确认 BeforeLastUserMessage 的插入点。
  5. 到 session/mod.rs，追踪 replacement history、WorldState 基线与 token 重算。
  6. 最后读相关测试断言，检查请求路径和恢复视图；把“读过测试”和“运行通过”分别记录。
参考答案：哪四件事足以说明你追踪到了真正的执行路径？

能指出入口条件；画出实际发出的请求；解释哪些原始 item 保留、哪些规则重建；说明 checkpoint 怎样安装和恢复。至于加密压缩项的内部语义和真实质量，仍需服务端资料或实测支持。

做自己的 harness 时，从这些不变量开始

保持调用与结果配对；让请求的工具表和执行器来自同一快照；把可恢复规则放在明确状态源中；为压缩请求本身留预算；用 replacement checkpoint 恢复模型视图。这些可以逐条验证，再讨论哪种摘要模型更好。
